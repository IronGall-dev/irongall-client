**Purpose:** the verifiable client side of irongall.dev. People are pointed here to check client behaviour, because the server is never trusted.

**`PROTOCOL.md` is the spec, and it is public like the rest** (it moved here from the server's repo on 2026-10-12). A change to the wire, to a check or to a refusal changes it in the same commit as the code. It describes the server only as a client meets it (routes, checks, refusals, what it promises to store): never how the server stores things, a server setting's value, a person's words, or a document that is not in this repo. What is specified and not built says so where it is described and in its §12, and is an issue in the milestone `M1: protocol freeze`.

**`PRECEDENTS.md` is the one place a comparison with another system is kept** (public here since 2026-10-12): Part 1 sets irongall beside whole systems, Part 2 each decision beside the system or standard that does the same. A row is added the day a big decision is made. Every claim about another system says how it is known: `read <date>` with its source, `review 2026-10-10`, or `from memory`; never a number from memory as if it were read. `PROTOCOL.md` cites it at its top and keeps a short mention where one helps at that step, with a pointer; do not grow a second table anywhere. Like the spec it holds nothing of how the server is built, nobody's words, and no file outside this repo.

**The README says as little as it can**. It holds what an agent must know to run a box safely, each command once, and pointers: the detail lives in `PROTOCOL.md` and the code. Before adding a line there, find one to cut. **Two of its lines are the maintainer's and are not ones to cut**: the status line's freeze date, which moves only on his word, and the line that sends a reader to the open issues for known gaps and welcomes new ones. That line's last sentence, that the tracker is public, was added with it and is not his. **Where the README or the spec states a limit that an open issue plans to change, the issue's number sits beside the statement** (agents asked to judge the service from its public pages read a limit with no number beside it as permanent, 2026-10-12). **Its status line never lists the operator or Cloudflare as a limit**: Cloudflare is said once, in § No Server Trust, as how irongall.dev is run today, and `PROTOCOL.md` §9 says it the same way. Three tests hold lines of it: `TestHelpAndREADMENameTheEchoBox` here, one in the server repo that requires the command its link page gives to be a line of this README, and one kept with irongall.dev's site that requires the same of every command in its `llms.txt`. So a command line there is changed in each place that gives it.

**Design priorities, in this order**: the correct encryption; then a server that is feasible and fast, not as cheap as possible; then simple things simple for the user. **Until the protocol freeze, a fix is chosen for being correct:** backwards compatibility and leaving the wire unchanged carry no weight, in a design, in an issue or in a recommendation. **Nor does an old tool:** the design assumes a current client and a modern library, and what the oldest `ssh-keygen` or `age` the script runs on can do is never a reason for or against a design. The script's floor follows the design.

**A design follows industry practice, read at its source** (an RFC, a major system's documentation, then its code), and never this project's own earlier choice. **Where a standard has a reference implementation, its behaviour is the practice:** OpenSSH for SSHSIG and certificates, age for age. A statement of the design that differs from that practice is challenged, whoever made it. **A deviation is discussed and justified as part of the design:** its reason is written in `PRECEDENTS.md` beside the systems it differs from, and one with no reason there is a defect.

**Clocks: every check is exact at the clock of whoever makes it, and whoever makes a time-limited thing leaves `protocol.MaxSkew`, an hour, of room** (`PROTOCOL.md` §0; `PRECEDENTS.md` § Clocks; decided on #40). 🛑 Do not add an allowance to a check, and do not make a thing that asks for exactly what its verifier takes: a certificate starts an hour before it is made, a server takes a prekey up to an hour past what a client asks for, a reader takes a `sent_at` up to an hour ahead. 🛑 **A test of anything timed uses two clocks.** Every test here once shared one, so none could see that a box two seconds fast could not register (`client/clock_test.go` is the pattern). A client reports how far its clock is from a server's, as the server's word, and never adopts it or tells its reader to: its own words point to a time source the reader trusts. An outbox entry dated ahead of the clock is held at every attempt, sealed or not. 🛑 A key that mail may be waiting for is never deleted to recover from a wrong clock: a box cannot know a statement was never published.

**Rules every client here keeps:**
- Verification always on, with no flag to skip it.
- Fail closed: a failed check stops, never warns and continues.
- Message bodies are untrusted data.
- State lives in `~/.config/irongall/<name>/` (0700), never the working directory.

**Layout:** the repo's, `README.md` § What is here; a box's files, the top of `client/doc.go`. One on-disk format, in the stock tools' own file formats (OpenSSH key, age key files), so a stock-tools client and the Go client run the same box. The identity is a plain OpenSSH key file, no seed, no passphrase.
- **`sent/` and `aliases` are in that format too:** a `sent/` record is the delivered line plus `receipt`, and `aliases` is `<name> <address>` lines, which either client and a person may write. A name is never moved by a client.
- **The consumer lock is `irongall.sh`'s `lock/` directory**, plus a flocked `lock/pid` so a crashed Go client's lock is taken over; a `lock/` with no `pid` is the script's, never taken over and never written into (`client/lock.go`).
- **`sh/irongall.sh` is the proof, not the client to run**: it shows that what the Go client encrypts and signs is what stock `age` and `ssh-keygen` read. So it need not gain every feature the Go client gets, and the README says to use the Go client.
- **It is kept explainable:** a check that only buys convenience stays out, and what it lacks against the Go client is listed in `README.md` § Stock tools instead of Go. A security check is never one of those gaps: it matches the Go client's verdict on every vector.
- **Dependencies are minimums, never pins, and move to the latest by committed updates:** bump `go.mod` in a commit (`go get -u ./... && go mod tidy`, tests green), never inside a build, so every build matches a commit and `go install …@latest` gets the new versions. `go.sum` is checked against the Go checksum database.

- **No mutation pass:** the hand-listed one was deleted 2026-10-11 as more pain than it found. Do not add one unasked.
- **Vectors:** `testdata/vectors/generate.sh` uses stock tools only (age ≥ 1.3 just for the one ciphertext, which it keeps). A re-run must change nothing but what you meant to change; diff the tree. Its keys are PUBLISHED test keys: RFC 8032's for every Ed25519 key, and RFC 6979 §A.2.5's for box C's P-256 identity. Never put any other private key in this repo. A certificate is made once and kept, since a second run cannot make the same bytes.

**A prekey serial is signed once** (`client/rekey.go`, `ig_renew`): a renewal the server did not take is sent again as it was signed, and a new key goes to a later number only when that statement has expired or, in the Go client, another type is asked for (the script keeps the pending key whatever type is asked). Signing the same key again with a later `not_after` gives a server that fails renewals and keeps the uploads one key without end (found 2026-10-11).

**What is encrypted is the envelope's line, its signature, then padding** (`protocol/signed.go`, `seal` in `client/send.go`, `ig_seal`; `PROTOCOL.md` §4.4; decided on #29). It is git's layout for a signed tag, and three rules for a reader came from what went wrong in git's verifiers (`PRECEDENTS.md`, Part 2, § 3): verify line 1 exactly as decrypted and never anything rebuilt; each part has one place and nothing after the first END line is read; one signature, one identity, the verifier's exit status. 🛑 A change to how a reader takes the parts apart breaks one of them: `OpenSigned` and `ig_open` are held to each other, code for code, on every `plain/` vector (`TestVectorsPlain`). 🛑 **A format's overhead is a fixed number of bytes, never a share of the message**: the envelope as base64 inside a JSON object was refused for that.
- **The outbox's `.P` is the signed line, its line feed included,** in both clients, and it carries the box's identity document. `recv`'s line, `inbox/` and `sent/` are built from the checked fields without it.
- **Every send is padded, at the seal and never before,** with bytes after the signature (`protocol/pad.go`, `ig_padding`). The padding is outside what is signed, so a message already on a block gets none: that settles what the `pad` member's flat 9 bytes were for. The block is counted on the ciphertext, from age's file sizes (`SealedSize`: a header fixed per key type, a nonce, a tag per 64 KiB chunk), and each client then checks the size of what age wrote and refuses a mismatch. No flag turns padding off or on. Change the arithmetic in both clients together: `TestPaddingIsTheGoClients` in `sh/` holds the script to the Go client's, and `TestSealedSizeIsWhatAgeWrites` holds the header sizes to age itself, so an age release that changes them fails there first.

**Exit status 3 is "done, and the box needs a look"** (`needsALook` in `cmd/irongall`): `recv` after a failed renewal, `status` with a non-empty `attention`. Refused mail never changes `recv`'s exit status, because any sender can cause a refusal.

**Nothing someone else wrote is printed as this client's words** (found 2026-10-11). A refusal is a code from the closed set in `client/errors.go` and `protocol/envelope.go`, with fixed words: never a value, key or field from an envelope, a served identity or a served statement. A server's `detail` and `hint` go through `plain` and are printed in quotes after "the server says". A new error path that formats outside text with `%s`, `%q` or `%v` breaks this: `TestARefusalNeverQuotesTheMessage` and `sh/test.sh` § 14 hold the envelope's.

**A box's identity signs certificates and nothing else; a working key signs what the box says** (`protocol/certificate.go`, `client/work.go`, `ig_work`, `ig_cert`; `PROTOCOL.md` §2b; decided on #30). Each client makes a new working key, with a new certificate, each time it makes a new prekey, and keeps it as `work/<serial>` in the names `ssh-keygen` uses. A client asks for 65 days and a verifier takes 66. `CheckCertificate` checks one certificate against an identity and a clock; holding its serial to an order is the caller's (`Resolve` does, for a peer's prekey statements). 🛑 `ssh-keygen -Y verify` takes a certificate with extensions, another key id or serial 0, so the script reads a certificate's fields from its bytes: `TestVectorsCertificate` holds that control, and a `cert/bad-*` vector for each rule.

**An identity is a key of a type `PROTOCOL.md` §2 defines** (`identityTypes` in `protocol/identity.go`, `ig_idcheck`; decided on #21): `ssh-ed25519`, which every client makes and verifies, or the optional `ecdsa-sha2-nistp256`.
- **A type is added in both clients together:** its one exact form, its key checks, and a vector for each document a client must refuse. Where the Go library and `ssh-keygen` differ on a key, the stricter rule is written into the spec and made explicit in the other client, so one document gets one verdict (`TestVectorBadIdentities`, `TestVectorsIdentity`).
- **A well-formed document of a type a client lacks is `unsupported_key_type`, never `bad_identity`,** and only once it is known to be the sender's: a malformed document points at tampering, and one of another type does not.
- **With each prekey a client declares the key types it verifies** (`sender_key_types`, §2c; `IG_SENDERS`): all of them, and never `any` unless it is told to. An optional type is never what a client makes by default, and `init --identity-type` warns.
- 🛑 **Nothing may rest on a certificate having one set of bytes:** one that an ECDSA identity signed has other encodings ((r, n − s), and either number padded with zero bytes), which anyone can write and both verifiers take (`TestAP256IdentityCertifies`).
- 🛑 **The script compares a document with itself rebuilt, byte for byte** (`ig_idcheck`): a shell variable drops a NUL, so a test of the variable alone passes a file that holds one. `identity/nul-*.doc` hold it to that.

**A signature is read as `ssh-keygen -Y verify` reads it, with two checks more** (`protocol.Dearmor`, `sshsig.Verify`, `ig_blob`, `ig_sshsig`; `PROTOCOL.md` §3; decided on #38): its armour as OpenSSH's `sshsig_dearmor` reads it, and `reserved` skipped and signed as empty, as `sshsig_wrap_verify` does; then at most `protocol.MaxSignature` bytes, and an Ed25519 S below L. A check beyond OpenSSH's is a deviation, with its reason in `PRECEDENTS.md`. The script reads the armour itself and never through `sed` and `base64 -d` alone, which refused forms `ssh-keygen` takes: `TestVectorsSignatureForm` holds both clients and `ssh-keygen` to one verdict on each `sig/` vector.

**Every JSON text is read by one set of rules, by every reader** (`protocol.Unmarshal`, `protocol.UnmarshalRequest`, `ig_json`, `ig_shape`, `ig_bytes`; `PROTOCOL.md` §0b; decided on #66 and IronGall-dev/irongall-server#17): I-JSON, one object, names matched exactly, nested at most 32 deep, an integer member from 0 to 2^53 − 1 written as one, a byte member base64 in its one encoding, and null as if the member were left out. A request's unknown member is refused; an answer's and an envelope's are ignored, and the rules hold in them.
- **The parsing is Go's `encoding/json/v2`, so the module needs Go ≥ 1.27.** A check beside it is one it does not make (depth, noncharacters, the integers). 🛑 Never `encoding/json`'s `Unmarshal` on a text a server, a sender or a file brought: it matches names in any case and keeps the last of a name given twice. Writing with it is fine.
- **The script adds to jq what jq does not check:** it skips a byte-order mark, takes `NaN`, `01` and `+1`, and keeps the last of a name given twice; and glibc's `iconv` takes a code point above U+10FFFF. `TestVectorsJSON` and `TestVectorsAnswer` hold its verdict to the Go client's on every `json/` and `answer/` vector, and jq ≥ 1.7 is needed for the integers: it gives back `1.0` as written.
- **A serial is at most 2^53 − 1 everywhere** (`protocol.MaxSerial`), since a send carries two as JSON numbers.

**A box proves itself with a pass it signs, and there is no token** (`protocol/pass.go`, `pass` in `client/work.go`, `ig_pass`; `PROTOCOL.md` §6.1b; decided on #36). The pass is kept in the box and used until 30 seconds before it runs out; if a server refuses it, a client signs another and tries once more. A registration and a prekey upload carry a pass under the certificate of the statement they bring (`publish`), which is kept only once the server took it. Nothing a server sends is decrypted with a key that reads mail: the token that was (`IsToken`, found 2026-10-12) is gone.

**A box never asks the server who a sender is, and pins one only once its signature verified** (`judge`, `pin`, `ig_meet`): the envelope carries the identity document, whose hash is the sender. The one thing it asks about a sender is whether a revocation of it exists, once in a drain and only after that sender's signature verified. On a send, a peer is pinned only once something its identity signed has verified: its prekey statement, or a revocation or a list that the lookup before the post brought. A drain is bounded (`maxDrain*`).

**An address is revoked by its identity's own signature, and a client takes "revoked" on nothing less** (`protocol/revocation.go`, `client/revocation.go`, `ig_revcheck`, `ig_gone`, `ig_lookup`; `PROTOCOL.md` §6.3; decided on #14).
- **A server's `revoked` or `sender_revoked` is checked, never believed:** `proved` asks for the record, and only one that verifies makes a `RevokedError`. Without one the call has failed and no state changes. 🛑 Neither code may go back into `undeliverable`.
- **A revocation that verified is kept and never removed** (`peers/<address>/revoke.sig`, `revoked.sig` for the box's own), read again and checked again at each use. `Resolve` refuses such a peer before any request, and `judge` refuses its mail, whenever it was signed.
- **A working key's signature is not a revocation:** `VerifyRevocation` verifies against the identity's bare key, and the script's signers line carries no `cert-authority`. `revoke/bad-by-a-working-key.sig` holds both to it.
- **A negative answer and no answer are different things** (`lookupRevocation`, `ig_lookup`): `not_revoked` lets a drain go on, and anything else stops it with the mail still on the server.
- **The statement is fixed text and never gains a field.** What is added later is a second statement under a new tag, beside it: a slot nobody fills is one that fails when it is used, and a rule to refuse what a reader does not understand would turn a revoked address back into a live one.
- **`revoke` takes the address in full as its confirmation,** and neither client writes a record unasked: beside the identity it is lost and stolen with it.

**Certificates are revoked through a serial their identity signs, and a box's statements are ordered by certificate first** (`protocol/revokedcerts.go`, `client/revocation.go`, `ig_certscheck`, `ig_certrevoked`, `ig_keepcerts`; `PROTOCOL.md` §6.3a, §2b; decided on #51, #48 and #79).
- **The order is the certificate's serial, then the prekey's own** (`Resolve`, `rekey`, `ig_resolve`, `ig_renew`): a later certificate passes any serial under an earlier one, and a renewal's number is above the served CERTIFICATE's. 🛑 Comparing prekey serials across certificates brings #48 back: one use of a taken working key, at the highest serial there is, ended the address.
- **A certificate's serial is its maker's clock, in seconds, or one above the highest serial the box knows of when the clock gives nothing higher** (`protocol.SerialAt`, `Init`, `rekey`, `ig_init`, `ig_renew`; `PROTOCOL.md` §2b; decided on #63). The prekey and working key made with it share the number. An identity is a key and keeps no record: a box restored from it knows only what a server shows, and by the clock its certificate is above every one made before, so the revocation of everything below it covers them all. 🛑 **A verifier never reads a serial as a time: it compares two.** Do not add a check of a serial against a clock, anywhere. 🛑 **"One above" stays: do not make it a refusal** (weighed on #73). It covers two renewals in one second, and a last certificate numbered ahead by a lost machine's fast clock, where a refusal would hold the owner's renewal and its revocation back until the clock passed that number (`TestALostMachinesFastClockDoesNotDelayTheRemedy`). 🛑 **A number an attempt took is kept until its statement is published or spent** (`highestBegun`): a new number for every retry would sign a new key each time and leave the waiting one unsent. 🛑 **A test reads a box's number and never assumes one** (`numberOf`, `num` in `sh/test.sh`): every test here once wrote 1, 2 and 3.
- **A send names its prekey by both serials** (`SendRequest.CertificateSerial`, `ig_seal`). The script writes them as the digits it checked, never through jq's numbers: a jq before 1.7 rounds one above 2^53.
- **It is verified as a revocation of the address is, under the identity's bare key, and then parsed exactly.** `revoked/bad-by-a-working-key` holds both clients to the first. The script compares the file with itself rebuilt from its lines, and compares serials in bash, whose integers are exact.
- **The highest serial a holder has verified stands, and nothing lowers it.** One that does not verify, or runs no higher, changes nothing, whenever it arrives: a certificate once revoked is never taken again. 🛑 There is no version and no list: do not add a way to revoke fewer. What is kept is read and checked again at each use, and one that no longer verifies is an error, never "nothing revoked". It is kept as ONE file, the record that carries it (`revoked-certs.json`), moved into place whole: a statement in one file and its signature in another can be left one new and one old by a crash, a pair that never verifies again.
- **A revoked certificate loses everything it signed, whenever it was signed:** `judge` and `ig_judge` refuse its mail as `certificate_revoked`, and `Resolve` and `ig_resolve` refuse a prekey statement under it. The address goes on.
- **A box never makes a certificate its identity has revoked** (`rekey`, `ig_renew`): the next is numbered above the highest serial the box holds revoked, as above any it knows of. One through 2^53 − 1 leaves none to make, and the box says so.
- **`rekey --revoke-earlier` runs `RenewAndRevoke`** (`client/revocation.go`; `PROTOCOL.md` §6.3a). It asks first what is held of its own (`askOwn`), renews above it, sends nothing an earlier renewal left (`rekey`'s `unused`), and publishes the revocation of every certificate below the new one when the renewal was taken or refused as `rate_limited`, and for nothing else. 🛑 **Do not widen that to every failure:** only the day's count is reached after a server has taken the box's certificate and pass as timely, and a revocation numbered by a clock that reads ahead covers certificates not yet made. A box whose own revocation covers the certificate it uses renews at its next drain (`renewIfDue`, `ownRevokes`).
- **The script applies one and makes none** (`README.md` § Stock tools instead of Go).

**A box asks before it posts, and checks the send against what it then holds** (`ask`, `post` and `sealStands` in `client/`, `ig_post`, `ig_under`; `PROTOCOL.md` §4.1, §4.5, §6.3; decided on #55).
- **The lookup comes before anything is sealed or posted, at every post:** a new message or one that waited, sealed or not. The Go client asks once for each recipient in a flush; the script asks every time.
- **No answer holds the message in the outbox.** 🛑 A failed lookup's code is never read as an answer about the message: it does not pass through `undeliverable`, and it never moves an entry to `outbox/failed/`.
- **"None held" is kept nowhere.** Nobody signs it, so it has no time it holds until. Do not add a cache of it: the lifetime it would need is nobody's to invent.
- **A seal that waited is checked against what the box holds, by the certificate serial the seal names,** and made again when that certificate is revoked or the seal cannot be read. 🛑 The script reads that serial as digits from the seal's first bytes (`ig_under`), in the one form both clients write: `{"prekey_serial":N,"certificate_serial":M,"ciphertext":"`. A change to the order of `SendRequest`'s members, or to how either client writes them, makes every waiting seal one the other client makes again: `TestAWaitingSealInBothClients` holds both to it.
- **Whatever verifies is kept, from a server or from a file** (`Ask`, `KeepRevocation`). A record handed over is refused whole when a part of it does not verify, and its owner is told; a server's answer that does not verify counts as nothing shown.

**A box asks revocation servers beside its own server, and publishes its revocations to them** (`client/revocationserver.go`, `ig_revservers`, `ig_lookup`, `ig_revoke`; the reference server is `revocationserver/`; `PROTOCOL.md` §6.3; decided on #52). A revocation is of an identity, and an identity belongs to no server.
- **The name is "revocation server", always both words:** "the server" alone is the box's own, the mailbox server. It was called an index until 2026-10-14, which is no standard's word for it: in the OpenPGP keyserver protocol an index is a listing, the one thing this never gives (`PRECEDENTS.md`, Part 2, § 3b).
- **A revocation server can only add.** What it shows is checked and kept as anything is (`take`, `ig_take`). Its "none held" is its word. 🛑 **And no answer from it changes nothing:** it never holds a send or stops a drain, where no answer from the box's own server does both. Do not let a revocation server's error reach `post` or `judge` as an error: every one a box listed would be one more way to stop its mail.
- **It is asked only once the box's own server has answered, with no pass, for ten seconds at most, and one that gave no answer is not asked again by the same command** (`lookups.silent`): a drain's time on a dead one is one wait, not one for each sender. The script asks again each time.
- **Which ones is the owner's to say,** in `Options.RevocationServers`, `$IRONGALL_REVOCATION_SERVERS` or the box's `revocation-servers` file, in one grammar both clients hold a list to. 🛑 A default is named only for a server whose own operator runs the revocation server: a lookup tells whoever runs one which address its asker corresponds with. A list that cannot be read is an error, and the box asks about nobody until it is put right.
- **A record is published at every server, whatever the others answer** (`publishRecord`): a mailbox server that refuses a revocation does not keep it from the rest. Not everywhere is a failure that says who took it (`NotPublishedError`), and once any server has taken a record its box keeps it. 🛑 What ends an address goes out only with that address written in full: `revoked --publish` takes a list and no revocation.
- **The reference server keeps one file for each address and nothing else.** It verifies before it keeps, answers what it holds again with no check, counts every other record against its caller before checking it, never logs a lookup, and has no route that lists. It imports `protocol/` and nothing of a mailbox server: keep it so, since that it can be built so is what it is for.

**Flags are written with two dashes** in the help, the README, error text and the server's `llms.txt`. Go's flag package takes one dash or two and writes one, so `cmd/irongall` prints a command's flags and a bad flag's error itself (`printFlags`, `oneDash`), and a test holds the help to it.

**The name** is written IronGall in the README's prose, and `irongall` in every command, label, path and format.

**Module path:** `github.com/IronGall-dev/irongall-client`. Installing must never depend on the irongall.dev server.

**`sshsig/`** implements exactly the API the Go team accepted for `x/crypto/ssh` (proposal golang/go#68197): `Sign(s Signer, rand io.Reader, message []byte, namespace string) ([]byte, error)` and `Verify(pub PublicKey, message, signature []byte, namespace string) error`. Verify accepts sha256 and sha512, and reads `reserved` as OpenSSH does: the blob's is skipped and the key signed an empty one (`TestReservedAsSSHKeygen`). When `x/crypto` ships it, check that its `Verify` does the same, then switch the import and delete ours. Its implementation, CL 659715, is unmerged at x/crypto v0.58.0 (2026-10-09).
- 🛑 **An identity key's checks live in `protocol.ParseIdentity`, not in `sshsig`** (Ed25519: small order, non-canonical; P-256: the bounds OpenSSH puts on a point's coordinates): x/crypto's would not make them, and every identity a verifier uses has passed `ParseIdentity` first.
