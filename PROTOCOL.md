# PROTOCOL — irongall v1 (pre-stable)

**The irongall protocol, byte by byte: every step from key generation to ack, with the stock tool used at each step.** It says what a client must check, what a server must do, and what the server at irongall.dev promises. The code beside it implements it: `protocol/` and `sshsig/` (the formats and the signatures), `client/` and `cmd/irongall` (the Go client), `sh/irongall.sh` (the same client in stock tools) and `testdata/vectors/`.

- **Pre-stable.** Nothing here is final until v1 is declared stable (§0a). What has to be settled before that is this repo's issues in the milestone `M1: protocol freeze`.
- **The server is not in this repo.** irongall.dev runs one, written to this document. A client never has to trust it: everything that protects a message is checked by the client, and the tests here play a hostile server (`SECURITY.md` maps each claim to the tests that hold it). This document describes the server as a client meets it: its routes, its checks and its refusals. How it stores things is its own business, apart from what it promises (§7).
- **"Not built" is said where it applies.** A few parts are specified and not yet built, by the server, the clients or both. Each says so where it is described, and §12 lists them.
- **Limits are a server's settings, not the protocol's.** This document names each limit and says what it does, never its value: irongall.dev states the ones a client meets in ordinary use at `https://irongall.dev/llms.txt`. The protocol's own constants are written out (the 33 days of a prekey and of the mail's lifetime, the 65 and the 66 days of a certificate, the 10 minutes and the hour of a pass, the page of 50).
- `[proposed]` marks a detail that is not decided.
- **Why each choice is the usual one is in `PRECEDENTS.md`:** every decision here beside the established systems and published standards that do the same, with their numbers, and irongall beside other messaging systems. This document keeps a mention where it helps at that step.
- **The stock client is `sh/irongall.sh`**, one section per step of this document, tested here against a fake server, honest and forging, and against the test vectors and the Go client (§11). It is the proof that the protocol needs nothing but stock tools; the client to run is the Go one (`README.md`).

## 0. Primitives — all standard, nothing home-rolled

| Name | Role | Spec |
|---|---|---|
| age v1 | encryption to the box's PREKEY: post-quantum `mlkem768x25519` (hybrid ML-KEM-768 + X25519, age ≥ 1.3) by default, or X25519 only (`--no-pq`); HKDF-SHA-256, ChaCha20-Poly1305, HMAC-SHA-256 | C2SP age spec |
| Ed25519 | the WORKING KEY, which signs prekeys, mail, profiles and passes; and the box IDENTITY that certifies it and signs a revocation, in the one identity key type every client makes and verifies (§2) | RFC 8032 |
| ECDSA P-256 | an IDENTITY of the optional key type `ecdsa-sha2-nistp256` (§2): it signs what any identity signs, certificates and a revocation | FIPS 186-5, RFC 5656 |
| SSHSIG | signature container: the key's signature over SHA-512(message), namespaced | OpenSSH `PROTOCOL.sshsig` |
| SSH public key text | `<key type> <base64 wire key>`: `ssh-ed25519`, or `ecdsa-sha2-nistp256` | RFC 4253 §6.6, RFC 8709, RFC 5656 |
| OpenSSH certificate | the identity's word for a working key (§2b) | `draft-ietf-sshm-cert`, OpenSSH's format (its `PROTOCOL.certkeys` until 2025) |
| SHA-256 | address = hash of the identity document; message id | FIPS 180-4 |
| UUID | the envelope's `msg_id`, random (version 4) | RFC 9562 |

**Stock tools, and nothing else:** bash ≥ 4, `age` + `age-keygen`, `ssh-keygen` (OpenSSH ≥ 9.1, the first to take a certificate's validity and a time to verify at in UTC; linked to OpenSSL, on which its verdicts are the Go client's but where §3 says builds differ), `curl` ≥ 7.76 (`--fail-with-body`), `jq` ≥ 1.7.1 (from 1.7 it gives back a number as written, §0b; 1.7.0 can abort on a number a sender writes, CVE-2023-50246, and Ubuntu 24.04's fixed jq prints `jq-1.7`), `iconv`, `sha256sum`, `base64`, `od`. **The Go client `irongall`, in this repo, does all of it.**
- **age ≥ 1.3 is needed to OWN a post-quantum box** (age-plugin-pq has no key generation) **and to send to one** (or age-plugin-pq). Too old for post-quantum: Ubuntu 24.04 (1.1.1, what Claude Code cloud sessions run), Ubuntu 26.04 and Debian 13 (1.2.1; also Docker's `python` and `node` images), Ubuntu 22.04 (1.0.0, which fails with a misleading "malformed recipient"). Fine: Alpine 3.24, Fedora 42+, Homebrew, Arch, Nix 25.11+. Otherwise `go install filippo.io/age/cmd/...@v1.3.2` (verified by the Go checksum database), the release tarball with its Sigsum proof, or the Go client.
- **Portable by construction**: dates go through `jq`'s `fromdateiso8601`/`todate`, never `date -d` (macOS has none; BusyBox rejects the `Z`); base64 is `base64 < f | tr -d '\n'`, never the GNU-only `-w0`.

**Paths:** every API path is under `/v1/`, and the discovery documents (`/`, `/llms.txt`) sit at the root. Every route, member, status and header is also described in OpenAPI, in `api/openapi.yaml` (§13).

**Transport:** a client calls a server, its own or a revocation server (§6.3), over `https` only, but for a server on its own machine, named by its address in `127.0.0.0/8` or as `[::1]`, which it may call over `http`; the name `localhost` is not one, since a resolver says what it is (RFC 8252 §8.3). A URL of any other form is refused before anything is sent, and nothing allows more. **It follows no redirect:** the API redirects nowhere, so a `3xx` is an answer that is not the API's, taken as no answer. A pass is a bearer credential for the minutes it has left (§6.1b), and a lookup names the address it asks about (§6.3): neither crosses a network in the clear (RFC 6750 §5.3), and neither is sent anywhere a server points.

**Keyed hashing is HMAC or HKDF only, never `hash(secret ‖ …)`.** SHA-256 and SHA-512 allow length extension, which breaks exactly that construction. Plain SHA-256 appears here only over PUBLIC inputs — the identity document, the ciphertext, the proof-of-work input — where extension gives an attacker nothing, and it stays: it is what Signal, TLS 1.3, MLS, age, Certificate Transparency and Git's new object format use, and `sha256sum` is on every machine.

**SSHSIG hash:** every verification in this protocol — prekeys, messages, passes, profiles, revocations — accepts `sha512` or `sha256`, the two the SSHSIG spec allows. `ssh-keygen` writes `sha512`. The server's verifier is `sshsig/` in this repo, with exactly the API accepted for `x/crypto/ssh` (golang/go#68197), until `x/crypto` ships one.

**Clocks: every check is exact at the clock of whoever makes it, and whoever makes a time-limited thing leaves an hour of room.** A box's clock is expected to be synced (NTP); the hour is for one that is not quite. It is how a certificate is checked in X.509 and OpenSSH, with the hour Let's Encrypt dates its certificates back by (`PRECEDENTS.md` § Clocks).

- **The hour is the pass's** (§6.1b). A client asks for 10 minutes and a server takes up to 60, so a server takes a new pass from a box whose clock is less than 10 minutes behind its own, or up to 50 ahead, and no two such clocks are an hour apart when each shows a pass.
- **What leaves the room.** A certificate starts an hour before it is made, and is asked for a day under its ceiling (§2b). A server takes a prekey statement that ends up to an hour past the 33 days a client asks for (§2a), and keeps mail an hour less than the 33 days a reader takes it for (§7). A reader takes a `sent_at` up to an hour ahead of its own clock (§5).
- **What has none.** A prekey past its `not_after`, a certificate past its end, a pass that has run out, a `sent_at` older than 33 days: each is refused to the second.
- **A box whose clock is further off is stopped before it fetches any mail it would judge by that clock, prunes its replay set by it, or deletes a prekey by it** (§5 check 9, §6.4). In most cases at its pass, with `401 pass_expired`. A box whose clock is more than 50 minutes ahead when it makes a certificate is stopped a step earlier, when the server checks that certificate (`400 prekey_time`): a server takes one only once it has begun by the clock of every box it takes, 10 minutes before its own, so every certificate a server takes has begun for every reader it takes. A box whose clock has gone back past the start of its own certificate is stopped by its own check of it. Keys are deleted by the clock as it read when the server took the pass, never by a later reading (§6.4).
- **A pass or a statement refused for its time is nearly always a clock,** and a new pass does not cure it. The server dates every answer by the clock its checks read (the `Date` header), and a client sets that date beside what its own clock reads. 🛑 **Those are the server's word, said as that, and a client's own words never tell its reader to set a clock by them:** they point to a time source the reader trusts. A box checks everything against its own clock, and a clock set by a server's lie would make an ended certificate valid again and stale mail fresh.
- **A client does not use a kept pass that has more than 10 minutes left:** it signs none that long, so its clock has gone back since it signed that one. The pass it signs instead is dated by the clock as it is, which is what stops it.
- **A client dates each post at that post (§4.5), and posts no entry written ahead of its own clock.** Such an entry was written while the clock read ahead of where it reads now, and the outbox counts its 33 days from when an entry was written, so it waits there until the clock passes that time. So a post's `sent_at` is its sender's clock when the server checks its pass.
- **A client does not use a kept certificate that began less than an hour before its clock,** as at an `init` or a renewal a server refused: it was made while the clock read ahead of where it reads now, and a reader whose clock the server takes may not have reached its start. The statement and working key made with it are made again, by the clock as it is, for the same prekey at `init`, and at a later number at a renewal (§6.4).
- **What this does not cover.** The window is checked when a pass is first shown, and a server may remember that pass for its ten minutes. A clock that moves by minutes inside those ten, or goes back by more than an hour in the middle of a drain, can still put a `sent_at` past a reader's hour, or have a reader judge mail by a clock no server took, and that reader refuses the message. It is a verdict like any other: the message is quarantined with what the checks found, the reader's clock among them, so its owner can see whose clock it was, and nothing is held for a clock to catch up (§5, "The verdict"; `PRECEDENTS.md` § Clocks). Each case needs a clock that is already wrong.

## 0a. Compatibility and versioning

🔑 **Pre-stable: nothing is final until v1 is declared stable.** Until then the live service is the test bed, and fields, formats and what is required may still change. The rules below bind from that declaration:
- **A server REFUSES a member it does not know in what it is sent** (`400 bad_request`, with the member in its `member`, §13): a mailbox server's requests, and a revocation server's.
- **Every other reader IGNORES one:** a client in a server's answer, a box in an envelope (§4.2), and whoever a later version has receive what a server sends. §0b's rules still hold in it. The envelope's `v` changes only for a breaking change, and a receiver rejects a `v` it does not know.
- **Signed statements match their format EXACTLY** (identity document, prekey statement, pass, revocation, revocation of certificates). A new format gets a new tag. Namespaces are versioned independently.
- **New v1 fields are added as optional.**
- **A server may add a route inside v1.** A client reads the router's plain `404` or `405`, with no code, as a route that server does not offer (§13), and a `404` with a code as that code.
- **`irongall-revoke-v1` stays valid forever**, so a revocation signed in advance keeps working.
- **A new identity key type is an addition inside v1.** The identity document has one form for every key type (§2), so a type defined later takes no new tag: a client that does not verify it refuses it with a code of its own, and each box declares the types its client verifies (§2c). A post-quantum signature key would come this way, as a key type.
- **A new prekey type is an addition inside v1** in the same way. A prekey statement's key is an age recipient (§2a), so a type defined later takes no new tag: a sender that cannot encrypt to it refuses the statement as `unsupported_prekey_type`, never as a statement that does not verify.

**What v1 fixes once it is stamped, and where each can grow inside it** (every such format had one look before the freeze: this repo's issue #39):

| Fixed | Grows by |
|---|---|
| The signed statements, byte for byte: the identity document (§2), the prekey statement (§2a), the pass (§6.1b), the revocation (§6.3), the revocation of certificates (§6.3a); a certificate's type, key id, principal and validity (§2b) | a new format under a new tag; a new identity or prekey key type (above); a certificate's extension, which a reader ignores (§2b) |
| The namespaces, `irongall-<purpose>-v1:<address>` | a new purpose |
| A signature's form, and its bound for each key type (§3) | a new key type, with a bound of its own |
| What is encrypted: the envelope's line, the signature block, the padding (§4.4) | the envelope's optional members (§4.2); its `v` changes only for a breaking change |
| JSON as §0b reads it; a byte member's one encoding; a message's ciphertext as the body itself (§4.5) | nothing |
| The routes, methods and statuses, the codes (§13), and every member a request or an answer has | a route; an optional member; a code, which a client that lacks it reads by its status |
| The pass's scheme and its three parameters (§6.1b) | a new scheme |
| An error's `type`, `tag:irongall.dev,2026-10-17:errors/<code>` (§13); the link, `https://<server>/to/<address>` (§2) | a new code |

## 0b. JSON — one way to read it

**Every JSON text the protocol carries is read by one set of rules, by the server, a revocation server and both clients:** a request's body, a server's answer, the envelope (§4.2) with the sender's body in it, a revocation record (§6.3), and the record a box keeps (`revoked-certs.json`). A text that breaks one is refused whole: a request with `400 bad_request` (`bad_encoding` for a byte field), an answer as no answer, an envelope as `bad_envelope`. So no two readers take different values from one text: RFC 7493 §3 has a security protocol's receiver "not trust" a text that breaks its rules.
- **It is I-JSON (RFC 7493):** UTF-8, so no code point above U+10FFFF; no member named twice in any object, after its escapes are read; and no surrogate or Unicode noncharacter in a name or a string, written or escaped.
- **It is one object, and nothing follows it but whitespace,** which in JSON is space, tab, LF and CR (RFC 8259 §2). **No byte-order mark** (RFC 8259 §8.1 lets a parser refuse one).
- **Names match exactly, case and all** (RFC 8259 §8.3): `"Identity"` is not `identity`, and a member a reader does not know.
- **Every number is in JSON's own grammar** (RFC 8259 §6): no `NaN`, `Infinity`, leading zero, `+` or bare `.`.
- **It nests at most 32 deep,** objects and arrays counted together, the outermost as one. RFC 8259 §9 lets a parser set that limit. 32 is well under every parser's own (jq 1.7 refuses 257, and Go's 10,001; both measured), so no reader's parser refuses what another takes.
- **A member the protocol defines is of its type, and null is the same as leaving it out,** as the protobuf JSON mapping reads null. The one exception is the envelope's `body`, which is required and whose null is a value (§4.2). **An integer member** (the envelope's `v`, a serial, a count, a size, seconds) is written as an integer, in digits alone, from 0 to 2^53 − 1, as typed JSON decoders read one (`PRECEDENTS.md`), so `1.0` and `1e0` are no integer: RFC 7493 §2.2 has no reader hold a larger one exactly, and jq and JavaScript do not. So a serial is at most 2^53 − 1 wherever it is written (§2a, §2b, §6.3a).
- **A byte member is standard base64 in its one encoding** (RFC 4648 §3): padded, with nothing outside the alphabet, a line break included, and the unused bits of its last character zero. Encoding the bytes again gives the text back, so a field has one text.
- **A member the reader does not know:** a server refuses one in what it is sent, and every other reader ignores one (§0a), RFC 7493 §4.2's "must-ignore" policy. The rules above still hold in it.

**How each reader holds to it.** The Go code reads every text through `protocol.Unmarshal`. That is Go's `encoding/json/v2` (Go ≥ 1.27), whose defaults refuse invalid UTF-8, a name twice, a byte-order mark and a second value, with the rest checked beside it. The stock script reads every text through `ig_json`, `ig_shape` and `ig_bytes`, which add what jq does not check: jq skips a byte-order mark, takes `NaN` and `01`, keeps the last of a name given twice, ends a number at a NUL and drops it, and reads an escaped lone low surrogate as U+FFFD. **Where the two still differ, the Go client is the reference,** and the script's tests name the difference: jq gives back as digits a number whose exponent cancels (`1e0` as 1, `0.5e1` as 5), so the script takes one in an integer member, `v` among them, where the Go client refuses it. A fraction jq gives back as written (`1.0`), and the script refuses it. The vectors are `testdata/vectors/json/` (a text by itself) and `answer/` (a whole answer of each kind), and both clients give each the verdict its name gives.

## Terms

- **Address / `H`:** the box identity — the SHA-256 of its identity document (§2). As text, 64 lowercase hex characters; inside MACs, the 32 raw bytes. `H_A` is the sender, `H_B` the recipient. **One identity key ⇔ exactly one address.**
- **Box:** a mailbox. In this file it never means a machine.
- **Identity document `D`:** the two-line text whose SHA-256 is the address (§2). Immutable. The API member carrying it is named `identity`.
- **Identity key:** the box's signing key, an Ed25519 key unless the box was made on another key type (§2), and its final authority. It signs certificates for the box's working keys and the box's revocations, of its address (§6.3) and of its certificates (§6.3a), and nothing else, so it need not be where the agent runs. **Working key:** an Ed25519 key the identity certifies, for at most 66 days (§2b). It signs everything the box says: its prekey statements, its mail and its passes. **Prekey:** the box's current age encryption key, published as a **prekey statement** signed by the working key (§2a). It is renewed at least every 33 days (the Go client renews it daily), with a new key each time; the address never changes.
- **Pass:** a short statement a box signs for itself to prove to the server who is calling: its address, the server's name, and a time ten minutes on (§6.1b). It replaces a bearer token: the server issues nothing and stores nothing for it.
- **"In system":** registered and active. Only those boxes can send.
- **Box states:** `active` → `deleted` (by its owner: answered as if never registered, and undone by a registration while the server keeps it) or `revoked` (permanent). A box nothing valid is left for is forgotten. The transitions are §3a's table.
- **A renewal** is a new PREKEY, published under a new working key and certificate (`irongall prekey renew`, `PUT …/prekey`, §6.4).
- **Last-use time of a prekey** = its renewal. Every send names the serial it used, and an honest server answers one naming a retired serial with `409 stale_prekey` (§4 step 7), so mail encrypted to a prekey reaches the server only while it is current. Senders also refuse an expired prekey.
- **Deletion time of a retired prekey:** the Go client keeps the newest retired prekey and deletes the older ones after a drain that empties the box and began more than an hour after the newest retired one was made, by which time all of them had been retired for an hour (the hour covers a send in progress as a renewal lands); `irongall.sh`, and the Go client as a backstop, delete at `not_after` + the 33-day TTL, when all mail encrypted to it has expired. Each deletes by its clock only once a server has taken a pass dated by that clock, and by the clock as it read then, when the server answered the drain's list, never by a later reading (§0): a box whose clock reads far ahead is stopped at its pass, one whose clock moves on during the drain deletes nothing by where it moved to, and neither deletes a key that mail may wait for. **Mail encrypted to it is unrecoverable from the box's keys after that** — THE forward-secrecy bound, stated once (§6.4). The Go client's early deletion rests on the server refusing a send to a retired serial: mail a server takes for one anyway may be mail the box can no longer read.
- **The live prekey** is the current one: the server checks a message's stanza TYPE against its type (§4 step 7). The server keeps the newest retired prekeys' key hashes (how many is a server setting) only to refuse a key that comes back.

## 1. Keys and the stock client — client side

**Every box lives in its own state directory, `${XDG_CONFIG_HOME:-~/.config}/irongall/<box>` (0700), never the working directory** — for a coding agent the working directory is a git repository, and `git add -A` would commit the keys. `IRONGALL_BOX` names the box; `IRONGALL_HOME` sets the directory outright, for sandboxes that may write only their workspace. The directory carries a `.gitignore` of `*`, so it ignores itself anywhere. The layout is shared with the Go client (the top of `client/doc.go`):

| File | Holds |
|---|---|
| `identity`, `identity.pub` | the identity key, OpenSSH format: Ed25519, unless the box was made on another key type (§2). **Backed up**; losing it loses the address (§6.3). It signs certificates and revocations only |
| `identity.doc`, `address` | the identity document (§2) and its hash |
| `work/<serial>`, `.pub`, `-cert.pub` | the working key made with prekey `<serial>` and its certificate, in the names `ssh-keygen` gives them, so `ssh-keygen -Y sign -f work/<serial>-cert.pub` signs with it. The one in use is the one made with the prekey published last; older ones are deleted when a newer prekey is published (§2b). Never backed up: a restored box makes new ones (§6.4) |
| `prekeys/<serial>.agekey`, `.txt`, `.txt.sig`, `.made` | each prekey, its signed statement, and when it was signed: `.made` is a timestamp alone on its line, which a client times its renewals and deletions by, never the statement's `not_after` (§6.4). 🛑 **Prekeys are NEVER backed up, NEVER synced, never stored where old versions survive (a secrets manager, git, snapshots), and never derived from a seed:** a prekey that survives its deletion voids forward secrecy. Losing a machine loses its prekeys — publish a new one with the identity alone (§6.4) |
| `prekey-lifetime` | how long each new prekey is valid for: a number of seconds alone on its line, from 93600 (a day and two hours) to 2851200 (33 days), the default (§6.4). Its owner's to write, or `irongall prekey lifetime`'s; one that names anything else is never read as the default, and no prekey is signed until it is put right |

| `peers/<address>/` | per correspondent: the PINNED identity document, the highest prekey serial and certificate serial seen, the last statement fetched, `revoke.sig`, its revocation, once one has verified (§6.3): that file is never removed; and `revoked-certs.json`, the highest revocation of its certificates that has verified (§6.3a). It exists only for a peer that has signed something this box verified |

One file, written whole, so a statement is never kept without its signature; and it is the record a revocation server takes (§6.3) |
| `seen` | the replay set, each line 66 days and an hour from its `sent_at` (§5 check 9) |
| `seen-floor` | the highest cutoff a prune of `seen` dropped a line at, in seconds: mail sent before it is `stale` (§5 check 9) |
| `outbox/`, `inbox/`, `quarantine/` | envelopes awaiting a receipt, as written, each dated and sealed at its post and never kept sealed (`outbox/failed/`: ones that can never be delivered) · accepted mail · refused mail, named by the ciphertext's SHA-256 as computed locally (§4.5, §5). A refused message is kept whole, as served (its list entry and its ciphertext), but each of the server's strings is in the clear only when it has its form (an id or address 64 lowercase hex, a time `YYYY-MM-DDTHH:MM:SSZ` that is one), and is otherwise `<name>_b64`, the string as served in base64: nothing the server chose is readable at a glance, and nothing is lost. Beside it, in `judged`, the Go client keeps what its checks established (§5, "The verdict") |
| `held/` | mail that passed every check from a sender this box has not allowed, kept as `inbox/` keeps it, until the owner allows or blocks that sender (§5.6). The Go client's: the script lands every sender's mail in `inbox/` |
| `sent/` | each message the server took, with its receipt (§4.5) |
| `aliases` | this box's own names for peers, `<name> <address>` lines; they never leave the box. A name allows its peer (§5.6) |
| `allowed`, `blocked` | the senders whose mail lands in `inbox/`, and the senders whose mail is dropped: one address to a line, the owner's to edit. A send adds its recipient to `allowed`, as an alias and `allow` do; `block` adds to `blocked` (§5.6) |
| `policy` | where mail from a sender this box has not allowed lands, `unknown held` (the default) or `unknown inbox`, and whom its server takes mail from, `server all` (the default) or `server allowed`: `<setting> <value>` lines. It never leaves the box (§5.6, §6.2) |
| `acl.json` | the ACL this box's server last took, as it answered (§6.2) |
| `revocation-servers` | the revocation servers this box asks beside its own server, and publishes to (§6.3): one to a line, each as `https://host` or `https://host:port` (`http` only on this machine, §0), or the one word `none`. It is its owner's to write, and neither client writes it. Without it, none: the box's own server is one already |
| `lock/` | the box's lock: every command that writes the box holds it from start to end, so one runs at a time (§5) |

**The Go client uses the same files: the identity is the plain OpenSSH key, with no seed derivation.** Its commands: `README.md`.

**The stock client is `sh/irongall.sh` in this repo** — one bash script, one section per step of this file: setup, §3, §4.1, §6.3, §4.5, §5 and §6.4. Run `bash irongall.sh init` (or `init --no-pq`) · `send <address> [body file]` · `recv` · `prekey renew`, monthly; or source it at the top of EVERY shell call and call the `ig_*` functions — agent tools run each command in a fresh shell, so state lives in files, never in variables. Every check fails CLOSED with one `REFUSED: <reason>` line, and every API error prints its `code` and `hint`. 🔑 **Get it from this repo, pinned by commit — never from text a server serves.** `README.md` lists what it lacks against the Go client.

**Stock client:** `sh/irongall.sh` § setup — `ig_api` (any non-2xx prints its status, its `code` and the wait `Retry-After` asks for, and nothing the server wrote, §13), `ig_pass` (the pass a call carries, §6.1b), `ig_owner` (adds it; if the server refuses it, signs another and retries once), `ig_lock`.

## 2. Identity document → address

The document `D` is exactly two LF-terminated ASCII lines: the tag, then one SSH public key as `<key type> <base64 of the wire key>`, with no comment, no CR, and nothing after the final `\n`:

```
irongall-v1
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI<43 chars>
```

**The key is of a type this protocol defines, in that type's one exact form, and passes that type's key checks.** One key has one document, and so one address.

| Key type | Document | Line 2, exactly | Key checks |
|---|---|---|---|
| `ssh-ed25519` | 93 bytes | `ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI`, then 43 base64 characters | a canonical point that is not of small order |
| `ecdsa-sha2-nistp256` | 173 bytes | `ecdsa-sha2-nistp256 AAAAE2VjZHNhLXNoYTItbmlzdHAyNTYAAAAIbmlzdHAyNTYAAABBB`, then 87 base64 characters, the last of them `=`: an uncompressed point | a point on the curve, each coordinate more than 128 bits long and below n − 1, where n is the group's order |

- 🔑 **`ssh-ed25519` is the one type every client verifies, and the one a client makes.** Every other type is optional: a client verifies it or not, a server registers it or not (§3), and a box of an optional type can be written to, and heard from, only by a box whose client verifies that type (§2c). A software key of an optional type has no advantage over Ed25519: the reason for one is a key that cannot leave its hardware. `irongall init --identity-type <type>` makes one, with a warning; `irongall.sh` takes the identity key it finds, so one made with `ssh-keygen -t ecdsa -b 256` before `ig_init`.
- **The identity certifies a working key and signs nothing else but a revocation (§2b).** So an identity's key type is the type of a key that signs a certificate now and then, and never a message: everything else a box signs is its working key's, which is Ed25519.
- **Why each type's key checks are explicit.** Go's `crypto/ed25519` takes small-order and non-canonical Ed25519 keys, as OpenSSH's own code did before 10.6p1 (from 10.4p1 it refuses the neutral point alone, `7763a38b`), so a client checks for them itself (§3 step 4). For P-256 it is the other way round: OpenSSH to 10.2p1 refuses a point on the curve with a coordinate of 128 bits or fewer, or of n − 1 or more (`sshkey_ec_validate_public`), and the Go library takes it. No key made from a private key is such a point, and the Go client and the server refuse it by explicit code. OpenSSH from 10.3p1 takes it too ("not needed", openssh-portable `9bea0818`), so a script on it takes one: a known variance (§3).
- **The form holds for every key type, defined here or not:** the tag line; a key type's name (RFC 4251 §6: printable ASCII with no comma, at most 64 characters); one space; the base64, in its one encoding, of an SSH wire key, which begins with that same name; LF. So a client can tell a document of a type it does not verify from something that is no document. **The first has a refusal of its own, `unsupported_key_type` (§5), and is never called malformed:** a document that does not hash to its address, or that breaks its form, points at tampering, and one of a type this client lacks does not. It is also how a type is added to v1 with no new tag (§0a).

- **Address = lowercase hex SHA-256 of `D`, 64 chars**: `sha256sum < identity.doc | cut -c1-64` (`ig_init`, §3). **It is shared as the link `https://irongall.dev/to/<64 hex>`**: the server serves a page there for exactly 64 lowercase hex characters, 404 otherwise, for people and for agents without a client: fixed text plus the hex, never text a box supplied, sent with `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex`. `irongall init` and `addr` (`ig_init`, `ig_addr`) print the box's link; `irongall send` (`ig_send`, via `ig_dest`) takes a link or a bare address, takes the hex from the path without fetching the page, and refuses a link to any server but its own. It is not `/v1/<addr>`, which is the API's read of the box (§4.1), and it carries no version.
- There is no checksum: a mangled address simply hits no box (`no_such_mailbox`).
- The version is line 1 of `D`. Another deployment of this protocol picks its own tag, and so its own address space.
- **It commits to the identity ONLY**, so renewing or re-typing the encryption key never changes it (§6.4).
- **The canonical form is lowercase hex.** Clients MUST use lowercase in `from`: the recipient compares the inner `from` (§4.2) with the verified signer as exact strings, and every SSHSIG namespace is an exact signed string. An address in a URL path is lowercase too: the server answers one in capitals `400 bad_address`, so that one box has one URL.

🔑 **An address is a SEND CAPABILITY — keeping it private is the real DoS defence.** Mailing a box hands it your address (it is your `from`), so it can mail you back.

## 2a. Prekey statement — the encryption key, signed by the working key

Exactly five LF-terminated lines, then signed by the box's working key, under its certificate (§2b), with namespace `irongall-prekey-v1:<A>`:

```
irongall-prekey-v1
<A — the box's own address>
<serial — a decimal integer, no leading zero, from 1 to 2^53 − 1 (9007199254740991, the most a JSON number holds exactly: an answer names one as a number, §13, §0b); strictly increasing under one certificate (a box's statements are ordered by certificate first: §2b); a client gives each the serial of the certificate it makes with it>
<age1pq1… (post-quantum, default) | age1… (X25519 only, `--no-pq`)>
<not_after — RFC 3339 UTC to the second, YYYY-MM-DDTHH:MM:SSZ>
```

- 🔑 **Every statement expires, and every renewal is a NEW key. A client signs one to end 33 days after it is made, or sooner, down to a day and two hours, when its owner sets a shorter lifetime (§6.4); a server takes one that ends at most 33 days and an hour from the server's own now.** The hour is the room of §0: without it, a client whose clock is a second ahead of the server's asks for more than the ceiling. 33 = the longest month, plus the day a renewal may wait (the Go client renews a prekey more than a day old), plus a day of slip, so a box received at least monthly never lapses (§6.4). `never` is not a valid `not_after`. This is TUF's mandatory expiry: it bounds how long a malicious operator can freeze a sender on an old statement.
- The key type IS the box's type: post-quantum by default, `--no-pq` (X25519 only) by choice. It can switch at any renewal (§6.4).
- **The key's type is its Bech32 human-readable part** (BIP 173, as age writes a recipient: lowercase, its checksum good, its data whole bytes): `age1pq` or `age`. A type defined later is an addition inside v1 (§0a). A sender holds a statement to every other rule first, and refuses one good in every way whose key is a well-formed age recipient of a type it lacks, a human-readable part that begins `age` and is neither of those, as `unsupported_prekey_type`: nothing is sealed or posted, and it is never refused as a statement that does not verify (`protocol.ErrPrekeyType`, `ig_prekeycheck`; `prekey/unsupported-type`).
- **Senders keep the highest `serial` they have seen**, and refuse a lower one. That is the rollback guard. They keep the highest certificate serial they have seen on a box's statements too, and refuse a lower (§2b).
- **A statement never outlives the certificate it is signed under:** its `not_after` is at most the certificate's end, and a verifier refuses one that is later.
- **Senders re-fetch at `not_after`**, or when a send gets `409 stale_prekey` (§4).
- **A prekey past its `not_after`: senders MUST refuse to encrypt**, and the server refuses the send with `409 prekey_expired` ("the box must publish a new prekey"). **No grace**: a grace only widens the time an expired, possibly deleted or leaked, prekey is used. The room for a clock that is off is at the other end, in what a server takes when the statement is published (§0). Nothing else about the box changes (§6.4).

## 2b. The working key and its certificate

🔑 **The identity signs certificates and revocations (§6.3, §6.3a), and nothing else. Every other signature a box makes is its working key's** (this repo's issue #30). So the identity key need not be where the agent runs: by default a client keeps both keys in the box and renews the certificate itself, and a box whose identity is kept elsewhere is handed a certificate.

A certificate is an OpenSSH user certificate, exactly as `ssh-keygen` writes it:

```sh
ssh-keygen -s identity -I irongall-cert-v1 -n "$A" -z "$SERIAL" -V -1h:+65d -O clear work.pub
```

| Field | Rule |
|---|---|
| Type | a user certificate |
| Certified key | the working key: `ssh-ed25519`, held to that type's key checks (§2), and never the identity key |
| Serial | from 1 to 2^53 − 1, as a prekey's. The identity gives each certificate a higher one than the last, and a client takes it from its clock to do so; who holds a certificate to that order is below |
| Key id | exactly `irongall-cert-v1` |
| Principals | exactly one: the box's address, lowercase |
| Validity | `valid after` ≤ now < `valid before` ≤ now + 66 days, in whole seconds |
| Critical options | none. One a verifier does not know is refused (draft-ietf-sshm-cert-01 §2.1.1), and none is known here |
| Extensions | ignored, each, as one a verifier does not know is (draft-ietf-sshm-cert-01 §2.1.1, §2.3): none is known here. They are read in one encoding: each name once, in lexical order (§2.2), and its value empty or one string that is not empty, the forms every extension OpenSSH defines takes (a deviation: `PRECEDENTS.md`, Part 2, § 4). A client writes none (`-O clear`; without it `ssh-keygen` adds five). A vector carries one nobody defines, so the slot stays in use (RFC 9170) |
| Reserved | ignored, whatever it holds (§2.1.1). A client writes it empty, and a vector fills it |
| Signed by | the identity: the key in the identity document (§2), byte for byte |

- **A signature made with `-f work-cert.pub` carries the certificate,** so no message format gains a field. A verifier takes the certificate from the signature, checks it against the identity it holds for that address, and verifies the signature under it (`protocol.VerifyCertified`, `ig_certified`). A signature by the bare working key, or by the identity itself, is refused.
- **It is checked against the verifier's own clock** (§0), and only once the identity's signature on it has verified: "it has not begun" is a verdict on a certificate the identity signed, never on bytes anyone could write. Nobody can vouch for when a signature was made, so a certificate must be valid when it is checked, and so must outlast what it signed: it runs at most 66 days, twice the 33 days mail may wait, and a client does not sign mail with 33 days or less left.
- **A client dates a certificate from an hour before it is made** (`-V -1h:+65d`). A verifier refuses one that has not begun by its own clock, so one dated from the moment it is made is refused by every verifier whose clock is behind its maker's: mail under it is refused by such a reader, and a registration by such a server. `ssh-keygen`'s own default, a minute or two back, covers machines that share a clock. The hour is §0's: no two clocks a server takes are further apart when each shows a pass, and a server takes a certificate only once it has begun for every box it takes, 10 minutes back.
- **A client asks for 65 days, and a verifier takes up to 66.** Asked for at the ceiling, a certificate would be refused by a verifier whose clock is behind its maker's. It is the pass's rule (§6.1b), 10 minutes asked and an hour taken, with a day where §0's hour would do.
- **A client makes every check in the table itself.** Given an `allowed_signers` line `<address> cert-authority <the identity's key>`, `ssh-keygen -Y verify` checks the identity's signature on a certificate, that the address is among its principals, and that it is valid at the time it is told to verify at. It takes a certificate with a second principal, with a critical option, or with extensions out of their order or given twice, checks no key id, and knows a serial only through a revocation list. So `irongall.sh` reads the other fields from the certificate's bytes, in order (`ig_cert`), and a test holds that `ssh-keygen` alone takes what it refuses.
- **Every certificate is for a new working key.** A certificate is public, since it rides in every signature, so a new one for the same key would retire nothing.
- **Where they are kept, and when they are made.** Both clients here make a new working key, with a new certificate, each time they make a new prekey, and name them by that prekey's serial: `work/<serial>`, with the certificate's serial the same number (§1). The Go client renews daily, so its certificates are a day old at most. The one in use is the one made with the prekey published last, and older ones are deleted then.
- 🔑 **A certificate's serial is the time it is made** (this repo's issue #63; `protocol.SerialAt`, `ig_init`, `ig_renew`). A client numbers a certificate by its own clock, in seconds since 1970, or one above the highest serial it knows of for the box when the clock gives nothing higher: the served certificate's, what the box has published or signed itself, and the highest its identity has revoked (§6.3a), which every renewal asks for, of its own server in the read of the box it makes first and of each revocation server it lists, so a box never makes a certificate that is revoked as it is made, a box restored from its identity alone among them. A box's first certificate is numbered so too.
  - **Why the clock.** An identity is a key, and a key keeps no record of what it signed. A box restored from its identity alone (§6.4) knows only what a server shows it, which may be an older record, and no server has seen a certificate that was made and never published. Counted from what it is shown, such a box gives its next certificate a serial another machine has used, and no revocation (§6.3a) can reach that machine's certificate and spare the box's own. By the clock, the certificate made later has the higher serial whichever machine made the earlier one, so the serials below a new certificate are those of every certificate made before it, known to its maker or not.
  - **A verifier never reads a serial as a time.** It compares two of them, and the higher is later: a server, a sender and a revocation of certificates are held to nothing new, and a box whose certificates were numbered from 1 goes on from its clock. A clock that reads behind the last serial still gives one that rises, by one.
  - **Why a serial rises by one where the clock gives nothing higher, and the client does not refuse instead.** Two renewals in one second are no failure. And the last certificate may have been made by a clock that read fast, by less than a server refuses, on a machine that is now lost: its owner's renewal, and the revocation that ends the taken key (§6.3a), then come at once, and do not wait for a right clock to pass that number.
  - **What it rests on is the clock of whoever holds the identity.** A certificate made while that clock read ahead has a serial above its time, and those after it are one above each other until the clock passes it. A box restored while its clock reads behind the lost machine's, at a server that shows it an older record, can still be numbered below what that machine made. Two certificates of one identity share a serial only when two machines make one in the same second. A holder that meets two takes either and pins nothing beyond the serial (decided on #63): a certificate the identity signed may be used until it ends or is revoked, and telling the box's owner of one in other hands is #74.
  - **A number once taken is kept** until its statement is published or can no longer be sent (§6.4, "A serial is signed once"): a renewal that waits is sent again under the number it was signed with.
  - **Who else takes a number from the clock,** and how a certificate authority that keeps records does without: `PRECEDENTS.md`, Part 2, § 2a.
- **Other key types** for the working key are not ruled out by the format, which certifies any SSH key type; `ssh-ed25519` is what is built. The optional key types of §2 are the identity's.
- **A certificate that an ECDSA identity signed has more than one set of bytes.** An ECDSA signature (r, s) verifies as (r, n − s) too, and with either number written with leading zero bytes up to the 2,049 bytes OpenSSH reads (§3), and anyone who has seen a certificate can write those other encodings of it. Nothing rests on a certificate having one set of bytes: a server takes a pass under exactly the bytes it has on record, and a recipient takes mail under any certificate its sender's identity signed.
- **A box moves to a new certificate by publishing a prekey under it** (§6.4): a new working key needs a prekey statement that it signed, and a prekey statement never outlives the certificate it is signed under.
- **What a newer certificate retires.** At the server, everything: it keeps the highest serial it has seen for a box and refuses anything under a lower one. For a sender fetching a box's prekey, the older ones: it keeps the highest serial it has seen on that box's prekey statements and refuses a lower. For a recipient reading mail, nothing: mail is signed once and read up to 33 days later, so it is taken under any certificate of the sender's identity that is valid when it is read. A stolen working key can therefore sign mail that verifies until its certificate ends, if a server delivers it. The identity can revoke that certificate and keep its address (§6.3a); revoking the identity ends everything it certified (§6.3).
- **A box's prekey statements are ordered by their certificate's serial first, and by their own serial second.** A statement replaces the one before it if it is under a later certificate, at any prekey serial, or under the same certificate at a higher one: at the server (§6.4) and in what a sender has seen (§4.1). So a prekey published at the highest serial there is, by whoever took a working key, holds nothing: the box's next certificate passes it. A certificate serial at the top takes a signature by the identity, which can already end the address by revoking it (§6.3), so no serial has a bound on how far it may rise. Nor does a verifier bound one by its clock: that was weighed and declined (#73), since a client numbers a certificate ahead of its dates for good reasons (a number kept from an attempt at a fast clock, one above a revocation of its certificates, one above a lost machine's fast number), and a bound would leave such a box unable to renew until its clock passed the number. No system in `PRECEDENTS.md` § 2a that numbers from a clock bounds the number at a verifier. A prekey serial can therefore come again under a later certificate, and a send names its prekey by both serials (§4.5). It is how DTLS orders its records: an epoch, and a sequence number kept separately for each epoch (RFC 9147 §4.2).
- **What proves a box to the server** is a pass the working key signs (§6.1b).
- **Who else does this** (OpenSSH certificates, OpenPGP subkeys, Matrix cross-signing): `PRECEDENTS.md`, Part 2, § 2.

## 2c. The sender key types a box declares

A sender learns from one fetch whether it can verify the recipient: the recipient's identity is of a key type its client verifies, or it is not (§4.1). Nothing in that tells it whether the recipient can verify the SENDER. Without more, a box of an optional key type could write to a box whose client lacks the type: the server would take the message, the recipient's client would refuse it, and the sender would hold a receipt.

- **With each prekey it publishes, a box declares the identity key types its client verifies:** the optional member `sender_key_types`, a list of key type names, in a registration (§3) and in every prekey upload (§6.4). The read of a box, `GET /v1/<A>`, returns it (§4.1).
- **`ssh-ed25519` is taken by every box, whatever it declared.** A box that declared nothing takes `ssh-ed25519` senders only.
- **A sender whose own key type is not on the list does not send** (§4.1), and the server refuses that send, `403 sender_key_type` (§4.5 step 7): the sender has an error, and never a receipt for mail that would not be read.
- **The one entry `any` is no key type.** It says that the box will not say which types its client verifies. The server then makes no check for that box, senders send, and the box's client refuses what it cannot verify. A client declares it only when told to. It lets through no key type the server does not register, since a box of such a type is not registered to send (§3).
- **The declaration is the current prekey's.** A prekey upload replaces it, with nothing if it brings none; an identical retry changes nothing. So a declaration follows the client a box runs. Both clients here declare every type they verify, with every prekey (the Go client declares what `IRONGALL_SENDER_KEY_TYPES` lists, if that is set).
- **It is not signed, and need not be.** A server that misstates a box's declaration can stop a message, or let one through that the recipient then refuses. It can do the first by dropping the message, and the second delivers nothing. What a recipient takes is settled by what its client verifies (§5), never by this list.
- **A server keeps the names it knows and ignores the rest,** so a client may verify more key types than a server registers.

## 3. Registration — a signed prekey, and a pass

**Stock client:** `sh/irongall.sh` § keys and registration — `ig_init` (creates the box or finishes a half-done init, and registers it), `ig_work` (a NEW working key and its certificate), `ig_prekey` (a NEW key, valid for 33 days, signed by that working key).

**One API call, no human:** `PUT /v1/<A>` with JSON `{identity, prekey, prekey_signature}` (standard base64 of the exact file bytes, §0b), and `sender_key_types` if the box declares any (§2c), carrying a pass (§6.1b) that the new working key signs. The box is in use at once.

**Signatures are made from stdin to stdout** (`ssh-keygen -Y sign … < f > f.sig`). Given a file name, `ssh-keygen` will not overwrite an existing `.sig`: with stdin at EOF it keeps the STALE signature and exits 0, and in Claude Code's Bash tool it blocks on "Overwrite (y/n)?".

**SSHSIG, in bytes.**
- Signed data = `"SSHSIG"` ‖ `str(namespace)` ‖ `str("")` ‖ `str("sha512")` ‖ `str(SHA-512(message))`, where `str` = uint32 length + bytes.
- Signature = Ed25519(working key, signed data).
- The `.sig` file is a PEM-armored (`SSH SIGNATURE`) blob: `"SSHSIG"` ‖ `u32(1)` ‖ `str(the signing key: here, the certificate)` ‖ `str(namespace)` ‖ `str("")` ‖ `str("sha512")` ‖ `str(str("ssh-ed25519") ‖ str(sig64))`. 846 bytes armored for a message and 850 for a prekey statement (measured), of which the certificate is the larger part; the identity's own signature, on a revocation, is 403. Under a certificate that a P-256 identity signed, a prekey statement's is 943 or 947: the two numbers of an ECDSA signature vary in length.
- **Every verifier reads a signature as OpenSSH reads it** (`sshsig.c`, and the key and signature code beneath it), the reference implementation of the format, **with two checks more** (`protocol.Dearmor`, `sshsig.Verify`; `ig_blob`, `ig_sshsig` in the script). Where every OpenSSH build reads a form one way, that is the rule. **Where OpenSSH's builds disagree, the rule is the Go client's,** which is also OpenSSH's linked to an OpenSSL that has Ed25519, but for one case (below). The `sig/` vectors hold one signature in each form.
  - **The armour:** the BEGIN line first, ending in LF or CRLF; then the base64, in which space, tab, LF, VT, FF and CR are skipped wherever they stand, and which is otherwise in its one encoding: padded, and the unused bits of its last character zero. Then LF and the END line. Nothing after the END line is read. One NUL may be the last byte before that LF (`sshbuf_dup_string`); any other byte in the base64, any other NUL among them, is refused.
  - **The blob:** its version is 0 or 1 (`sshsig_parse_preamble` refuses only a higher one, and nothing signs the version). A string OpenSSH reads with `sshbuf_get_cstring` where no signature covers it may end in one NUL, which is not part of it: the namespace, the hash name, each signature's type, and a bare key's type and curve. A NUL before its last byte is refused. OpenSSH builds the data a signature covers from those strings without it, so a signature verifies with the NUL or without. What an identity signed in a certificate is read byte for byte (§2b). An ECDSA signature's r and s are each at most 2,049 bytes (`sshbuf_get_bignum2`).
  - **`reserved`:** what the key signed has an empty one, and the blob's field is read and skipped, whatever it holds (`PROTOCOL.sshsig`: "Implementations should ignore the reserved field if it is not empty"). So a signature made over a field that is not empty does not verify.
  - **The first check more: a bound on its size, stated for each identity key type** (`protocol.SignatureBound`, `ig_sigmax`): 4,096 bytes for `ssh-ed25519`, and 4,096 for `ecdsa-sha2-nistp256`. What a box signs, with its identity or with a working key under a certificate its identity signed, is held to its identity's bound. A field that carries a signature counts every byte it holds, what follows the END line too; in a message it is the block from its BEGIN line through its END line (§4.4). Every verifier refuses a longer one before verifying it, a server's included, and nobody cuts one down; one longer than the most any type allows (`protocol.MaxSignature`) is refused before it is read. Each bound is several times the largest its type makes. **A new key type states its own and leaves the others where they are:** were one to rise, a block padded past it would be refused by one reader and delivered by another.
  - **The second: an Ed25519 signature's S is below the group's order L** (RFC 8032 §5.1.7), in the SSHSIG and on a certificate. Go's `crypto/ed25519` refuses S + L, and so does OpenSSH from 10.3p1 on OpenSSL's Ed25519 (`266647c5`) and from 10.4p1 on its own (`7763a38b`). `ssh-keygen` before them takes it, so the script checks S itself.
  - **Where OpenSSH's builds disagree, each a known variance:** `go test ./sh` names the build it ran on, holds the script to the Go client's verdict, and on a build named here to this shape; any other fails.
    - **An Ed25519 signature's R.** The equation is RFC 8032 §5.1.7's without the cofactor, `[S]B = R + [k]A'`, compared as encodings, as Go's `crypto/ed25519` and OpenSSL check it: a neutral R is taken, and R with a point of small order added is refused. OpenSSH's own Ed25519 from 10.6p1, libsodium's (`eab91661`), used where libcrypto has none, judges both the other way. Only the key's holder can make either. The equation with the cofactor would take both, and no verifier here makes it.
    - **A P-256 key's coordinates (§2),** the one case where the Go client's verdict is not the OpenSSL build's: OpenSSH from 10.3p1 takes a coordinate the Go client refuses.
    - **A P-256 key at all:** OpenSSH built without OpenSSL reads none, so a script on it refuses every P-256 identity.
  - **A server keeps a signature as it was sent, and serves it so** (§4.5): the bound is what limits what it stores.

**Server:**
1. The URL-path address must be 64 lowercase hex chars → `H`. Otherwise, capitals included, `bad_address`.
2. The body is exactly `{identity, prekey, prekey_signature}`, with `sender_key_types` (a list of strings, §2c) or without → otherwise `bad_request`, naming the missing or unknown field (§0a).
3. `SHA-256(identity) == H`, and `identity` has the form of an identity document (§2). Otherwise `identity_mismatch`, with a hint naming the usual causes: a comment left on the SSH line, CRLF, a missing final newline.
4. **The key's type, then the key.** A key type this protocol does not define → `unsupported_key_type`. The document in that type's one exact form → otherwise `identity_mismatch`. The key checks of that type (§2) → otherwise `bad_key`: for `ssh-ed25519`, a 32-byte key that is canonical and not of small order, which is **explicit code** — `filippo.io/edwards25519`, a canonical-encoding check and a `MultByCofactor` check — because Go's `crypto/ed25519` and OpenSSH 10.2 both accept such keys; for `ecdsa-sha2-nistp256`, a point on the curve in its one encoding, and the two bounds on its coordinates, which are explicit code for the opposite reason. **Then the server's own list:** a server registers `ssh-ed25519` and whichever other defined types its operator chooses, and answers the rest `unsupported_key_type`, naming its list. Parse the prekey statement: the exact five-line grammar (§2a); line 2 == `H`; a valid `age1pq1…`/`age1…` recipient on line 4 (rejecting X25519 small-order points, including the X25519 half of a post-quantum key); `not_after` after now and at most 33 days and an hour after now (§2a, §0). Any failure → `bad_key`.
5. **What could change nothing is answered first, and the rest is counted first.** **Registration never changes a registered box**, so one the server holds already is answered from its record, before anything below is checked: active, and the request byte-identical to its CURRENT identity + prekey statement + signature → `200 {}` once its pass (step 7) is checked under the box's current certificate (an idempotent retry); anything else → `409 conflict`, with a hint that names `irongall prekey renew`, which replaces a registered box's prekey. A revoked address → `410 revoked`, box or none (§6.3). Every prekey change goes through §6.4. Any other registration counts against its IPv4 address or IPv6 /64 here (§8), before its signatures are checked. Proof of work is a lever a server may add here (§12); nothing in v1 carries it.
6. Verify the prekey SSHSIG: the blob's key is a certificate of that identity, in every rule of §2b's table; namespace `irongall-prekey-v1:<H>`, hash per §0; and the statement does not outlive the certificate → otherwise `bad_key`, or `prekey_time` when what fails is the certificate's time or the statement's `not_after` (§2a) at the server's clock, a certificate that began less than 10 minutes before it among them (§0). **Then what the server keeps of the address, box or none** (§6.3, §7): a certificate the identity revoked (§6.3a) → `401 certificate_revoked`; and while it keeps the record of a box its owner deleted (§6.2), a certificate of a serial no higher than that box's last → `401 certificate_not_current`, with that serial in `certificate_serial`.
7. **The pass** (§6.1b): this box's, for this server, not run out, and signed under the certificate of step 6 → otherwise a `401` (§6.1b says which). **The two together are the proof of possession:** the certificate shows the identity chose this working key, and a pass minutes old shows its holder is here now. Nobody can register an identity they do not hold, and a statement that leaked cannot be registered by whoever found it.
8. **A new box** is stored `active` → `201 {}`. **So is a deleted box the server still keeps, which the registration undoes:** held to its record as a renewal is (§6.4), with a key it never published (`400 prekey_not_new` otherwise), it comes back as it was, its ACL and its account with it, but for its mail, which the delete deleted. A box registered by another request meanwhile is answered as step 5 answers.
9. The server keeps which certificate the statement is signed under, and its serial: it takes a pass only under that certificate, and a later statement only under it or one of a higher serial (§2b, §6.4).

## 3a. Box states — normative

Every call names a box; this is what each event does in each state.

| State ↓ / event → | Register `PUT /v1/<a>` (with a pass) | New prekey `PUT …/prekey` (a later certificate, or the current one and a higher serial; with a pass under its certificate) | A call with the box's pass (`messages`, `account`, `acl`, `profile`) | Delete `DELETE /v1/<a>` (with the pass) | Revoke `PUT …/revocations` (the identity's own signature, no pass) |
|---|---|---|---|---|---|
| **unknown** (never registered, or forgotten) | → `active`: `201` | `404 no_such_mailbox` | `404` | `404` | kept, box or none: of the address → `revoked`, `201`; of certificates, `200`, and the address stays unknown |
| **active** | identical replay: `200`; otherwise `409 conflict` | stays `active`: `200` | served | → `deleted`; unacked mail deleted: `204` | of the address → `revoked`: `201`; mail deleted. Of certificates: `200` |
| **deleted** | → `active` (the delete undone; a later certificate than the box's last, and a new key): `201` | `404` | `404` | `404` | as for an active box |
| **revoked** | `410 revoked` | `410` | `410` | `410` | `410`, answered from the record with no check: nothing could change it |

- **Not built:** `profile` among the calls with a pass (§6.2).
- **A revocation that does not verify is `400 bad_revocation` in every state but `revoked`,** and changes nothing (§6.3).
- **There is no pending state.** A registration carries a pass minutes old, which shows a live holder of the working key, so a box is active from its first call.
- **Replays:** a byte-identical replay of a request that already took effect gets `200` and the same result; a conflicting one gets `409 conflict`. That covers registration, prekey uploads, profiles (a `version` not above the current one) and sends (§4 step 6).
- **The read of a box, `GET /v1/<a>`,** answers for an `active` box. A deleted box, and an address with no box, are `404 no_such_mailbox`, whatever its identity revoked of its certificates, which `GET …/revocations` serves (§6.3). A `revoked` address's read is `410 revoked` with its record (§6.3).
- **A box is forgotten once nothing valid for it is left** (§7): a deleted box once its newest certificate has ended, and a box that stopped renewing once its certificate has ended and its last prekey's mail has expired. It is then unknown, and registers anew (§3), its ACL and its account gone with the old one. What its identity revoked is kept.
- **No `last_seen`.** A box whose owner stops renewing refuses mail once its prekey expires (`prekey_expired`, §6.4), and a renewal turns it back on while the server keeps it. The current prekey statement dates the owner's last renewal, so the server tracks no activity of its own: what forgets a box is its record's expiry, which each renewal moves (§7).

## 4. Sending A → B

**4.1 Read B's box, and verify it** — one GET, `GET /v1/<B>`, the one read of a box: everything a sender needs before it posts. → `{identity, prekey, prekey_signature}`, all base64, with `sender_key_types` if B declared any (§2c), and `revoked_certificates` with `revoked_certificates_signature` when the server holds a revocation of B's certificates (§6.3a). A revoked address is `410 revoked`, with the record the server holds in the member `record` (§6.3). The answer is open, as every answer is (§0a): a later version may add a member, and a box's signed profile is the one named so far (§12). **The read carries the sender's pass** (§6.1b), as a drain's read of a sender does (§5). A lookup takes a pass or none; with one, the server counts it against the box that makes it, and with none, against the address it comes from (§8), so a box's lookups are its own whatever address it calls from. A lookup whose pass the server refuses is asked again without one: what was refused is the asker's pass, and the post that follows meets the same refusal and says what it means. What a box looks up about itself is asked with no pass, since its pass may be what is wrong. `ig_resolve` prints the serial and the age recipient ONLY when every check passes; until then nothing exists to encrypt to.

**Stock client:** `sh/irongall.sh` § verify a peer — `ig_look` (a lookup with the box's pass, §8), `ig_resolve` (prints a prekey only when every check passes), `ig_idcheck`, `ig_cert` and `ig_certified` (a signature under a certificate of that identity, §2b), `ig_prekeycheck`, `ig_meet` (pins a peer, once something it signed has verified).
- **Identity: the pinned one, or at first contact the served one, and a pin always wins.** The served identity is hash-checked against the address and held to its key type's exact two-line form and key checks (§2) — as the server holds it at registration, so one identity key can never have two addresses. One of a key type this client does not verify is refused in words that say so, and nothing is encrypted. It is pinned only once its prekey statement has verified, and later fetches never replace it. The `allowed_signers` file is ONE line, `<address> cert-authority <key>`, rebuilt from those hash-checked bytes for each verification, never built from server text: an `allowed_signers` principal is a pattern list, so a server-supplied address carrying a newline could otherwise plant a `*` signer that verifies the operator for every box.
- **The operator cannot swap the encryption key** (the signature fails), **pass off another box's validly-signed prekey** (wrong namespace, line 2 and certificate), **roll back a sender that has seen a newer one** (the persisted serials, compared by certificate first, §2b — recorded only after every check passes), **offer a prekey under a certificate older than one the sender has seen** (the persisted certificate serial: a stolen working key that was since replaced), or **keep a sender on one past `not_after`** (§2a). All are tested against a forging server (§11).
- **The read comes before anything is sealed or posted, at every post** (§6.3), of a new message or of one that waited in the outbox. What it carries of a revocation of B's address or of B's certificates is kept once it verifies, and the send is checked against what the box then holds: nothing is posted to an address it holds a revocation of, and a prekey statement under a revoked certificate is refused (§6.3a). What a server shows, or leaves out, is its word and is kept nowhere, so the next post reads again. **No answer is not "none held":** nothing is sealed or posted, and the message waits in the outbox. Neither does a read that serves no box (`404 no_such_mailbox`, or `410 revoked` with nothing that verifies) give anything to seal to. Whatever code a failed read carries is no answer about the message. The read tells the server that this address is about to be written to, which the post tells it a moment later. **Once the box's own server has answered, each revocation server the box lists is asked** (§6.3, "Revocation servers"): by the Go client once for each recipient in a command, by the script at every post. A record it shows is checked and kept as any is, and neither its "none held" nor its silence holds the message.
- **Caching:** the identity forever; the prekey until its `not_after` or a `409 stale_prekey`. Both clients read the box at every post, which brings what is held of its revocations too; the serial guards make that safe.
- **The read may come in gzip** (RFC 9110 §8.4.1.3), and only to a request whose `Accept-Encoding` takes it (§12.5.3): it is base64 in JSON, read before every post and for each sender in a drain. What a client checks is the JSON beneath, and a client that sends no `Accept-Encoding` gets none. A server compresses no other answer of the API: a list puts what senders chose beside the box's own values (BREACH, RFC 7457 §2.6), and a ciphertext does not compress.
- **A box this client holds a revocation of is refused before any call,** whatever a server serves for it afterwards (§6.3). **A `410 revoked`, in answer to the read or to the send, is checked and never believed:** the read's carries the record, a send's sends the client to read the box, and the client takes the box as revoked only if a revocation verifies.

**4.2 The ENVELOPE `P` — one line of compact JSON, ending in a line feed.** It is what the sender signs (§4.4), and the server never sees it.

| Field | | |
|---|---|---|
| `v` | required | `1` |
| `from`, `to` | required | the sender's and recipient's addresses. **The recipient rejects the message unless `from` is the address of the identity that signed it and `to` equals itself** (§5) |
| `sent_at` | required | RFC 3339 UTC to the second: the time of the post that carried it, dated afresh at every post, with nothing else in the envelope changed (§4.5); the replay window needs it (§5) |
| `msg_id` | required | a UUID as RFC 9562 §4 writes one (its 4, 2, 2, 2 and 6 octets in hex, with hyphens between), of any version, and lowercase only: one value has one text, as an address does. A client makes a random one (version 4) ONCE per logical message and keeps it on every re-encryption, so a retry is never acted on twice (§5) |
| `identity` | required | the sender's identity document (§2), as standard base64 in its one encoding. `from` is its hash, and the signature must verify under it, so a recipient checks a sender it has never met without asking the server anything |
| `body` | required | the message: any JSON value, carried as that value, and a string is text. Both clients send text, or with `--json` one JSON value: an object then arrives as that object, not as a string holding it |
| `subject` | optional | a string |
| `in_reply_to` | optional | the `msg_id` replied to — never the ciphertext id |
| `supersedes` | optional | a `msg_id` of the same sender that this message replaces. Stored mail is never altered; the recipient decides |

- **Both clients set `subject`, `in_reply_to` and `supersedes`**: `--subject`, `--reply-to` and `--supersedes` on `irongall send` and on `ig_send`. A sender refuses an `in_reply_to` or `supersedes` that is not a `msg_id` before it builds anything; what `send` prints is the server's 64-character id of the ciphertext, which is not one. A receiver checks only that each is a string: they are the verified sender's words, and a reply can name any `msg_id`. **An empty string in any of the three is read as the member left out,** as null is (§0b), and a writer leaves such a member out.
- **A sender holds the envelope it builds to the rules its reader holds it to (§0b, §5 check 3), and keeps and posts nothing that breaks one.** A JSON body is one value and nothing after it, with no name twice in any object, nested at most 31 deep (32 with the envelope), and no noncharacter; one that breaks a rule is refused whole, never repaired, and one that keeps them is sent compact, its members in the order given and its strings and numbers as written, but that U+2028 and U+2029 are escaped, as in every string the envelope carries. The same reading refuses a noncharacter in a text body or a subject before the outbox keeps it.
- **Encoding: compact UTF-8 JSON without HTML escaping** — `jq -c`, Go's `SetEscapeHTML(false)`, Python's `ensure_ascii=False` with compact separators. Default serializers that escape `<`, `>`, `&` or non-ASCII inflate the body. **Compact JSON holds no line feed of its own**, since JSON escapes one inside a string, so the envelope is exactly one line: that is what lets a reader take it apart from the signature after it (§4.4). Receivers accept any JSON text on that line that §0b takes, and ignore unknown fields (§0a).
- **What a client delivers and keeps** is the line built from the checked fields, without `identity`: `recv`'s output, `inbox/` and `sent/`.
- The server's size cap counts the ciphertext's bytes, which are the post's whole body (§4.5). age adds 1,659 B (PQ) or 200 B (`--no-pq`), and the signature 846 B.

**4.3 Encrypt to B's prekey — binary, not armored.** What is encrypted is the envelope's line, the signature over it (§4.4), and padding (§4.3a), one after the other: `{ cat P P.sig; padding; } | age -r <recipient> > m.age` (`ig_seal`, §4.5).
- **Post-quantum prekey (the default):** one `mlkem768x25519` stanza — age's hybrid ML-KEM-768 + X25519 recipient (age ≥ 1.3, which builds it on HPKE, per its `filippo.io/hpke` dependency). It adds 1,659 B (measured). The payload layer below is identical.
- **`--no-pq` prekey:** the X25519 stanza, below.

Inside age, for a `--no-pq` prekey:
- File key `K` = 16 random bytes.
- Ephemeral secret `e` = 32 random bytes; share `E = X25519(e, 9)`; `Z = X25519(e, B_x)` — abort if `Z` is all zeros.
- Wrap key = HKDF-SHA-256(ikm `Z`, salt `E ‖ B_x`, info `"age-encryption.org/v1/X25519"`). Stanza body = ChaCha20-Poly1305(wrap key, nonce 0¹², `K`), 32 bytes.
- Header = `age-encryption.org/v1\n-> X25519 b64(E)\nb64(body)\n---`. MAC = HMAC-SHA-256(HKDF(`K`, info `"header"`), header).
- Payload: nonce `n` = 16 random bytes; payload key = HKDF(`K`, salt `n`, info `"payload"`). A message of up to 64 KiB is one chunk = ChaCha20-Poly1305(payload key, nonce `0¹¹ ‖ 0x01`, `P`). The last-chunk flag stops truncation.
- No armor: the post carries the file's bytes as they are (§4.5), and armor would add a third. Overhead is 200 B `--no-pq`, 1,659 B post-quantum (measured).

**4.3a Padding — every message is a whole number of blocks** (`protocol/pad.go`, `protocol.Plaintext`, `ig_padding`). The server sees each ciphertext's size, and without padding reads a message's length to the byte.
- **The rule.** A block is the smallest power of two that is at least 1/16 of the ciphertext's size, and never under 1 KiB: 1 KiB up to 16 KiB, 2 KiB up to 32 KiB, and on. The sender adds padding, after the signature, that makes the CIPHERTEXT the next whole number of blocks. So a ciphertext takes one of 16 sizes up to 16 KiB and of 8 for each doubling after it.
- **The padding is bytes after the signature, to the end:** `.`, as many as it takes, and none for a message already on a block. A reader never looks past the signature's END line (§4.4), so nothing has to be said of what the padding holds.
- **It is outside what is signed,** where OpenPGP puts its own padding packet. So each encryption is padded for its own prekey without touching what is signed, and a message's size does not depend on its own signature's.
- **The ciphertext is measured, not the body,** because it is what the server sees and what its size cap counts. age's file size is a fixed function of the key type and the plaintext length: a header of 168 B (`--no-pq`) or 1,627 B (post-quantum), a 16-byte nonce, and a 16-byte tag after each 64 KiB chunk of plaintext (measured against age 1.3.2 up to 10 MiB, and the X25519 header against age 1.2.1; one chunk gives §4.3's 200 and 1,659). The sender computes the padding from that, encrypts, and refuses to send a file that is not the size it computed.
- **Made at the seal, never before.** The padding depends on the prekey's type, so an encryption after `409 stale_prekey` is padded again for the newer prekey: between the two types the age file differs by 1,459 B. The envelope and its `msg_id` stay.
- **The server does nothing, and a size limit must be a whole number of its own blocks.** As sizes go, any power of two is such a number and 100 KiB is not: a message just under a limit like that one would be padded past it. With limits chosen that way a client never needs to know the limit: a message fits it padded exactly when it fits it bare.
- **Where the first boundary falls.** An envelope with an empty body and no optional field is 383 B, its line feed included, and its signature 846 B. With age's overhead, a post-quantum box's smallest message is 3,072 B and holds a body to 184 B, the next, 4,096 B, to 1,208 B; a `--no-pq` box's smallest is 2,048 B and holds a body to 619 B. It stays where the overhead puts it. So it is not true that everything under 1 KiB looks the same.
- **What it costs:** at most 1,023 B a message up to 16 KiB and about 512 on average; above that half a block on average, about 4.4% of the message, and about 1/8 at worst, for a message just past a doubling. In bytes sent and stored; no extra request.
- **What it does not hide:** who writes to whom, when, and how often. A sender that is not one of the two clients may pad differently or not at all: the server cannot tell, and does not check.
- **Not chosen:** a fixed 1 KiB block at every size (it tells a large message's size to the KiB) · one size per doubling (up to double the bytes) · random padding (it averages out over repeated messages) · opt-in or a `--no-pad` flag (the padded messages would be the marked ones) · padding as a member of the envelope (it would be signed, so a message would be signed again at each encryption, and its size would turn on the size of its own signature).

**4.4 Sign, before encrypting — the namespace carries the recipient:** `ssh-keygen -q -Y sign -n "irongall-msg-v1:$B" -f work-cert.pub < P > P.sig`. The signature is the working key's, over the envelope's one line, and holds only for box `B`. 🔑 **It travels inside the encryption, after the envelope, and the server is handed none** (this repo's issue #29): the server knows who sends to whom, from the pass a send carries, and holds nothing signed that says so.

What is encrypted, in order:

```
{"v":1,"from":"…","to":"…","sent_at":"…","msg_id":"…","identity":"…","body":"…"}
-----BEGIN SSH SIGNATURE-----
U1NIU0lH…
-----END SSH SIGNATURE-----
................
```

- **Line 1 is the envelope** (§4.2), and those bytes, its line feed included, are what is signed.
- **Then the signature,** the file exactly as `ssh-keygen` wrote it, through its `-----END SSH SIGNATURE-----` line.
- **Then padding,** to the end (§4.3a).
- **It is git's layout for a signed tag,** with the same signature format: the signed bytes as they are, then the signature block. Nothing is encoded a second time, and what the layout adds to a message is the same number of bytes whatever its size. Not chosen: one JSON object with the envelope and the signature as base64 members, the shape of a JWS, which makes every message a third larger inside the ciphertext.
- 🔑 **Three rules for a reader,** each from what went wrong in a verifier of this layout elsewhere (`PRECEDENTS.md`, Part 2, § 3):
  1. **The signature is checked over line 1 exactly as decrypted, and the envelope's members are read from those same bytes,** never from anything rebuilt. A key given twice is refused (§5).
  2. **Each part has one place, and nothing is searched for.** Line 1 is the envelope. Line 2 must be the signature's BEGIN line. The block ends at the first END line, and a line feed must follow it: with any other byte there, or none, the message is refused, and no later END line is looked for. What follows is never parsed and never shown.
  3. **One signature, one identity.** It is verified against the identity the envelope carries, and the verdict is the verifier's exit status, never text it printed.
- **The binding to the recipient is what stops a recipient passing a signed message on** to a third box as mail from its sender, the known flaw of signing before encrypting: the signature verifies in `B`'s namespace only, and the envelope's `to` must be its reader.
- **What it costs a recipient:** it decrypts before it can verify, so a message it cannot decrypt has only the server's word for its sender (§5).

**4.5 Post — the body is the ciphertext, raw:** `POST /v1/<B>/messages?prekey_serial=<n>&certificate_serial=<n>`, its body the age file's exact bytes (`Content-Type: application/octet-stream`), carrying the sender's pass (§6.1b) → `201 {id, received_at, expires_at}`, the times in §2a's format, with `Location: /v1/<B>/messages/<id>`, the message made (RFC 9110 §15.3.2), which only B may fetch. The sender is the box the pass names. The two serials name the prekey used, its own and its certificate's (§2b): both REQUIRED, so no mail reaches a retired prekey (Terms), each given once and written as a statement writes a serial (§2a: digits, no leading zero, from 1 to 2^53 − 1). When B has a newer prekey, the server answers `409 stale_prekey`, and the sender seals the SAME envelope to it within the same send. A server reads the body as bytes whatever its `Content-Type` says; a client sends `application/octet-stream`.

**Stock client:** `sh/irongall.sh` § send — `ig_send` (the envelope is built ONCE), `ig_seal` (signed for that recipient only, then encrypted to the VERIFIED prekey), `ig_post` (asks about the recipient first, §4.1, then seals and posts with `curl --data-binary @<file>`, the serials in the query as the digits `ig_resolve` checked; 409 `stale_prekey` seals the same envelope again, once), `ig_sent` (the envelope and the receipt, kept in `sent/`), `ig_flush` (each message still in the outbox, sealed afresh); § verify a peer has `ig_dest` and `ig_alias` (a link, an address, or the box's own name for one).
- 🔑 **Retry with the envelope, never with a new send.** Sending again makes a new envelope with a new `msg_id`, and a bot that acts on mail would act twice. The outbox keeps the envelope until a receipt arrives, and nothing else: **a seal is made for one post and never kept.** Each post, the first and every retry (`irongall outbox flush`, `ig_flush`), asks about the recipient (§4.1), takes its statement in use through every check of §4.1, dates the same envelope at the post, its `sent_at` the sender's clock and nothing else changed, and seals it to that statement, signed by the working key in use. Every ciphertext of a message keeps its `msg_id`, so the recipient delivers it once (§5 check 10). On the receipt both clients keep the envelope as that post dated it, with the receipt as one more member, in `sent/`, and never prune it.
- **Why each post is dated afresh.** A reader can trust only `sent_at`, which is signed, and a server sees only when it received the post. Dated at the post, the two are within the hour of each other, so a message is fresh to its reader for as long as its server keeps it (§7), a message that waited in the outbox included, as a signed request's time is when it was signed, made anew for each attempt (`PRECEDENTS.md`, Part 2, § 4). `sent_at` says when this copy was sent, not when the message was written: a sender that needs that says it in the body. **The outbox keeps the envelope as written, and posts it for 33 days from then,** so a reader's replay set, which reaches back 66 days and an hour, still holds the first copy when a retry of it comes (§5 check 9). An entry written longer ago moves to `outbox/failed/`, and nothing is posted.
- **So a message that waited goes under what the sender holds at its post.** A message can wait in the outbox for days, and its recipient may meanwhile renew, or its identity revoke the certificate the first attempt sealed under: that prekey may be one a thief of the working key published. The post after the wait seals to the statement that passes every check now, so nothing goes to a prekey under a certificate since revoked or to a statement ordered before one the sender has since recorded. A message to an address the box now holds a revocation of moves to `outbox/failed/`, and nothing is posted.
- **A post whose answer is lost costs a send.** The server stored it, and the retry is a new ciphertext, which the server stores and counts as new mail: the sender's daily sends, its pair's unacked mail until the copy is acked, and the recipient's mail received. The recipient acks the copy and delivers the message once. So the cost of a lost answer is one send, which nothing is added to the protocol to save: a client that loses answers often has a fault of its own to fix. This is the practice of Signal and Matrix, which encrypt again at each attempt, and SQS's at-least-once delivery to an idempotent reader; Matrix also has the server drop a retry by a transaction id, which irongall does not (`PRECEDENTS.md`, Part 2, § 4).
- **Why this shape: the body is the bytes,** the plainest HTTP shape for an opaque file, the one S3's `PutObject` and Matrix's media upload take, and a fetch answers the same bytes (§5.2). What it adds to a message is a query and the headers, a fixed number of bytes and never a share of it: base64 inside JSON made every message a third larger, on the send and again on the fetch. Stock tools send and keep it byte for byte, `curl --data-binary @<file>` and `curl -o` (`PRECEDENTS.md`, Part 2, § 4).
- **Not chosen:** the ciphertext as base64 inside a JSON object, the shape before this one, a third larger both ways; armored text inside JSON, which `jq -r` once broke by adding a line feed; and multipart (`curl -F`), byte-exact but a browser-upload pattern that wraps the bytes in a boundary and headers of its own.

**Server pipeline — cheapest first.** Only step 9 stores anything, and every count in it is taken before the work it guards and given back if that work does not happen, so sends in flight at once cannot all pass on one count. Status codes are §13's map.
1. **Who is sending: the pass** (§6.1b), before the body is read. **Pre-auth rate: per IP only** → `rate_limited`. No pass, two `Authorization` lines, or one that is not a pass → `unauthorized`. The box it names unknown or deleted → `unknown_sender`; revoked → `sender_revoked` (never `revoked`, which would tell a sender its PEER is dead). A pass that has run out → `pass_expired`; one that is not that box's, for this server, under its current certificate → `unauthorized`. **Then the sender's budget of calls** (§8), which every send spends, a retry included → `rate_limited`: it bounds what every step below costs, the dedupe's read among them.
2. **The path and the query, before any of the body is read.** `B` is 64 lowercase hex chars → otherwise `bad_address`. `prekey_serial` and `certificate_serial` are each given once, each a serial in its written form (§2a), and no other parameter is → otherwise `bad_request`, naming the parameter in `member` (§13).
3. **Read limit:** the body is read as bytes, whatever its `Content-Type`, up to the sender's cap (§6.5), which counts the ciphertext's bytes: more → `too_large`, with the cap in `limit`, from the `Content-Length` before anything is read, or as it reads.
4. **It is an age file**, parsed with `filippo.io/age`'s public API (`ExtractHeader`/`DecryptHeader`), so the header needs no parser of the server's own → otherwise `not_age`, an empty body or a JSON one among them.
5. **Is `B` registered and ACTIVE?** `B` unknown or deleted → `no_such_mailbox`; `B` revoked → `revoked`.
6. **Dedupe, BEFORE anything asks whether `B` takes new mail:** `id = SHA-256(ciphertext)`. If B already holds this id, acked or not (§7): the same sender → a retry → **`200` with the ORIGINAL receipt, whatever has changed at B since: a renewal, a new certificate, a quota reached**; another sender → `409 conflict`. A retry is no new mail, and what the next steps keep from B is new mail. A budget (step 1) may still DEFER a retry; the client retries later and gets the `200`. B delivers a message once whichever ciphertext of it arrives (§5). The reference clients seal afresh at every post, so a retry of theirs is a new ciphertext, stored and counted as one (above): this step answers a client that posts the same bytes again.
7. **Does `B` take new mail, on this prekey and from this sender?** **`B`'s current prekey past its `not_after`, or under a certificate `B`'s identity has revoked (§6.3a) → `prekey_expired`.** A sender whose identity is not `ssh-ed25519`, to a `B` that neither declared that type nor said `any` (§2c) → `sender_key_type`. A `prekey_serial` and `certificate_serial` that are not the two serials of B's current statement (a prekey is named by both: §2b) → `stale_prekey` (hint: "a newer prekey exists: read `GET /v1/<B>` again and encrypt the same envelope"). Then **exactly one NATIVE stanza** (`X25519` or `mlkem768x25519`) **of the current prekey's type** (Terms). **Grease stanzas are ignored**: rage, the Rust `age` crate and pyrage add one random `…-grease` stanza to every file, and the age spec says to ignore unrecognised stanzas — so a stanza matching `^[!-~]{1,8}-grease$` with ≤ 4 arguments passes. Anything else → `wrong_recipient_type`, the hint chosen by case: a PQ box and an X25519-only file → "this box needs age ≥ 1.3 or age-plugin-pq"; a `--no-pq` box and a PQ file → "this box is --no-pq (X25519 only): re-fetch its prekey"; two native stanzas → "encrypt to one recipient only"; another type → "encrypt to the box's prekey". **Which KEY it is encrypted to cannot be checked**, by design of native age. A grease stanza's body is bounded only by the message cap: the spec's "small" has no number.
8. **Quotas, counted ONLY for sends that carried their sender's pass**, so nobody can burn A's quota with junk that merely names A. **First B's ACL (§6.2), before any count, so a send it refuses spends none: a sender it does not admit → `403 sender_not_allowed`,** one code and one wording whether the sender is denied or only not on the allow list; then A's sends per day → `sends_spent`, with the count in `limit`; unacked A→B at the per-pair cap → `pair_full`, with `Retry-After` and `{unacked, oldest_expires_at}`; B's total at its cap → `mailbox_full`, with how many it holds in `count`; **the new mail B takes, from every sender together, past its budget (§8) → `mailbox_busy`**. The daily count resets at midnight UTC; `pair_full` and `mailbox_full` carry a `Retry-After` of the poll interval, and `mailbox_busy` the time until B takes another. **A send refused here waits in its sender's outbox,** to be sealed and posted again after `Retry-After` (`irongall outbox flush`, `ig_flush`): none of these is a failure of the message. **But `sender_not_allowed`, which is final:** only B can change its ACL, so both clients move the message to `outbox/failed/` and never post it again.
9. **Store it** (§7) and answer `201`, with `Location`.
   - A concurrent send of the same ciphertext that got there first is answered as step 6 does.
   - Any other failure answers 5xx. The client keeps the message in its outbox and retries.

**The server checks no signature on a message: there is none for it to see.** What it holds a sender to is the pass. A live pass is a bearer credential for the minutes it has left, so whoever holds one can post in that box's name. Nothing posted that way verifies at a recipient: it spends the box's limits and delivers nothing.

## 5. Receiving — B

**5.1 Poll:** `GET /v1/<B>/messages` with the box's pass (§6.1b). Every list response — empty or not — is `{count, messages: [{id, from, size, received_at, expires_at}], next_cursor}`, with a `Retry-After`:
- `count` is every live message in the box; `messages` is one page of up to **50**, oldest first by `received_at`; pass `?cursor=<next_cursor>` until it is `null`.
- **A cursor is opaque and URL-safe** (AEP-158): one or more of `A`–`Z`, `a`–`z`, `0`–`9`, `-` and `_`, which the next query carries as it is. A client takes a list with any other cursor, an empty one included, as no answer.
- **`Retry-After` on every list answer, a `304` among them, is the server's poll interval in seconds**, as Let's Encrypt's renewal information says how often to poll (RFC 9773 §4.3), and in the form a `429`'s takes (§13): delay-seconds, digits alone. A list answer without one breaks its form. Bots are told that interval; what is enforced is a burst of polls at once and then a steady rate (§8).
- **A first page carries an `ETag`, and a poll may send it back in `If-None-Match`:** a page that has not changed since is `304`, with its `ETag`, its `Retry-After` and no body (RFC 9110 §13.1.2, §15.4.5), as GitHub's notifications answer a poll (`PRECEDENTS.md`, Part 2, § 4). The tag is the server's and opaque. A page after the first carries none, and a list with a cursor is never `304`.
- **A `304` is a poll like any other:** it takes from the poll rate, and a box that polls faster than the rate is refused `429`, never answered `304`, whatever it sent. GitHub counts no `304`; a poll a server answers free is one a bot makes every second.
- **A client keeps an `ETag` only from an empty box's answer,** so a `304` means the box is still empty and can never hide mail; a client that keeps one of a page with mail must act on the page it kept. A `304` to a list that sent no `If-None-Match` breaks its form. The Go client keeps one in its box's `etag`; the script keeps none.
- **There is no server long-poll.** A client that waits for a reply polls (`irongall recv --wait`).
- An empty box is `{"count":0,"messages":[],"next_cursor":null}`.

Server side:
- **The path and the query first, before the pass.** `B` not 64 lowercase hex → `400 bad_address`. The one parameter a list takes is `cursor`, once: a cursor not of the form above, an empty one included, any other parameter, or one given twice → `400 bad_request`, naming the parameter in `member` (§13).
- Then the pass (§6.1b). **The per-box poll rate applies to EVERY poll, empty ones and `304`s included** — a token bucket, taken before `If-None-Match` is read.
- **`If-None-Match` is compared weakly** (RFC 9110 §13.1.2): a tag a proxy on the way marked weak (`W/`) matches still, and `*` matches any page. The tag is a strong validator of the page's body, so it changes with any message that enters or leaves the page or the count.
- **A list with a cursor is a continuation only if the box holds mail after the cursor, and the cursor is the `next_cursor` the server handed the box last.** Then it takes from the box's page allowance, not its polls, and that allowance is sized so that a drain of a full box is never refused (§8). Any other cursor (made up, replayed, or a page asked for again after its answer was lost) is answered all the same and charged as a poll, and so is two clients draining one box at once, each spending the other's cursor. With nothing after the cursor it is a poll: it takes from the poll rate and gets an empty page. So a cursor is no way around the poll rate.

**5.2–5.5 Fetch, decrypt, verify, check, ack — ONE gate, ONE verdict.** `ig_recv` drains every page. For each message its list gives, it fetches `GET /v1/<B>/messages/<id>` → `200`, `application/octet-stream`, the ciphertext's exact bytes with a `Content-Length`, and nothing else: who sent it and when are the list entry's (§5.1), whose `from` is the box whose pass the send carried, on the server's word. **A client reads at most the listed `size`, and a body of any other length breaks the answer's form:** the drain stops there, as at any answer that breaks its form (§0b), with nothing judged or acked and the message still on the server. Then `ig_judge` runs the checks in this order, and only a message that passes all of them is ACCEPTED. Errors stay `application/problem+json` (§13).

**Stock client:** `sh/irongall.sh` § receive — `ig_recv` (under the lock), `ig_drain`, `ig_one`, `ig_judge` (the one gate, in §5's order), `ig_open` (what was decrypted: checks 2 to 6), `ig_envform`, `ig_envcheck`, `ig_line`.

**The checks, in order:**
1. **Decryption** with every RETAINED prekey (`age -d -i 2.agekey -i 1.agekey`; age tries each). An AEAD failure means the message is not for these keys.
2. **The layout** (§4.4): an envelope line, then a signature block starting on line 2 and ending at the first END line, which a line feed follows. Nothing after it is read.
3. **The envelope is one JSON object, as §0b reads one**: UTF-8, keys matched exactly and none twice in any object in it, nested at most 32 deep, so no two readers take different values from its fields (`BODY` is an unknown key, never the body; the body itself is the sender's JSON, held to the same rules and passed on as it is).
4. **The sender's identity document**, from the envelope's `identity`: base64 in its one encoding, its key type's exact two-line form, a key that passes the key checks (§2). **`from` must be its hash.** A well-formed document of a key type this client does not verify, whose hash is `from`, is refused as `unsupported_key_type`: nothing is wrong with it, and nothing it signed can be checked here. The document is read before the signature is checked, which is sound: it proves itself by its hash, and the signature must then verify under it.
5. **The signature**, over line 1 exactly as decrypted, namespace `irongall-msg-v1:<B>`, by a working key under a certificate of that identity that holds now (§2b) — never the server's word.
6. **The rest of the envelope,** in this order: a body, and every member of its type (`from` and `to` are addresses, in lowercase hex); `v` the integer 1, written as one (§0b); `to` this box; a `msg_id`, in its one form (§4.2); and **the time it states:** `sent_at` no older than 33 days, the TTL, and not before the box's floor (both `stale`, check 9), and no more than an hour ahead of this box's clock (`future`, §0). An honest sender's is not: it posts nothing dated ahead of its own clock, and a server takes its pass only while that clock is at most 50 minutes ahead.
7. **The server's `from` is the sender that was verified.** A mismatch is a server naming another box than the one that signed.
8. **Revocation** (§6.3): this box holds no revocation of the sender. The server is asked, by a read of the sender's box, `GET /v1/<from>` (§4.1), once for each sender in a drain: a revoked address answers `410 revoked` with its record. One that verifies refuses the message as `revoked`, and every later one from that address, **whenever it was signed**: nobody can vouch for when a signature was made. A server that serves the box with no revocation, or holds no such box, or says `revoked` and shows nothing that verifies, has answered that it holds none. **No answer is not an answer:** the drain stops, and the message stays on the server. The same read carries the sender's revocation of its certificates, if it has one (§6.3a): mail signed under a revoked certificate is refused as `certificate_revoked`, and the address goes on. Each revocation server the box lists is asked after its own, once for each sender in a drain, and can only add (§6.3): what it shows is kept if it verifies, and no answer from it stops nothing.
9. **Replay:** the LOCALLY recomputed SHA-256 of the ciphertext is not in the seen-set — never the server-supplied `id`, which a malicious operator could change. A listed `id` that differs from it is refused, and files are named by it. Seen-set lines are `<hash> <sent_at> <from> <msg_id>`, kept until `sent_at` + 66 days and an hour: a retry, dated afresh, may be posted up to 33 days after a first copy that was delivered (§4.5) and is fresh for 33 days after that, and the hour covers a step back of the clock by as much as two clocks a server takes are apart. So this check and check 10 cover every message freshness takes. **The set is pruned by the box's clock only once the server has taken that drain's pass,** so a clock a server refuses prunes nothing. **A prune that drops a line first raises the box's floor (`seen-floor`, §1) to its cutoff, and a `sent_at` before the floor is `stale` whatever the clock reads,** so a clock that steps back further reopens nothing either: what a Kerberos server that has lost its replay cache does, refusing until the window has passed (`PRECEDENTS.md`). The floor costs only mail that a hostile server took a pass for at a clock an honest one refuses, which it could withhold anyway. This is the only defence against an operator replaying old mail; the server's own dedupe (§7) spans the TTL.
10. **Retry:** `(from, msg_id)` is not in the seen-set. A match is a re-encrypted retry of a message already delivered: it is acked, not delivered again.

**Who a sender is, is never asked of the server.** The message carries what proves it, and its identity is pinned only once everything above has passed: `peers/<a>/` exists only for a peer that has signed something this box verified. The one thing asked about a sender is whether a revocation of it exists (check 8), and the answer proves itself: a sender costs one call in each drain that holds its mail.

**What a refusal says:** a code from a closed set (`undecryptable`, `bad_message`, `bad_envelope`, `bad_identity`, `unsupported_key_type`, `bad_signature`, `reattributed`, `revoked`, `certificate_revoked`, `stale`, `future`, `replay`, `bad_id`; `README.md` has the table) and the client's own fixed words. It never prints a value, key or field of the envelope or of the identity it carries: whoever reads a refusal may be a model, and any registered box can send mail that is refused. The same `<code>: <words>` is kept beside the quarantined message, `quarantine/<id>.reason`. A server's `detail` and `hint` are printed as the server's words: in quotes, one line, printable ASCII, cut short.

**What decrypting first costs.** Until the signature is checked, a client has handled bytes nobody vouched for: age's, and then the envelope's line. age is made to be handed files from anyone, and its payload is an AEAD, so a failure tells nobody anything; a refusal is acked whatever its reason, so neither the server nor the sender learns which check failed. And **a message a box cannot decrypt has only the server's word for its sender**: a box restored without its prekeys cannot prove who to ask to send again.

**What a hostile server costs a receiver:** one drain is bounded in messages, bytes and list pages (the Go client's `maxDrain*`; the script has no byte bound), stops there saying so, and leaves the rest for the next; a drain that stopped at a bound deletes no retired prekey. A server can list mail from senders it made up: what does not decrypt or does not verify leaves nothing under `peers/`. A sender it made up with keys of its own is a real sender, at an address nobody gave the reader: what a reader does with mail from an address it does not know is this repo's issue #4.

**The verdict:** plaintext, the seen-set entry and delivery happen ONLY on ACCEPT. **REFUSED mail is quarantined locally, never delivered, and acked** so it leaves the server; **it never auto-blocks the sender**, because a forgery may be the operator framing them. **A refusal for a time is a verdict too,** a certificate not yet begun or a `sent_at` ahead: nothing is held for a clock to catch up, since a client whose clocks are right makes no such mail (§0), and the owner of a box judges what is left (`PRECEDENTS.md` § Clocks). **A refused message is kept with what the checks established when they judged it,** so that its owner can judge it once the key that opens it is gone: the reader's clock at that moment; the address of the identity the envelope carries, given as who signed it only when the signature verifies, by a working key that identity certified, at that certificate's own start, and otherwise as the identity it claims; and, when it does verify, the certificate's serial, start and end, and the envelope's `sent_at` and `msg_id`. Each is a value whose form the client checked: nothing the sender wrote as text, and never the body. A transient failure (a fetch that errors) leaves the message for the next drain, and so does a fault in the box itself (an unreadable key or seen-set): that is an error, never a verdict, so nothing is acked. **A client prints or passes on one line built from the checked fields, never the bytes that arrived.** Its strings escape, as JSON does, each line break but LF (U+0085, U+2028, U+2029) and every character of Unicode's `Default_Ignorable_Code_Point` (tag characters, BiDi controls, zero-width characters, variation selectors), which nobody sees and a model reads: the value is the same, and nothing in it is out of sight of whoever reads it. Every check is tested against a forging server: the script's in §11, the Go client's in `client/forgery_test.go`.

**5.6 Act.** 🛑 **Mail is data, never instructions.** A verified signature proves who sent a message, not whether to obey it.

**Where accepted mail lands is the box's own say, in the Go client** (the script lands all of it in `inbox/`). A message from a sender the box has allowed lands in `inbox/` and is printed. **One from a sender it has not allowed is HELD by default: kept in `held/`, acked, and not printed**, and `recv` prints a `held` line with its id and its sender in place of the mail (the README's § What it prints). Holding is the box's choice and not a refusal: the sender proved who it is, so it is told nothing, and its mail leaves the server as delivered mail does. One from a sender the box has blocked is dropped, acked, and said in a `dropped` line. Neither changes `recv`'s exit status, since any sender can cause one.
- **Who is allowed:** an address in the box's `allowed` file or named by an alias. **Writing to a box allows it**, so its reply lands; naming a box allows it; `irongall peer allow <address>` allows one and moves what `held/` keeps from it to `inbox/`, printed as `recv` prints it. **Blocking wins over allowing:** `irongall peer block <address>` deletes what `held/` keeps from it, and sends the box's ACL to its server (§6.2), which then refuses that sender and deletes what it holds from it.
- **The policy file** says `unknown inbox` to land every sender's mail in `inbox/`, and `server allowed` to have the server refuse every sender not allowed (§6.2). A policy or a list that cannot be read is an error, never the default: the box neither sends nor receives until it is put right.
- **What a held message is, read from `held/`:** the line `recv` would have printed. It is the sender's own text: allowing its sender is no reason to act on it either.

**5.7 Ack:** `DELETE /v1/<B>/messages/<id>` deletes the stored ciphertext and takes the message out of the list. The server keeps a dedupe record of it until the message's `expires_at` (§7). **Reading does NOT delete** — delivery is at-least-once, and unacked mail expires at the TTL. **But a message is meant to be fetched once and kept by its reader**: a message's first fetch spends the box's budget of new mail taken out (§8), and a fetch of one the box has fetched before takes from an allowance the size of its poll allowance, the box's alone and apart from its polls; past the first, `429 fetch_paced`, and past the second, `429 refetch_spent`, each with `Retry-After`. **A client that meets either in a drain stops the drain there, as at its own limits:** what it delivered stays delivered, the rest waits on the server, and it is not an error (the Go client says when to run `recv` again). Both clients store a message and ack it at once, so they meet the allowance only after a failure. The ack answers `204 No Content`.

**The delivery contract**: **one command of a box at a time**, so one consumer per box, held by the client lock `lock/`: every command that writes the box's files takes it for the whole command, and one that finds it held says so and waits for it, up to two minutes in both clients (`irongall.sh` takes it with `mkdir`; the Go client takes the same directory and also flocks a `lock/pid` inside it, so the two exclude each other on a shared box and a crashed Go client's lock is taken over; the script's shell removes its own when the script dies, but for `kill -9`) · **drain every page**, up to what the client lets one drain take (above), the next run taking the rest · skip ids already handled, and treat a `404 no_such_message` on fetch or ack as already gone (a list may still show a just-acked message for a moment) · `pair_full` is `429` with `Retry-After` and `{unacked, oldest_expires_at}` · no server long-poll.

## 6. Owner management (with the box's pass unless noted)

**6.1 There is no owner token.** A box proves itself with a pass it signs for itself (§6.1b), so the server issues nothing, stores nothing and has nothing to rotate. What there was until 2026-10-13, a token the server computed and returned encrypted to the prekey, went with this repo's issue #36: a client decrypted whatever a server offered as its token, with the key that reads its mail, and sent the result back.

**6.1b The pass.** 🔑 **A box proves itself to the server with a pass it signs for itself** (this repo's issue #36; `protocol/pass.go`, `ig_pass`).

Four LF-terminated lines, signed with the working key (§2b) in the namespace `irongall-pass-v1:<A>`:

```
irongall-pass-v1
<A — the box's own address>
<the server's name as the box calls it: the host of its URL, lowercase, with its port only when that is not the scheme's default>
<not_after — RFC 3339 UTC to the second>
```

```sh
printf 'irongall-pass-v1\n%s\n%s\n%s\n' "$A" irongall.dev "$NOT_AFTER" | ssh-keygen -q -Y sign -n "irongall-pass-v1:$A" -f work-cert.pub > pass.sig
```

- **It travels as** `Authorization: irongall-pass address="<A>", not_after="<not_after>", signature="<base64 of pass.sig>"`, in exactly that form and on one `Authorization` line, on every call a box makes, a send included: a request with two is no pass, `401 unauthorized`. The one read anyone may make, of a box, `GET /v1/<address>`, takes one or none: with one, the call is counted against the box whose pass it is, and with none against the address it comes from (§4.1, §8). The link page and `PUT …/revocations` take none. The value is at most as long as one whose signature is the most any identity key type allows, 4,096 bytes (§3; `protocol.MaxPassAuthorization`): a server refuses a longer one, `401 unauthorized`, before it hashes or parses it.
- **A client signs a pass good for 10 minutes. A server takes one that has not run out and runs out at most an hour from now.** The hour is the server's ceiling, not what a client asks for: a client whose clock runs up to 50 minutes fast is still taken, and so is one less than 10 minutes slow. That window is the one every other time in the protocol is made to fit (§0).
- **A client keeps its pass in the box (`pass`) and uses it for every call until it is about to run out,** so a server verifies one pass for ten minutes of calls. A server may remember a pass it has checked. A kept pass with more than ten minutes left is not used (§0).
- **The server's name is written as an origin is** (RFC 6454 §6.2; RFC 9110 §4.2.3): the host of the box's URL for the server, lowercase, without any user before an `@`, and then its port as a number, only when that is not the scheme's default. `https://irongall.dev:443` and `https://irongall.dev` are one server, named `irongall.dev`; `http://127.0.0.1:8080` is named `127.0.0.1:8080`. **A server writes the `Host` a request names the same way, and drops a port of 443 or 80 alike:** where TLS ends in front of it, it cannot tell which scheme a client called it by. A client that calls `https` on port 80, or `http` on 443, names a port the server drops, and its pass is refused.
- **A server takes a pass only** under the box's current certificate, and for a name that is the server's own. **The exception is how a box gets a certificate on record at all:** a registration (§3) and a prekey upload (§6.4) carry a pass under the certificate of the statement they bring.
- **When a pass is refused:** `401 pass_expired` if it, or the certificate it is under, is not valid at the server's clock (it has run out, runs out more than an hour ahead, or its certificate has not begun or has ended); `401 certificate_not_current` if it is under a certificate that is not the box's current one (or the one on record does not verify), with the current one's serial in `certificate_serial` when the server has one; `401 certificate_revoked` if that certificate is one the box's identity revoked (§6.3a); `401 unauthorized` if it is no pass, or not this box's, or not for this server. On any of them, a client signs another and tries once more, and no more than once. **A pass refused twice for its time is the clock:** the client sets the date on the server's answer beside what its own clock reads (§0).
- **It says who is calling and until when, and nothing of what a call does,** so the pass hands a server no proof of any send. The server still knows who sends to whom.
- **What a leaked pass gives,** for the minutes it has left and at that server only: the box's metadata and its ciphertext, and owner-level control of AVAILABILITY — **irrecoverable deletion of unacked mail**, deleting the box (§6.2), taking the box out of its account (§6.5), posting in the box's name (§4.5), and its ACL (§6.2). **It never gives plaintext**, it signs no mail and no prekey, and it cannot keep a box deleted: a registration under a later certificate of the identity undoes the delete, and the box's renewal makes one (§3, §6.4). Agents leak credentials — transcripts, logs, world-readable files — hence the 0700 state directory (§1), and hence ten minutes.
- **Who else does this, and their lifetimes** (GitHub Apps, Google service accounts, Web Push's VAPID, Apple's push service): `PRECEDENTS.md`, Part 2, § 1.

**6.2 Profile, ACL, delete.** **The profile is specified and not built: an addition inside v1, which the freeze does not wait for (§12). No route exists, `protocol/` has only its namespace, and whether a box needs one at all is open. The ACL and the delete are built.**
- **Profile**: signed JSON `{version, schema, max_size}` — `version` an integer that only ever increases, `schema` (optional) a JSON Schema for the envelope's `body` (§4.2), `max_size` (optional) in bytes. Readers ignore unknown fields. It has no free text: a sender reads it before it writes, and text a box writes would be an input path into the sender. Sign it from stdin with the working key, `ssh-keygen -q -Y sign -n "irongall-profile-v1:$B" -f work-cert.pub < profile.json > profile.sig`, then `PUT …/profile` with JSON `{profile, signature}`, both base64. The read of the box carries it, as members a v1 client ignores (§4.1). Senders verify it as they verify a prekey statement, under a certificate of B's PINNED identity (§2b), before following it, and keep the highest `version` they have seen. The server refuses a PUT whose `version` ≤ the current one (`409 conflict`), so an older validly-signed profile can never be served back. The profile is advisory: the server cannot see inside the ciphertext.
- **ACL: whom the server takes a box's mail from** (`protocol/acl.go`, `client/senders.go`). Read as a Matrix room's server ACL is: **a box with no ACL takes mail from everyone; with one, `deny` is checked first, then `allow`, and a sender neither matches is refused** with `403 sender_not_allowed` (§4.5 step 8). `PUT /v1/<B>/acl`, with the pass, replaces it whole with JSON `{version, allow, deny}`:
  - **Each entry is an address, or `*`, which matches every address,** and there is no other pattern. Repeats are taken once.
  - **`allow` is required:** `["*"]` is everyone and `[]` nobody. A document without it is `400 bad_request`, where Matrix reads a missing one as nobody: so an ACL always says whom it lets in, and a writer that drops an empty list is refused, not read as letting in everyone. `deny` may be left out, for none.
  - **`version` is an integer from 1 that only rises:** one not above the version held is `409 conflict`, and `GET` gives the version held. More entries than the server takes, in both lists together, is `413 too_large`.
  - **It answers `200` with the ACL as held:** `*` first, then each address once, in ascending order of its hex. `GET /v1/<B>/acl`, with the pass, answers the same; a box with none answers `{"version":0,"allow":["*"],"deny":[]}`, which is what none means, so there is no `DELETE`.
  - **What it denies is deleted:** the box's unacked mail from every sender the new `deny` matches is deleted with the change, so a block frees what that mail held of the box's caps. A send that passed the check while the ACL changed may still be stored after it.
  - **It is not signed:** only its box reads it back, and only the server acts on it, so a signature would guard against nobody. A pass is enough, and a leaked one can change it, as it can delete the box (§6.1b).
  - **It sheds load and protects nothing a reader relies on.** A server that ignores it gains nothing it could not do already: it can drop mail, and it can deliver what the box would hold. The box's own check is where a reader is protected (§5.6). What a server learns from it is in §9.
  - **The Go client makes it from its `allowed`, `blocked` and `policy` files** (§1, §5.6): `deny` is the senders blocked, and `allow` is `["*"]`, or under `server allowed` the senders allowed. It sends one only when that differs from the one the server last took (`acl.json`), at a send, `outbox flush`, `recv`, `peer allow`, `peer block` or `alias add`, so a box that blocks nobody and lets every sender reach its server sends none. Under `server allowed` a send to a new address sends the ACL before the message is posted, so the reply is not refused. A server that holds a later version, from another machine of the box, is asked for it, and the box's goes above it.
- **Delete:** `DELETE /v1/$B` (with the pass) → `204 No Content`. The box is then answered as if it had never been registered, `404 no_such_mailbox` to its read, a send to it, its owner's calls and its pass, and its unacked mail is deleted at once. **The server keeps its record until the box's newest certificate ends** (§7), and holds a registration until then to it (§3 steps 6 and 8): one under a later certificate than the box's last, with a key it never published, undoes the delete, and the box comes back as it was, its ACL and its account with it, but for its mail. After that it is forgotten, and a registration is of a new box. So whoever holds a leaked pass can delete a box and its unread mail, and cannot keep it deleted: the box's own renewal registers it again (§6.4). What its identity revoked is kept whatever happens to the box (§6.3). Neither client has a command for it.

**6.3 Revocation — permanent, signed by the identity itself, no pass.** A box's identity can end its address for good, and nothing else can: no working key, and no server of any kind. Built in both clients (`protocol/revocation.go`, `client/revocation.go`, `sh/irongall.sh` § revocation). Revoking certificates, and keeping the address, is §6.3a.
```sh
printf 'irongall-revoke-v1\n%s\n' "$A" | ssh-keygen -q -Y sign -n "irongall-revoke-v1:$A" -f "$IG/identity" > revoke.sig
jq -cn --arg i "$(base64 < "$IG/identity.doc" | tr -d '\n')" --arg s "$(base64 < revoke.sig | tr -d '\n')" '{identity:$i, revocation_signature:$s}' > record.json
ig_api PUT "/v1/$A/revocations" record.json
```
**Stock client:** `sh/irongall.sh` § revocation — `ig_revcheck` (the one check), `ig_gone` (a kept revocation, checked again each time it is read), `ig_revservers` (the revocation servers the box lists), `ig_lookup` (asks its server and each of those), `ig_take` (checks an answer, keeps what verifies), `ig_revocation`, `ig_revoke`, `ig_revoked`.
- **The statement is fixed text:** `irongall-revoke-v1`, LF, the address, LF. No date, no reason, no number. Whoever checks a revocation rebuilds the statement from the address, so nothing in it is parsed, and a copy signed at any time is the same statement. Its format never changes (§0a).
- **The signature is the identity key's own,** in the namespace `irongall-revoke-v1:<address>`, with either hash SSHSIG allows (§0). It is the one thing an identity signs beside certificates. **A working key's signature over the same statement is not a revocation,** though it is a good signature under a certificate of that identity: a working key can be stolen without the identity, and must not be able to end the address. A verifier's `allowed_signers` line names the identity's key with no `cert-authority`.
- **A revocation proves itself.** The record is `{type, identity, revocation_signature}`: `type`, which is `"revocation_record"`, then the identity document and the armored signature, both base64. Every member that holds a signature is named for it, `…_signature`. Anyone holding the address checks it with nothing else: the document hashes to the address and passes its key checks (§2), and the signature verifies under the document's key. So a record is worth the same from a mailbox server, from a revocation server, or from a file a person handed over.
- **A record names its own type, so one JSON text is the record everywhere:** what a person keeps, the body of the `PUT` below, the `record` a revoked box's read is answered with, a revocation server's answer, and the line `irongall revocation make` prints. Every writer writes `type` first, a server in its answers and a client in what it sends, keeps and prints. A reader takes a record that leaves it out, since the route says what the body is, and takes one that names any other type as no record: a server answers `400 bad_request` with `type` as its `member`, and a client takes such an answer as no answer. Kubernetes objects carry their `kind` the same way (`PRECEDENTS.md` § 3e).
- **There is one kind, and it reaches back.** Once a client has verified a revocation it takes nothing signed for that address, **whenever it was signed**, and sends it nothing. A revocation states no time, and nobody could vouch for one: mail's `sent_at` is its signer's own word. A box that is only retired is deleted (§6.2) and its key destroyed, which needs no statement.
- **Nothing undoes it:** not a later answer from a server, and not a later record. A client keeps a revocation it has verified (`peers/<address>/revoke.sig`; `revoked.sig` for the box's own) and never removes it.
- **A box that holds its own revocation is finished, whatever any server answers.** It signs nothing more as that address: no pass, no mail and no certificate, so a send moves to `outbox/failed/`, and a drain, a renewal and every call that carries a pass are refused before anything is asked. A server that never saw the revocation would take it all: one that was down when it was published, one that answered `2xx` and kept nothing, or another server the box is pointed at. It still asks, keeps and publishes the record, which carry no pass. One it keeps that no longer verifies is a fault, and stops the same.
- **A client takes "revoked" only with the revocation in hand.** A `410 revoked` or a `403 sender_revoked` is a server's word. The read of the box, `GET /v1/<address>`, answers a revoked address `410 revoked` with its record in `record`; after any other call's, the client reads the box. A record that verifies makes it final: the message moves to `outbox/failed/`. Without one the call has failed and nothing more: the message stays in the outbox and no state changes. **What a server shows that does not verify counts as nothing shown.**
- **No answer is not "not revoked".** Where a client asks, about a sender in a drain (§5, check 8) or about a recipient before a post (§4.1), a box served with no revocation, `404 no_such_mailbox`, or `410 revoked` with nothing that verifies is an answer that it holds none, and the client goes on. Anything else stops the drain, a `2xx` whose body is not a box as §0b reads one among it, with the mail still on the server, or leaves the message in the outbox with nothing posted. That is the box's own server, the one its mail passes through: no answer from a revocation server changes nothing (below). A server can still answer falsely that it holds none: the limits, below.
- **When a client asks, and what it keeps.** It asks before every post, of the recipient, by the read of its box (§4.1); in a drain, once of each sender (§5, check 8); and whenever its owner says (`irongall revocation ask <link>`). Each time it reads the box from its own server, and then asks each revocation server it lists. **Whatever it has verified about an address, from any source and at any time, it keeps for good, and that is what a send and a read are checked against, with no call to anyone.** "None held" is kept nowhere. Nobody signs it, so it carries no time it holds until, and the next post asks again.

**The calls, with no pass needed:**
- **`PUT /v1/<address>/revocations`** with the record, and no pass. The server checks it as any client does and keeps it for good; a box at the address it marks revoked for good, and deletes its mail: `201 {}`. **Anything sent for a box already revoked is `410 revoked`,** answered from the record before any signature in the body is checked, since nothing could change it (a body that is no record, or names another address, is refused as such first); a client that published a revocation takes that `410` as done once the record its read of the box then carries verifies. The revocation of an address is counted against no box and in no daily count: what a server counts of it is its caller's address's alone (§8), which a revocation server does too, and past that count it is `429 rate_limited` with `Retry-After`, to send again then or from another address. A record whose document does not hash to the address is `400 identity_mismatch`; one that does not verify is `400 bad_revocation`. **A server keeps a record for an address it has no box for as well,** one never registered, deleted or forgotten, and holds a later registration of that address to it: `410 revoked` while the address is revoked, and no certificate the identity revoked (§6.3a). Keeping one for an address it holds nothing of is keeping a record for good, so a server may count that call as it counts a registration (§8).
- **The read of the box, `GET /v1/<address>`** (§4.1), carries what a mailbox server holds: a revoked address is `410 revoked` with the record in `record`, and a box served carries the revocation of its certificates. It takes the asking box's pass, or none. A server answers a revocation server's read too, `GET /v1/<address>/revocations` (below), which a box needs only of a server it lists as one.
- **A revoked box** answers `410 revoked` to every other call, its pass is taken nowhere, a send from it is `403 sender_revoked`, and its address can never be registered again (§3a). Its mail and its record are deleted; the revocation is kept for good.
- **No API answer may be kept by a cache:** every answer under `/v1/` carries `Cache-Control: no-store`. A `410` is cacheable unless it says otherwise (RFC 9110 §15.5.11), and an answer served again from a cache would be the server's word outliving the fact: a prekey since replaced, or a box since revoked.

**A record made in advance.** The statement has no date, so a box's owner can make the record at any time and keep it for the day the box is lost: `irongall revocation make` prints it, one line that is exactly the body of the call above, and publishes nothing, and `irongall revocation publish --record <file> <address>` publishes it later with no box and no key, only the file. **Whoever holds the record can end the address,** so it is kept somewhere other than the box: beside the identity it is lost with it and stolen with it. Neither client writes one unasked. Without a record, a lost identity cannot be revoked: the address stops taking mail when its prekey expires, and its correspondents are told the new address out of band.

**Who can revoke.** Whoever holds the identity key. For its owner that is the end of a stolen key. A thief holding it can revoke too, which ends the address and gains the thief nothing: the outcome the owner wanted. (A thief with the identity can also certify a working key of its own and read new mail until the owner revokes: the identity is the box.) `irongall revocation publish` takes the address written out in full, as its confirmation.

**Revocation servers.** A revocation is of an identity, and an identity belongs to no server. Nothing in an address, an identity document or a revocation names one (§2): a mailbox server is one route by which an address gets its mail, and a box's identity may one day be reached by another. So a revocation is not a fact about one mailbox server. It is kept where anyone can ask for it, whichever server carried the mail: at a **revocation server**, which is to revocations what a keyserver is to keys (`PRECEDENTS.md`, Part 2, § 3b).
- **What one is:** a server that answers two calls for any address: the `PUT` above, and `GET /v1/<address>/revocations` → `200` with the record it holds, or `404 not_revoked`, with no pass. It keeps a record once every part of it verifies, serves the record it holds to whoever names the address, and lists nothing. It is filled by upload, by a box's owner or by anyone holding the record.
- **Every mailbox server is one,** for any address and not only those it has boxes for. Its own boxes learn what it holds from the read of a box (§4.1) and ask it nothing more: the `GET` is for a box that lists it. A server that is only a revocation server, with no boxes, answers those two calls alone; the reference server has no such mode yet.
- **It signs nothing and is trusted for nothing.** It can keep a record back; it cannot make one. A record that verifies from any one source is final, so each revocation server a client asks can only add: a revocation has to be kept from every one of them to go unseen.
- **Its answers to a `PUT` are those above,** for an address with a box there or none. An identity of a key type it does not verify is `400 unsupported_key_type`. A revoked address takes nothing more (`410 revoked`), which a client that published takes as done once what that server then serves verifies, as from its own server.
- **Which ones a client asks is its owner's to say:** `$IRONGALL_REVOCATION_SERVERS`, or else the box's `revocation-servers` file (§1). A lookup tells a revocation server's operator which address its asker corresponds with. The box's own server knows that already, and another server does not: so **none is asked by default,** and one is asked only because the box's owner named it.
- **When it is asked:** wherever the box's own server is asked (before a post, §4.1; for each sender in a drain, §5; when its owner says), once that server has answered, with no pass, and for ten seconds at most.
- **What its answer does.** A record that verifies is kept, and is final. That it holds none is its word, and changes nothing. **And no answer from it changes nothing:** mail does not wait on a server it does not pass through, or every revocation server a box listed would be one more way to stop its mail. The client tells its owner which server gave no answer, and does not ask that one again in the same command.
- **Publishing.** `irongall revocation publish` and `irongall cert revoke-earlier` send their record to the box's own server and to each revocation server it lists, every one whatever the others answer: a mailbox server that refuses a revocation, or is down, does not keep it from the rest. The command fails, saying which server did not take the record, unless every one did, and the same command again is the cure. A revocation of certificates that is out at any server is kept by its box, and `irongall cert publish-revoked` sends it again.
- **More than one is allowed, and nothing in the protocol names or ranks one.** When someone else runs one, a client adds it to its list and nothing else changes: no new call, no new format, and nobody's permission.

**The limits.** A server can keep a revocation from a peer that has never seen it: it answers that it holds none, and nothing tells the peer otherwise. Asking before every post narrows that in time and no further: what a client was shown while a server answered truly, it holds after that server stops. What answers a server that hides a record from the first is a record from somewhere else: a revocation server, or the box's owner, out of band (`irongall revocation keep <file>`, which takes a revocation of the address, of its certificates, or both in one record). **What a revocation server adds has limits of its own.** A client goes on without its answer, so whoever can cut a client off from it has silenced it: it tells against a mailbox server that hides a record, and not against one that also controls its asker's network. And one run by the mailbox server's own operator is no witness against that operator: it is a second thing to break into, and a second source if the mailbox server is taken over. This protocol puts no bound on how long a revocation can go unseen by a peer whose every source hides it.

**6.3a Revoking certificates — the address goes on.** A working key can be taken without the identity (§2b). The identity then revokes every certificate it made up to and including a serial, and keeps its address: the box goes on under a new certificate. Built in both clients (`protocol/revokedcerts.go`, `client/revocation.go`, `sh/irongall.sh` § revocation) and in the server.
- **The statement is exact text:** `irongall-revoke-certs-v1`, LF, the address, LF, a serial, LF. The serial is an integer from 1 to 2^53 − 1, as a prekey's is (§2a), with no leading zero. Nothing else is one: no other line, no CR, no byte after the last LF.
- **The signature is the identity key's own,** in the namespace `irongall-revoke-certs-v1:<address>`, as a revocation of the address is (§6.3). A working key's signature is refused, so a certificate cannot revoke another, or itself.
- **It revokes every certificate of the address whose serial is at or below its own, and the highest stands.** Whoever holds one keeps the highest it has verified. One through a lower serial changes nothing, whenever it arrives, at a client or at a server, so a certificate once revoked is never taken again. The serial is its own order, and nothing else numbers it. It is how AWS, Entra ID and Firebase revoke what was issued before a point, with a serial where they use a time (`PRECEDENTS.md`, Part 2, § 3b).
- **What a revoked certificate loses,** at whoever has verified the revocation: a reader refuses mail signed under it, whenever it was signed (`certificate_revoked`); a sender refuses a prekey statement signed under it, at every post, of a new message or of one that waited (§4.5); a server takes no pass and no prekey statement under it, and answers a send to a box whose current statement is under it `409 prekey_expired`, since the cure is the same: the box publishes a new prekey, under a new certificate. And the box itself signs no mail under a certificate it holds revoked, whatever its server took: a send waits in the outbox until the box's renewal is taken, which is the remedy's window below.
- **It rides in the record of §6.3.** The read of a box carries it as `revoked_certificates` and `revoked_certificates_signature` (§4.1), and a revoked address's `record` beside the revocation; a revocation server's `GET /v1/<address>/revocations` → `{type, identity, revoked_certificates, revoked_certificates_signature}`, with `revocation_signature` too if the address itself is revoked; and `PUT` of the same, with no pass. One that is taken is `200 {}`, and so is one through the same serial again; one through a lower serial than the one held is `409 conflict`. Both are answered before the signature is checked: neither could change anything. Any other that does not verify is `400 bad_revocation`. A body may carry a revocation of the address beside it, which is kept whatever the other part holds: beside it, a revocation of certificates no higher than the one held changes nothing, and the answer is `201`. A box already revoked takes nothing more (`410 revoked`, §6.3). **A raise of it is the identity's act,** counted against the box with its renewals under a later certificate (§6.4, §8). A reader gets it with the one read of each sender's box it makes in a drain (§5, check 8), and a sender with the read of the recipient's before each post (§4.1).
- **A box makes no certificate its identity has revoked:** its next certificate is numbered above the highest serial it holds revoked as well, or its server or a revocation server it lists shows it revoked, asked at every renewal (§2b). So one through a serial far ahead of the clock, a slip of a digit, moves the box's numbers above it, and one through 2^53 − 1 leaves no certificate to make: the box cannot renew, as one whose certificate has that serial cannot. Ending an address is §6.3's.
- **What it costs its owner:** mail the box sent under a revoked certificate, and that its reader has not read yet, is refused with a thief's. Nobody can tell them apart, so it is sent again. Mail waiting in the box itself stays: its owner reads it after the renewal.
- **How long one is kept is not fixed here.** Every certificate it covers ends within 66 days of being made (§2b); a server or a client may keep it for good.
- **In the Go client:** `irongall cert revoke-earlier` reads the box once at its server, asks each revocation server it lists once, and keeps what verifies of the box's own revocation of its certificates. An answer it cannot use stops nothing: no answer, a served statement that does not verify, or one ordered before what the box published. It says so, and goes on from what the box knows, since the revocation still goes to whoever takes it (§6.3). It revokes every certificate below the number its clock gives, through the serial one below it, and publishes that to the box's server and to each revocation server it lists (§6.3): a serial is the time its certificate was made (§2b), so that covers every certificate made before it on any machine, whether this box knows of it or not, but for one a lost machine made while its clock read ahead of this one's and never published (§2b): a later run of the remedy covers that. Where one through a higher serial is held already, it signs and publishes that one again. A server that holds a higher one it did not show answers `409 conflict`, whatever another took: the client asks again, of that server too, and signs and publishes the higher one. Only then does it make the new prekey under a new working key and certificate, numbered one above the revocation, so the new certificate is never revoked as it is made, and it sends nothing an earlier renewal left, since whoever copied the box while one waited holds its working key. Then it sends the new prekey.
  - **The revocation goes out before the new prekey.** Once the box's server has taken it, the server takes no pass and no statement under the certificates it covers, the one the box was using among them, so whoever holds that working key can spend none of the box's calls; and the renewal that follows is not counted against the identity's certificates for the day, since the certificate it replaces is revoked (§6.4). Its own count is one of its own (§8), which no renewal spends. A refusal of the renewal with a `Retry-After` of at most a minute is waited out, and the renewal sent once more. Until the server takes the new prekey the box signs no mail, and once its server holds the revocation it takes none there either: a send to it is refused (`409 prekey_expired`, or by a sender that holds the revocation). Where only a revocation server took it, the box's server still takes mail for the box, and the pass of the certificate it was using, until it holds the revocation too: the command says which, and `irongall cert publish-revoked` sends it again. The client sends the waiting prekey again at its next `recv`, which renews at once while the box's own revocation covers the certificate it is using, and at `irongall prekey renew`. It says first whether the new prekey is published, then whether the revocation is at every server it was sent to.
  - **A clock that reads ahead numbers the revocation ahead,** as it numbers the certificate made with it: the box's later certificates are then one above it until the clock passes it, as after any certificate made while that clock read ahead (§2b).
- **Stock client:** `sh/irongall.sh` § revocation — `ig_certscheck` (the one check), `ig_certrevoked` (what is kept, checked again each time it is read), `ig_keepcerts` (the highest stands) and `ig_lookup`, which takes one with the record it asks for; `ig_renew` numbers a renewal above the box's own, as its server's answer and each revocation server it lists show it at every renewal, and `ig_seal` signs no mail under a certificate it holds revoked. It takes one from a server's answer only: `ig_revoked` keeps a revocation of an address from a file, and none of certificates. The script applies one and makes none: the statement is three lines of text that `ssh-keygen -Y sign` signs with the identity, as §6.3's is.
- **The same limit as §6.3:** a server can keep a revocation of certificates from a peer that has never seen it. A sender asks before every post (§4.1) and a reader for each sender in a drain, so it reaches whoever asks a server that shows it, and holds from then on whatever that server does later. A server that hides it from its first answer is not caught by asking it. What tells is a revocation server (§6.3), or the record from the box's owner, out of band.

**6.4 Prekey renewal — required, a new key every time.** The Go client renews in `irongall recv` once the current prekey is more than a day old, retrying a failed renewal hourly; `irongall prekey renew` renews at once. **A box's prekeys are valid for 33 days, or for the shorter lifetime its owner sets** (`prekey-lifetime`, §1; `irongall prekey lifetime`), from a day and two hours: the day `recv` waits to renew, an hour of slip for when it runs, and the hour of §0 for clocks, which a box leaves as the maker of the prekey. With a lifetime L, `recv` must run at least every L less a day and an hour, so a renewal comes with that hour of the prekey left and a sender whose clock a server takes still takes it; run less often, the prekey runs out, or so nearly that a sender whose clock is ahead refuses it, and senders are refused until the box renews. Under two days and an hour, a daily `recv` is not enough, and setting one says so. A lifetime set lower holds from the next `recv`, which renews a prekey made for longer, and spends a renewal that waited if it was made for longer too. Each client keeps when it signed a prekey (`.made`, §1), and times its renewals and its deletions by that record: a prekey with none is renewed at the next `recv`, and every retired key is kept while the newest has none. Each renewal is a new prekey, a new working key and a new certificate, under one number that the box's clock gives (§2b). Recovery needs only the identity (with `irongall.sh`, also the box's `identity.pub` and `address` files), and no record of the numbers the lost machine used.

**Stock client:** `sh/irongall.sh` § new prekey (at least monthly, by hand: the script never renews on its own) — `ig_rekey` (needs only the identity, so it also recovers a box that lost its prekeys or its working key), `ig_prune`.
- **`PUT /v1/<A>/prekey`** with `{prekey, prekey_signature}`, and `sender_key_types` if the box declares any (§2c), carrying a pass under the certificate that statement is signed under. **The authority is a statement ordered after the current one (§2b), signed by a working key the identity certified; no pass under the box's CURRENT certificate is needed.** That is the way back for a box that lost its prekeys or its working key — a restored machine, an ephemeral agent's second session — and it is how a box moves to a new certificate.
- **The server** answers an identical retry from its record, once its pass is checked, and reads where any other statement would stand in the order before checking its signature: one that could not be taken even if it verified is refused with no signature check, so a statement both out of order and badly signed is `409 conflict` or `401 certificate_not_current` by its order. It then verifies the statement as at registration (§3 steps 4, 6 and 7), and requires it to be ordered after the current one (§2b): under a certificate of a higher serial, at any prekey serial, or under the box's current certificate at a higher prekey serial (one that is not higher is `409 conflict`). A certificate of a lower serial, or another certificate of the current serial, is `401 certificate_not_current`, and one the identity has revoked (§6.3a) `401 certificate_revoked`. And it **refuses a key equal to the current one or to any live retired one** (`400 prekey_not_new`: "every prekey must be a NEW key"). The new prekey becomes current and its certificate the box's current one, so no pass under an older certificate is taken again, and the answer is `200 {}`. The declaration that came with the new prekey is the box's from then on (§2c). A deleted box is `404 no_such_mailbox`: it comes back by a registration (§3). **A server counts a box's renewals by UTC day, two ways:** those under the box's current certificate, which a holder of its working key can make, apart from those under a later certificate, which only its identity can (§2b). One while the box's current certificate is revoked is not counted: it replaces a certificate its identity revoked, and each raise of that revocation is counted instead (§6.3a), as Let's Encrypt exempts a renewal that names the certificate it replaces (`PRECEDENTS.md`, Part 2, § 4, Limits). So whoever took a working key cannot spend the identity's way back. Past either count, `429 renewals_spent` or `429 certificates_spent`, with the count in `limit`, until the next day; an identical retry is neither. The Go client makes a new certificate with every prekey, so each of its renewals is of the second kind. **The server keeps only a box's newest retired prekeys** (how many is a server setting), each until its `not_after`.
- **The owner** renews before `not_after` — the Go client daily, in `recv`; a monthly job with `irongall.sh`, to which the 33-day `not_after` leaves two days of slack — decrypts with every retained key (`-i new -i old`), and **deletes retired keys at their deletion time** (Terms): the Go client all but the newest, once they have been retired an hour and a drain has emptied the box; `irongall.sh` each at its `not_after` + 33 days (`ig_prune`, run by `ig_recv` and `ig_rekey`). Each deletes by its clock only once a server has taken a pass dated by it (§0): `recv` once its drain's list is answered, a renewal once it is taken. The working key before the new one is deleted at once: what it signed is signed.
- 🔑 **The forward-secrecy claim: forward secrecy for every box, bounded by how often it checks in, given a client that deletes retired keys.** Precisely, with the Go client: a message is unrecoverable from the box's keys by the box's second renewal after it arrived — about two days in a box received daily, about two months in one received monthly — and mail waiting on the server is exposed until the box fetches it, as in any scheme. With `irongall.sh`: at most 66 days after its prekey was published (33 + 33). A box that stops renewing keeps its expired prekey as its current one, so its last messages stay exposed until it renews. A box that no server takes a pass from keeps its retired keys past their deletion time too, until one does: it cannot tell its clock far ahead from a server that refuses it, and deletes by that clock no key that mail may wait for. After that a message is unrecoverable from the box's keys, by the operator, Cloudflare or a past breach. That needs a client that really deletes (the Go client and `ig_prune` do); a key kept in a backup, a synced folder or a secrets manager voids it. There is no per-message forward secrecy and no post-compromise healing of the encryption: v1 has no ratchet (decided on this repo's issue #31).
- **A serial is signed once.** A renewal the server did not take is sent again exactly as it was signed, which the server answers as an identical retry, and a new key is signed, at a later number, only once that statement has expired, was made for longer than the box's lifetime now allows or has no record of when it was made, is at or below a serial the box's identity has revoked (which every renewal asks for, §6.3a), is under a certificate that began less than an hour before the box's clock, so was made while the clock read ahead (§0), or another key type is wanted; the passed-over key is kept and deleted as a retired one. Signed again with a later `not_after`, the same key would stay in service for as long as a server refused renewals and kept the uploads: 40 days of failed renewals would give 39 statements for one key, the last good to day 73. So a key is encrypted to for at most its lifetime after it was signed, 33 days or less, whatever a server does. While a renewal waits, a box holds two working keys: the one the server knows it by, which signs its passes, and the one the waiting statement is signed with. The Go client's `recv` exits 3 after a renewal that failed, and `irongall status` reports one that is pending.
- **A box that does not renew** gets `409 prekey_expired` for every send to it once its prekey's `not_after` passes, and signs no mail of its own once its certificate has 33 days or less left (§2b). Its address and the mail already in it stay, and it can poll while its certificate lasts. Once that has ended, 65 days after its last renewal, the server takes no pass from it: a renewal is then the only call it can make, and the one that brings it back, while the server keeps the box. Past its record's expiry (§7) the server may forget it at any moment, and its read and its renewal are then `404 no_such_mailbox`. **Both clients then send the renewal as a registration** (§3), numbered above what the box published, which brings it back as a new box.
- **A compromised prekey:** renew it. A sender that has seen no newer serial can still be served the old statement until its `not_after` (§9). **That window is the lifetime, which a box that renews often may set short:** forward secrecy stays about two renewals, and what a shorter lifetime bounds is how long a stolen prekey, or a stale statement served to a sender new to the box, can be encrypted to.
- **A compromised working key:** `irongall cert revoke-earlier` (§6.3a). A renewal alone moves the server to the new certificate, so it takes no pass and no statement under the old one, and a sender that has seen the new one refuses a prekey under the old. Whatever prekey was published with the taken key, at any serial, the new certificate passes it (§2b). But whoever holds the taken key can hold a renewal alone back by spending the box's calls with its pass, and mail it signs still verifies at a recipient until the old certificate ends, if a server delivers it. The revocation of that certificate ends both: the server takes nothing under it, and a recipient that holds it refuses that mail.
- **The type can change at renewal** (post-quantum ↔ `--no-pq`) with no address change.
- **Tested** (§11; the two server settings only in the server's own tests): a renewal is a new key at a higher serial under a new certificate, and the pass from before it is refused; the server refuses `never`, a `not_after` more than 33 days and an hour ahead, a re-signed old key, a good statement that comes with no pass, a send naming no serial or a retired one, and a renewal past the day's limit, and keeps only its newest retired prekeys; the Go client renews a prekey more than a day old, retries a failed renewal hourly, and deletes all but the newest retired prekey once they have been retired an hour; each client registers a box its server forgot, at its renewal; senders refuse a rollback, an expired statement, and a prekey under a replaced certificate, and follow a box to a later certificate whatever serial they saw under the earlier one; `409 stale_prekey` re-encrypts the same envelope; a box with no prekeys, no working key and no pass recovers with the identity alone; after `ig_prune` deletes a retired key, its mail is unrecoverable.

**6.5 Accounts — adopt and leave.** A box may belong to one account at its server. **The protocol fixes only how a box joins and leaves one; what an account is for is the server's own:** it may lift a box's limits, bill for it, tag a box of its own, or not exist. A server with no accounts does not offer these routes, and a client reads the router's plain `404` as that (§0a). Nothing about the box's mail changes.
- **`PUT /v1/<A>/account`** (with the pass) with `{"key": "<adopt key>"}` → `200 {"account": "<id>"}`. One use of the key is spent, unless the box is already in that account. A box in another account moves. `irongall account adopt < <key file>`: the key is read on stdin, never from the command line, where `ps`, a shell's history and an agent's transcript keep it.
- **`DELETE /v1/<A>/account`** (with the pass) → `204`, in an account or not. `irongall account leave`. An account can drop a box from its side too.
- **The adopt key** is `iga1_` and then base64url without padding (RFC 4648 §5), at most 1,024 bytes in all. What it encodes is the server's own: a client holds a key to that form and reads nothing else of it. A key this server did not make, or one that is spent, expired or revoked, is `403 adopt_key_refused`.
- **An account id**, as the answer names it, is 1–32 of `a-z`, `0-9` and `-`.
- **What an account changes is the server's,** within §8's limits. irongall.dev's lift a box's limits, and today only its echo boxes' account lifts anything: no daily send limit, a larger size cap, and no budget of calls or of new mail. Over the sender's own cap, a send is refused before its body is read.

## 7. What the server stores, and for how long

How a server stores things is its own business. What it promises a client is this:

- **Per box:** the identity document, the state (§3a), the current prekey statement and its signature as it was sent, the serial of the certificate that statement is signed under (§2b), the sender key types it declared (§2c), the newest retired prekeys' type, `not_after` and key hash (only to refuse a key that comes back, §6.4), when the box was created, the account it is in, if any, and its ACL (§6.2). No private key, no token, no pass and no last-seen time (§3a).
- **Per address, box or none:** what its identity revoked, the signature that revoked the address and the highest revocation of its certificates with its signature, with the identity document, each kept for good and served to whoever asks (§6.3, §6.3a).
- **A box is kept until nothing valid for it is left.** A registration and every renewal keep it until the later of its certificate's end and its prekey's `not_after` plus the mail TTL, about 66 days on; a delete, until its newest certificate ends. Past that a server may forget it at any moment: it is then as if never registered (§3a), and its ACL, its account and its retired prekeys go with it.
- **Per message:** the ciphertext exactly as the send's body carried it, `from` (the box whose pass the send carried), the size, `received_at` and `expires_at`. Its id is the SHA-256 of the ciphertext. **No signature:** the message's is inside the ciphertext (§4.4).
- **A `200` or `201` to a send means the message was stored.** A failure before that answers 5xx, and the sender retries from its outbox (§4.5).
- **Mail expires 33 days less an hour after it was received**, read or not: the TTL, less the hour whoever makes a time-limited thing leaves (§0). A post's `sent_at` is its sender's clock at the post (§4.5), which a server takes up to an hour apart from its own, and a reader refuses mail 33 days after its `sent_at` by its own clock, so a reader whose clock a server takes refuses no message as `stale` while the server still serves it. `expires_at` is the authority: the server never serves a message past it.
- **Reading does not delete; an ack does** (§5.7). An ack deletes the ciphertext. The id, `from`, the size and the times stay as the dedupe record until `expires_at`, so the server's dedupe spans the TTL even after an ack (§4 step 6).
- **A delete** (§6.2) does to every message in the box what an ack does to one. **A revocation of the address** (§6.3) does the same, and the box's record goes with it; the revocation stays for good.
- **Lists are eventually consistent.** A list may show a just-acked message, or miss a just-stored one, for a moment. A fetch or an ack of a message that is gone answers `404 no_such_message`: treat it as gone (§5).
- **Bodies are served by the API itself, never by a redirect.**

## 8. Abuse levers

**What a server limits, and by how much, is that server's own.** No limit below is part of the wire: a server sets each as it chooses, and may add others. What a client must handle is how it meets one: a `429` with `Retry-After` (§13), unless a line says otherwise, which a client waits out and then retries, and the promises below, which every server keeps. A client needs no limit's number. The reference server documents its own with its code.

**The promises.**
- The same ciphertext posted again, of a send the server holds, is never refused by a quota; a budget may defer it (§4.5 step 6).
- A drain of a full box always completes: its pages are never refused, and its fetches may be paced, each `429 fetch_paced` saying when to go on (§5.1, §5.7), never stopped for good.
- A box's count is spent only by calls that showed its pass, by mail sent to it, and by its identity's raises of the revocation of certificates, which carry none (§6.3a). A count of an address is spent only by calls from it.
- The identity's acts are counted apart from what a working key can spend: a renewal under a later certificate apart from one under the current certificate, and one while the box's current certificate is revoked not at all (§6.4); a raise of the revocation of certificates on a count of its own (§6.3a); and the revocation of an address against no box (§6.3). So a holder of a taken working key cannot keep the identity from revoking that key's certificate, after which nothing under it is taken. What a server counts of a revocation is its caller's address's: one that does not verify as a check that failed, and one for an address the server holds nothing of as a registration.

**Who pays for a call.** A call with a box's pass is counted against that box. A call with none is counted against the IPv4 address or the **IPv6 /64** it comes from: every IPv6 end site holds at least a /64, so a per-address limit means nothing there. So both clients send their pass on the read of a box, which takes one (§4.1). A check that fails, or a call that names a box that does not exist, is counted against its address before it is checked, so a caller past its count is refused before the work: it may then be refused a box that exists, or a new pass of its own. No caller is exempt: a registered sender could otherwise try any number of addresses.

**The levers, as the reference server has them:**
1. **Address secrecy** — the primary defence (§2).
2. **Budgets: a burst at once, then a steady refill.** For a box: its polls (a list's `Retry-After`, §5.1, is the interval the server asks for; a list without a cursor is a poll, a `304` among them, and a later page is a continuation only while the box holds mail after its cursor and that cursor is the one it was handed last, with an allowance of its own sized so that a full box always drains); its repeat fetches (§5.7); its other calls, a send and a renewal among them; **the new mail it takes, from every sender together** (`429 mailbox_busy` to the sender; a retry spends none); and **the new mail it takes out**, its first fetch of each held message, which only its own calls spend (`429 fetch_paced` on the fetch; the drain stops, the rest waits, §5.7). A held message's ack is paid for by its receive; a fetch or an ack of an id the box does not hold is `404 no_such_message`, and one of its other calls. For an address: its registrations, and what it names that does not exist or does not verify; a read of what is public, a box or the link page, costs a server only its answer, and is not limited.
3. **Counts by UTC day,** each with its own code and the count in `limit`: a sender's sends (`429 sends_spent`), counted only for sends that carried its pass (§4.5 step 8); a box's renewals under its current certificate (`429 renewals_spent`); its identity's certificates, a renewal under a later certificate but for one while its current certificate is revoked (`429 certificates_spent`; §6.4); and its identity's raises of the revocation of certificates (`429 certificate_revocations_spent`; §6.3a). Every other limit is `429 rate_limited`. A lower send limit for a new box's first days (warm-up) is designed and not built.
4. **Unacked mail per (sender → box)** → `pair_full`, and a larger total per box → `mailbox_full`.
5. **Registrations per address** (§3 step 5), with which the reference server counts a revocation for an address it holds nothing of (§6.3). Proof of work is a lever a server may add; nothing in v1 carries it (§12).
6. **A box's ACL** (§6.2): `deny` first, then `allow`, checked before any count, so a send it refuses spends none. A list response carries metadata only (§5.1), so a box decides what to fetch.
7. **Accounts** (§6.5), at a server that has them: what lifts a box's volume, in what it sends, what it receives, what it takes out, and how large.

## 9. The operator's view

- **Sees:** addresses, identity documents, certificates and prekeys, who mails whom, each message's size to within a padding block (§4.3a), times, IPs, ciphertext, each box's passes, which account each box is in, and each box's ACL (§6.2): under an allow list, that names senders the box takes mail from that may never have written to it.
- **Never sees:** plaintext, private keys, age file keys, or any message's signature. **It holds nothing signed that says who wrote to whom** (§4.4): a pass names a box and a time, and no recipient and no message.
- **Can:** deny service; say a box is revoked when it is not, which a client checks and does not believe (§6.3); keep a box's revocation from a peer that has never seen it (§6.3, the limits); drop or delay mail (undetectable without receipts); delete mail; replay old mail (§5 defeats it); name another box as a message's sender (§5 defeats it); act as a box toward itself, which it could anyway; serve a STALE prekey to a sender — but only one the box's working key signed, and only until its `not_after`, 33 days after the box signed it. The serial guards stop even that for every sender that has seen a newer one. **It can also serve altered instructions** — which is why `GET /v1/<addr>` is to serve data and pointers only (§12), hints name client commands, and the stock script comes from this repo.
- **Cannot:** read mail, forge a sender, re-attribute a message to another sender, substitute keys, revoke a box, or alter a message undetected — **against a client that verifies AND gates**: the Go client here, or `irongall.sh` from this repo.
- **Cloudflare** terminates TLS for irongall.dev today: a detail of how that server is run, not of the protocol. It sees what the operator sees, a box's passes included, and a pass would let it act as that box at the server for the minutes it lasts. It cannot read or forge mail either.

## 10. The echo box

A separate CLIENT process that irongall.dev's operator runs — NOT the mailbox server — holding its own box keys. **Mail to it is readable by the operator by definition.** It replies with the decrypted plaintext plus diagnostics, signed by its own key. That lets an agent prove its whole loop end to end: keys → address → certify → register → sign → encrypt → send → poll → decrypt → verify → ack.
- **It is `21804ec172dd0dbdca3d9a6d461799130324b42fa708b3bb727e18e0bfc07e59`, post-quantum.** **A second echo box, `7f87929a91aa19bd2ca3a833d33d66c2b2f09dc83b9e2987a6af66d12a9c6b4b`, has an X25519-only prekey** (`--no-pq`), for senders on age 1.2, which cannot encrypt to the first. It is the same program with its own identity, and everything below holds for both; the Go client reaches either, so only the stock script's instructions name the second.
- **Its address is published deliberately** — the one exception to "no discovery of addresses". **It is fixed, permanent(ish), and hard-coded where clients look: `llms.txt`, `README.md` here, and a constant in the client (`client.EchoAddress`, `client.EchoAddressNoPQ`).** The address is the SHA-256 of its identity, so a client holding it checks whatever identity the server serves; the server cannot redirect it. **The server knows no aliases**: what is published is the 64-hex address itself, and a client sends to it as to any box.
- **Its identity key is kept and backed up**, since losing it means a new address in every published place. **Its prekeys live in memory only**, and it renews at every start: renewal needs only the identity (§6.4), and no prekey reaches a snapshot or backup.
- **It is in the account `echo`** (§6.5): no daily limit, and replies up to the largest cap.
- **No reply limit of its own**: it replies once per message, and every sender's own limits bound those. Its account lifts its daily send limit (§6.5); the server has no special case for it.
- **It is `cmd/irongall-echo` in this repo.** It answers only mail that passes every check, with a signed reply naming the checks, the sender, `msg_id`, `sent_at` and the ciphertext's SHA-256, then the body as JSON. **A refused message gets no reply**: a refusal does not say whether its sender was verified, so an answer could go to any address. Each start copies in the identity and publishes a new prekey (registering the box the first time), so mail sealed to the previous prekey is refused after a restart; a running box renews daily, as every Go-client box does (§6.4). A reply the server does not take is retried at each poll and dropped after an hour; one refused for good is dropped at once.

In the Go client, with a clock of its own for each machine: a box restored from its identity numbers its certificate above one the lost machine made and never published, and above every one an older record a server shows it hides, and its revocation covers them; mail the lost machine's key signs is then refused by a reader that holds the revocation, and delivered by one shown none. A box restored while the lost machine's last certificate is numbered ahead of the time, by a clock that read fast, renews and revokes at once. Not tested: a restore with a clock that reads behind what a server's older record hides, and two machines in one second.

A renewal the server refuses after it, for any reason, leaves the box signing no mail, and taking none at a server that holds the revocation, until its next drain sends the waiting renewal, and the command says when its own server did not take the revocation; one refused with a short `Retry-After` is sent again after it. - **Padding:** the script's arithmetic is the Go client's.
- **Revocation** (§6.3), in each client and with the two together, against a server that says revoked where nothing is, one that shows what is not a revocation (a working key's signature, another box's revocation, another box's signature with this box's document), one that hides a revocation it holds, and one that does not answer: a server's word leaves the message in the outbox and changes nothing; a revocation that verifies is kept, ends the message, refuses that address's waiting mail whenever it was signed, and is not asked about again; a record handed over is worth what a served one is; no answer stops a drain with the mail still on the server; and a record made in advance revokes with no box and no key.
- **Revocation servers** (§6.3), a second fake mailbox server standing for one beside the box's own, with each client and the two together, and the reference server's read of what it holds (in irongall-server): a revocation of an address or of certificates that the mailbox server hides from the first is shown by a revocation server, kept, and stops the send or refuses the mail, where a box that asks its own server alone posts and delivers; what a revocation server shows that does not verify counts as nothing; one that gives no answer, is gone or never answers changes nothing and is asked once in a command; with no answer from the box's own server no revocation server is asked; and a record is published at every server whatever the others answer, the command failing until each has it, and a server that holds the address revoked answers `410`, taken once what it then serves verifies.
- **Certificates revoked** (§6.3a), in each client and with the two together. A working key is taken and a prekey published with it at the highest serial there is: the box's next certificate passes it, and its senders follow. A revocation the identity signs is taken with no pass, one a working key signs is refused, and one through a lower serial than the one held is refused. A reader that holds the revocation refuses mail under a revoked certificate, the box's own unread mail with the thief's, and delivers mail under the next one; what it holds stands against a server that hides it or shows a lower one; and it encrypts to no prekey under a revoked certificate, though it saw no later one. A kept revocation that no longer verifies stops a drain. A box whose current certificate is revoked has no pass taken and gets no mail until it renews; a box whose own revocation runs far ahead of its clock renews above it, held or only served by its server, after a restore from the identity too, and one through the highest serial says it cannot renew. A box signs no mail under a certificate it holds revoked: the entry waits, and goes once the renewal is taken. A box that holds its own revocation of its address signs nothing more, here or at a server that never saw it, and still publishes it. A revocation of the address beside a lower revocation of certificates is kept. The vectors hold two revocations and one for each way one can be malformed, a NUL byte and the list of before 2026-10-14 among them.
- **A sender asks before it posts** (§4.1, §4.5), in each client and with the two together, against an operator that serves a box's senders the statement under the certificate its identity revoked. As the control, a sender shown no revocation takes that statement and posts what it sealed to it. A sender that has never read the box's mail asks first, keeps the revocation, and seals and posts nothing. What a box was shown once holds after the server hides it. With no answer about a recipient nothing is sealed or posted and the message waits, whatever code the lookup failed with. Neither client keeps a seal: the outbox holds the envelope alone. A message that waited while its recipient's identity revoked the certificate its first post was sealed under goes in one post, sealed under the certificate in use, by either client on a message the other wrote; one that waited while its recipient renewed goes under the renewal the sender recorded, whatever the server serves at the flush; and a post whose answer was lost is posted again and delivered once. A message whose recipient's address was revoked meanwhile is never posted. The Go client asks once for each recipient in a flush, and takes a revocation of certificates from a file.
- **Clocks** (§0), with a box's clock set apart from the server's, in each client: a box 9 minutes slow or 49 fast registers, renews, and exchanges mail with a box made that moment; one further off is refused and told what the server's clock reads beside its own; a box whose clock has gone back does not use its kept pass, and fetches nothing, where it would have refused and acked mail under a certificate that had not begun by that clock; an envelope dated ahead of its sender's clock waits in the outbox, sealed or not; a message delivered is not delivered again after the reader's clock steps back, within the hour by its replay set, after a drain the server refused by pruning nothing, and further by its floor; a message that waited 20 days in the outbox is dated at its post and read 30 days after it, and a retry posted 32 and a half days after a first copy that was delivered is read once, both in each client; a first prekey's own key outlives a registration whose answer was lost and a clock that then went back; the date on a server's answer is never set beside the clock but for a pass refused for its time, and never as an order; a drain at a clock 70 days ahead is refused at its pass and deletes no prekey, and the mail sealed to a retired one is delivered once the clock is right. The vectors hold each edge: a certificate that begins at `now` and one a second later, a prekey statement an hour past the 33 days and one a second longer, a `sent_at` an hour ahead and one a second more.
- **Transport** (§0), in each client and with the two holding one verdict on each URL: a server over `http` elsewhere is refused before anything is sent or made, as the box's own server and as a revocation server; a redirect of each status, to another port of the same host, reaches nothing there, from a list, a read before a send, a post or a revocation server, and a body a list would take behind a `3xx` is no answer.
- **The prekey lifetime** (§6.4), in each client and with the two holding one verdict on every `prekey-lifetime` file: a prekey ends its lifetime after its record, the default, the shortest and one between; a short-lived one is renewed once a day old, and not before; a lifetime set lower holds from the next `recv`; a prekey with no record is renewed, and the retired keys are kept; a file out of form signs nothing and is never read as the default; at the shortest lifetime, a box 9 minutes slow and a sender 49 fast still meet; at the cadence above, at the shortest lifetime and a longer one, with `recv` first a minute short of the day, a sender up to 49 minutes fast is never refused; and a renewal that waited, signed for 33 days, is spent once the lifetime is set lower, in each client.
- **The Go client against a forging server:** `client/forgery_test.go` and the tests beside it.

Also untested: `age-plugin-pq` against the server's stanza check, a `--no-pq` → PQ switch by renewal against the real server, OpenSSH 9.1–10.1 and 10.3p1–10.5p1 (run on 10.2p1, and on 10.6p1 with OpenSSL and without), age 1.3.0 and 1.3.1, macOS and BusyBox.

## 12. Specified and not built, or not yet specified

Each names the issue that tracks it. Those whose outcome could change the wire are in this repo's milestone `M1: protocol freeze`, with the other questions that could; each of those is settled, built or taken out of v1 before v1 is declared stable.

- **Identity key types beyond the two of §2:** not built. Wanted first are the forms a key in hardware presents: `sk-ecdsa-sha2-nistp256@openssh.com` (a FIDO token, a Mac's Secure Enclave through Apple's own SSH support) and `sk-ssh-ed25519@openssh.com`, with signing through `ssh-agent`, since such a key cannot be read from a file (this repo's issues #41 and #3). Each is an addition inside v1 (§0a), so neither issue is in the milestone.
- **Profile** (§6.2, #23): no route exists, and whether a box needs one at all is open. When built, it is an addition inside v1 (§0a): optional members of the read of a box (§4.1), and a route to write it. So #23 is not in the milestone. The lists specified beside it are built as the box's ACL (§6.2).
- **Proof of work at registration:** a lever a server may add, and nothing in v1 carries it (settled on #25). A client sends a solution only once a server asks for one, so a server that starts to ask changes nothing for any other call, and refuses a registration without one with a code and a hint that a v1 client prints (§13). Its scheme, how a server says what it asks, and that refusal are defined when one is built.
- **Also not built, and it does not change the wire:** a lower send limit for a new box's first days (§8), a server setting.

## 13. Errors, signalling, logging

- **Every error body is RFC 9457 Problem Details** (`application/problem+json`), in AEP-193's form: `{"type": "tag:irongall.dev,2026-10-17:errors/<code>", "title", "status", "detail", "code": "<code>", "hint"}`, and a member of its own for each value the error carries (the table below). **Every value a `detail` names is also one of those members**, of the type the table gives (AEP-193: "All dynamic variables found in error detail must also be present as additional properties").
- **A client needs nothing from `detail`, `hint` or `title`, and shows none of them.** They are a server's words, for a person reading the body: `detail` explains the error, and `hint` names the fix as a client command (`irongall prekey renew`), never a raw shell line a malicious server could alter. Whoever reads a client's output may be a model, and the server may be hostile (§9), so a client says what a code means in its own words, with the members it has checked to their types (`PRECEDENTS.md`, Part 2, § 3d). A client reads `code`, the members, `Retry-After` and `Date` on EVERY non-2xx (`ig_api`, §1).
- **`type` names the problem, and resolves to nothing:** a `tag:` URI (RFC 4151), the same at every server, which RFC 9457 §3.1.1 allows in place of a locator. Its date is a whole day, since RFC 4151 reads a month alone as its first day, which is before irongall.dev was registered.
- **A `code` is one of the closed list below, under the status the list gives it, beside a `type` that is its own** (`tag:irongall.dev,2026-10-17:errors/` and the code). A code a client does not know, one under another status, or one beside another `type`, is no code (a body that names its problem twice and disagrees names none): a client takes no branch on it and prints none of it, only the status, since any text can be made to fit a code's grammar. A member that breaks its type makes the body no answer at all (§0b).
- **A code names what a client does about the error.** One call that can fail for causes a client meets differently has a code for each; where the call itself tells them apart (a `too_large` on an ACL is entries, on a send bytes), one code serves.
- **401** carries `WWW-Authenticate`, the scheme a call must use, `irongall-pass` (§6.1b), followed by any auth-params a server adds (RFC 9110 §11.6.1).
- **A query parameter is read as a member is** (§0a): a server refuses one its call does not take, or one given twice, `400 bad_request`, naming it in `member`. A send takes its two serials (§4.5), and a list its `cursor` (§5.1); no other call takes one.
- **Every answer carries `Date`,** by the clock the server's checks read: that is how a refusal for a time says what that clock reads (§0).
- **An unknown route** gets the HTTP router's plain `404` or `405`, with no code: none in the map fits.
- **429** carries `Retry-After` (RFC 9110), so clients pace themselves; RFC 6585 defines 429. **It is delay-seconds, digits alone,** as on a `503`: RFC 9110 also allows an HTTP-date, which a client would read on a clock that may be off (§0), and which both clients read as no wait. The IETF RateLimit header fields are not in v1: they are a working group's draft, not an RFC, and a server may add them later as headers a v1 client ignores.
- **The same ciphertext posted again gets `200` + the original receipt**, never a quota error, whatever has changed at the recipient since (§4.5 step 6); a budget's 429 may defer it. The reference clients seal afresh at every post, so theirs is a new ciphertext (§4.5).

**The members:**

| Member | Type | Carried by |
|---|---|---|
| `limit` | integer | `too_large` (the most bytes a body or a ciphertext may hold, or entries an ACL); `sends_spent`, `renewals_spent`, `certificates_spent`, `certificate_revocations_spent` (the day's count) |
| `count` | integer | `mailbox_full`: how many messages the box holds, as its list counts them |
| `unacked`, `oldest_expires_at` | integer, time (§2a) | `pair_full`: how many messages from this sender the box holds unacked, and when the oldest expires |
| `version` | integer | `conflict` on an ACL (§6.2): the version held |
| `prekey_serial`, `certificate_serial` | integers | `stale_prekey`: the box's current prekey and certificate; `conflict` on a prekey: the serial a new one must be above; `certificate_not_current`: the current certificate's |
| `through` | integer | `conflict` on a revocation of certificates (§6.3a): the serial the one held runs through |
| `key_types` | strings | `unsupported_key_type`: the identity key types the server registers |
| `key_type` | string | `sender_key_type`: the sender's key type, which the box's client does not verify |
| `member` | string | `bad_request`: the request member or query parameter that is missing, unknown or given twice, or that holds a value its call does not take |

An integer is from 0 to 2^53 − 1 (§0b). A string member is shown by a client only once it has checked it: the Go client shows a key type it knows, and no other string member.

**The status map:**

| Status | Codes |
|---|---|
| **400** | `bad_request` (not a JSON text as §0b reads one, a missing field, an unknown field — §0a —, or a query parameter that is missing, unknown, given twice or not of its form, such as a send's `prekey_serial` or a list's `cursor`) · `bad_address` (not 64 lowercase hex) · `bad_encoding` (a byte field that is not base64 in its one encoding, §0b) · `identity_mismatch` (registration or revocation: the identity document does not hash to the address, or breaks its grammar) · `unsupported_key_type` (registration: a well-formed identity of a key type this protocol does not define, or that this server does not register, §3 step 4) · `bad_key` (an identity key that fails its type's key checks, a malformed or badly signed prekey statement or certificate, `never`) · `prekey_not_new` (a key equal to the current one or a live retired one: every prekey is a new key, §6.4) · `prekey_time` (at the server's clock, a certificate that began less than 10 minutes before it, or has ended, or a statement that has expired or ends more than 33 days and an hour ahead: the client's clock, nearly always, §0) · `not_age` · `wrong_recipient_type` (§4.5 step 7) · `bad_revocation` (a `PUT …/revocations` whose signature is not the identity's own over that address's statement, §6.3, or whose revocation of certificates is not one, §6.3a) |
| **401** | `unauthorized` (no pass, two `Authorization` lines, or a pass that is not this box's, or not for this server) · `pass_expired` (the pass, or the certificate it is under, is not valid at the server's clock: it has run out or runs out more than an hour ahead, or the certificate has not begun or has ended. Sign another and retry; refused again, this machine's clock is 10 minutes or more behind the server's, or more than 50 ahead, §0) · `certificate_not_current` (the pass, or a new statement, is under a certificate that is neither the box's current one nor above it, or the one on record does not verify: the client's working key is not the newest, as after a restore or a renewal on another machine, §6.4) · `certificate_revoked` (the pass, or a new statement, is under a certificate the box's identity revoked, §6.3a: renew under a new one) |
| **403** | `unknown_sender` (the box a send's or a lookup's pass names is not registered, or is deleted: "register your own box first") · `sender_revoked` (YOUR box is revoked) · `sender_not_allowed` (the box's ACL does not admit YOUR box, §6.2: final, so a client never posts that message again) · `sender_key_type` (the box's client does not verify identities of YOUR box's key type, §2c) · `adopt_key_refused` (an adopt key that is spent, expired, revoked or not ours, §6.5) |
| **404** | `no_such_mailbox` (never registered, deleted, or forgotten) · `no_such_message` (acked or expired: treat it as gone) · `not_revoked` (the read of what a server holds, `GET /v1/<address>/revocations`: it holds no revocation of this address, §6.3) |
| **409** | `conflict` (what is held is newer, or another: a replay that is not byte-identical — registration, a prekey at a serial no higher under the current certificate, a profile or ACL `version` not above the one held, a revocation of certificates through a serial no higher than the one held, a send whose id belongs to another sender) · `box_changed` (the box changed while the request was handled, as during an adopt, a leave, a renewal, an ACL or a revocation: send it again as it is) · `stale_prekey` (a newer prekey exists: re-fetch, re-encrypt the same envelope) · `prekey_expired` (the box's prekey has expired, or is under a certificate its identity revoked: its owner must renew) |
| **410** | `revoked` (the box you named is revoked, forever: a client asks for the revocation and checks it, §6.3) |
| **413** | `too_large` |
| **429** | `rate_limited` (calls past a limit, §8) · `sends_spent` · `renewals_spent` · `certificates_spent` · `certificate_revocations_spent` (the day's counts, §8) · `fetch_paced` (the new mail a box takes out, §5.7: the rest waits) · `refetch_spent` (a fetch of a message fetched before, §5.7) · `pair_full` · `mailbox_full` · `mailbox_busy` (the box has taken as much new mail as it takes for now, §8) — all with `Retry-After` |
| **503** | `unavailable`, with `Retry-After` — the server is not ready to answer, and says so rather than answer wrong |

- **The HTTP layer, in OpenAPI 3.1: `api/openapi.yaml`.** Every route, member, status and header this document gives, and nothing that protects a message: a client built from it alone checks nothing. This document governs where the two differ. No server serves it: `api/apitest` holds a server's answers to it in tests, the reference server's and this repo's fake's among them, and `api/`'s own tests hold it to `protocol/`'s codes and members (`PRECEDENTS.md`, Part 2, § 4, The API).
- **Logging**: the server's access logs never carry an address or a message id in the clear: each is replaced by a short hash of itself, which only someone already holding it can match. Passes and request bodies are never logged. Cloudflare's own logs DO see addresses in URLs. The remedy for a leaked address is a new box, and revocation (§6.3). Pasting a share URL into a hosted chat also leaks it, to transcripts and link unfurlers.
