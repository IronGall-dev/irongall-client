# PROTOCOL — irongall v1 (pre-stable)

**The irongall protocol, byte by byte: every step from key generation to ack, with the stock tool used at each step.** It says what a client must check, what a server must do, and what the server at irongall.dev promises. The code beside it implements it: `protocol/` and `sshsig/` (the formats and the signatures), `client/` and `cmd/irongall` (the Go client), `sh/irongall.sh` (the proof that a box of stock tools exchanges mail with a Go box) and `testdata/vectors/`.

- **Pre-stable.** Nothing here is final until v1 is declared stable (§0a). What has to be settled before that is this repo's issues in the milestone `M1: protocol freeze`.
- **The server is not in this repo.** irongall.dev runs one, written to this document. A client never has to trust it: everything that protects a message is checked by the client, and the tests here play a hostile server (`SECURITY.md` maps each claim to the tests that hold it). This document describes the server as a client meets it: its routes, its checks and its refusals. How it stores things is its own business, apart from what it promises (§7).
- **"Not built" is said where it applies.** A few parts are specified and not yet built, by the server, the clients or both. Each says so where it is described, and §12 lists them.
- **Limits are a server's settings, not the protocol's.** This document names each limit and says what it does, never its value: irongall.dev states the ones a client meets in ordinary use at `https://irongall.dev/llms.txt`. The protocol's own constants are written out (the 33 days of a prekey and of the mail's lifetime, the 65 and the 66 days of a certificate, the 10 minutes and the hour of a pass, the page of 50, the 16 MiB of a ciphertext).
- `[proposed]` marks a detail that is not decided.
- **Why each choice is the usual one is in `PRECEDENTS.md`:** every decision here beside the established systems and published standards that do the same, with their numbers, and irongall beside other messaging systems. This document keeps a mention where it helps at that step.
- **What a command prints, the order of a client's own steps, its retries and its words are the code's,** with the tests beside it: this document says what any implementation must do to interoperate and to be safe, and where the Go client goes beyond that, its code and `README.md` say so.

## 0. Primitives — all standard, nothing home-rolled

| Name | Role | Spec |
|---|---|---|
| age v1 | encryption to the box's PREKEY: post-quantum `mlkem768x25519` (hybrid ML-KEM-768 + X25519, age ≥ 1.3) by default, or X25519 only (`--no-pq`); HKDF-SHA-256, ChaCha20-Poly1305, HMAC-SHA-256 | C2SP age spec |
| Ed25519 | the WORKING KEY, which signs prekeys, mail, profiles and passes; and the box IDENTITY that certifies it and signs a revocation, in the one identity key type every client makes and verifies (§2) | RFC 8032 |
| ECDSA P-256 | an IDENTITY of the optional key type `ecdsa-sha2-nistp256` (§2): it signs what any identity signs, certificates and a revocation | FIPS 186-5, RFC 5656 |
| SSHSIG | signature container: the key's signature over SHA-512(message), namespaced | OpenSSH `PROTOCOL.sshsig` |
| SSH public key text | `<key type> <base64 wire key>`: `ssh-ed25519`, or `ecdsa-sha2-nistp256` | RFC 4253 §6.6, RFC 8709, RFC 5656 |
| OpenSSH certificate | the identity's word for a working key (§2b) | `draft-ietf-sshm-cert`, OpenSSH's format (its `PROTOCOL.certkeys` until 2025) |
| SHA-256 | address = hash of the identity document; message id | FIPS 180-4 |
| UUID | the envelope's `msg_id`, random (version 4) | RFC 9562 |

**Stock tools suffice:** every format here is one that `age`, `ssh-keygen`, `jq` and `sha256sum` read and write, every call is one `curl` makes, and each step below names the tool. `sh/irongall.sh` is the proof, and its header names the versions it needs. **The Go client `irongall`, in this repo, does all of it.**
- **age ≥ 1.3 is needed to OWN a post-quantum box** (age-plugin-pq has no key generation) **and to send to one** (or age-plugin-pq). An older age reaches a `--no-pq` box only.

**Paths:** every API path is under `/v1/`, and the discovery documents (`/`, `/llms.txt`) sit at the root. Every route, member, status and header is also described in OpenAPI, in `api/openapi.yaml` (§13).

**Transport:** a client calls its server over `https` only, but for a server on its own machine, named by its address in `127.0.0.0/8` or as `[::1]`, which it may call over `http`; the name `localhost` is not one, since a resolver says what it is (RFC 8252 §8.3). A URL of any other form is refused before anything is sent, and nothing allows more. A call to a server at a loopback address, or named `localhost`, goes through no proxy, whatever the environment names. **It follows no redirect:** the API redirects nowhere, so a `3xx` is an answer that is not the API's, taken as no answer. A pass is a bearer credential for the minutes it has left (§6.1b), and a lookup names the address it asks about (§6.3): neither crosses a network in the clear (RFC 6750 §5.3), and neither is sent anywhere a server points.

**Keyed hashing is HMAC or HKDF only, never `hash(secret ‖ …)`.** SHA-256 and SHA-512 allow length extension, which breaks exactly that construction. Plain SHA-256 appears here only over PUBLIC inputs — the identity document, the ciphertext, the proof-of-work input — where extension gives an attacker nothing, and it stays: it is what Signal, TLS 1.3, MLS, age, Certificate Transparency and Git's new object format use, and `sha256sum` is on every machine.

**SSHSIG hash:** every verification in this protocol — prekeys, messages, passes, profiles, revocations — accepts `sha512` or `sha256`, the two the SSHSIG spec allows. `ssh-keygen` writes `sha512`.

**Clocks: every check is exact at the clock of whoever makes it, and whoever makes a time-limited thing leaves an hour of room.** A box's clock is expected to be synced (NTP); the hour is for one that is not quite. It is how a certificate is checked in X.509 and OpenSSH, with the hour Let's Encrypt dates its certificates back by (`PRECEDENTS.md` § Clocks).

- **The hour is the pass's** (§6.1b). A client asks for 10 minutes and a server takes up to 60, so a server takes a new pass from a box whose clock is less than 10 minutes behind its own, or up to 50 ahead, and no two such clocks are an hour apart when each shows a pass.
- **What leaves the room.** A certificate starts an hour before it is made, and is asked for a day under its ceiling (§2b). A server takes a prekey statement that ends up to an hour past the 33 days a client asks for (§2a), and keeps mail an hour and two minutes less than the 33 days a reader takes it for, the two minutes for a post's own time (§7). A box's renewal leaves an hour for its own calls beside the hour for clocks (§6.4). A reader takes a `sent_at` up to an hour ahead of its own clock (§5).
- **What has none.** A prekey past its `not_after`, a certificate past its end, a pass that has run out, a `sent_at` older than 33 days: each is refused to the second.
- **A box whose clock is further off is stopped before it fetches any mail it would judge by that clock, prunes its replay set by it, or deletes a prekey by it** (§5 check 9, §6.4). In most cases at its pass, with `401 pass_expired`. A box whose clock is more than 50 minutes ahead when it makes a certificate is stopped a step earlier, when the server checks that certificate (`400 prekey_time`): a server takes one only once it has begun by the clock of every box it takes, 10 minutes before its own, so every certificate a server takes has begun for every reader it takes. A box whose clock has gone back past the start of its own certificate is stopped by its own check of it. **Keys are deleted, and the replay set pruned, by the date of the pass the server took, its `not_after` less ten minutes, never by a reading of the clock** (§5 check 9, §6.4): that date is the reading the server checked, so a clock that jumps or steps back while a call is in flight deletes nothing by where it went.
- **A pass or a statement refused for its time is nearly always a clock,** and a new pass does not cure it. The server dates every answer by the clock its checks read (the `Date` header), and a client sets that date beside what its own clock reads. 🛑 **Those are the server's word, said as that, and a client's own words never tell its reader to set a clock by them:** they point to a time source the reader trusts. A box checks everything against its own clock, and a clock set by a server's lie would make an ended certificate valid again and stale mail fresh.
- **A client does not use a kept pass that has more than 10 minutes left:** it signs none that long, so its clock has gone back since it signed that one. The pass it signs instead is dated by the clock as it is, which is what stops it.
- **A client dates each post last, once it has read the recipient's box (§4.5), and never before its entry was written.** An entry dated ahead of the clock at its dating was written while the clock read ahead of where it reads now, or the clock went back while the box was read, and the outbox counts its 33 days from when an entry was written, so it waits there until the clock passes that time. Every copy of a message is then dated within 33 days of every other (§4.5). So a post's `sent_at` is its sender's clock when the server checks its pass, less only the post's seal and the second its dating truncates, for which the server's keep of mail leaves two minutes (§7); the request itself is bounded by its pass.
- **A client does not use a kept certificate that began less than an hour before its clock,** as at an `init` or a renewal a server refused: it was made while the clock read ahead of where it reads now, and a reader whose clock the server takes may not have reached its start. The statement and working key made with it are made again, by the clock as it is, for the same prekey at `init`, and at a later number at a renewal (§6.4).
- **What this does not cover.** The window is checked when a pass is first shown, and a server may remember that pass for its ten minutes. A clock that moves by minutes inside those ten, or goes back by more than an hour in the middle of a drain, can still put a `sent_at` past a reader's hour, or have a reader judge mail by a clock no server took, and that reader refuses the message. It is a verdict like any other: the message is quarantined with what the checks found, the reader's clock among them, so its owner can see whose clock it was, and nothing is held for a clock to catch up (§5, "The verdict"; `PRECEDENTS.md` § Clocks). Each case needs a clock that is already wrong.

## 0a. Compatibility and versioning

🔑 **Pre-stable: nothing is final until v1 is declared stable.** Until then the live service is the test bed, and fields, formats and what is required may still change. The rules below bind from that declaration:
- **A server REFUSES a member it does not know in what it is sent** (`400 bad_request`, with the member in its `member`, §13).
- **Every other reader IGNORES one:** a client in a server's answer, a box in an envelope (§4.2), and whoever a later version has receive what a server sends. §0b's rules still hold in it. The envelope's `v` changes only for a breaking change, and a receiver rejects a `v` it does not know.
- **Signed statements match their format EXACTLY** (identity document, prekey statement, pass, revocation, revocation of certificates). A new format gets a new tag. Namespaces are versioned independently.
- **New v1 fields are added as optional.**
- **A server may add a route inside v1.** A client reads the router's plain `404` or `405`, with no code, as a route that server does not offer (§13), and a `404` with a code as that code.
- **`irongall-revoke-v1` stays valid forever**, so a revocation signed in advance keeps working.
- **A new identity key type is an addition inside v1.** The identity document has one form for every key type (§2), so a type defined later takes no new tag: a client that does not verify it refuses it with a code of its own, and each box declares the types its client verifies (§2c). A post-quantum signature key would come this way, as a key type.
- **A new prekey type is an addition inside v1** in the same way. A prekey statement's key is an age recipient (§2a), so a type defined later takes no new tag: a sender that cannot encrypt to it refuses the statement as `unsupported_prekey_type`, never as a statement that does not verify.

**What v1 fixes once it is stamped, and where each can grow inside it** (every such format had one look before the freeze: this repo's issue #39):

| Fixed | Grows by |
|---|---|
| The signed statements, byte for byte: the identity document (§2), the prekey statement (§2a), the pass (§6.1b), the revocation (§6.3), the revocation of certificates (§6.3a); a certificate's type, key id, principal and validity (§2b) | a new format under a new tag; a new identity or prekey key type (above); a certificate's extension, which a reader ignores (§2b) |
| The namespaces, `irongall-<purpose>-v1:<address>` | a new purpose |
| A signature's form, and its bound for each key type (§3) | a new key type, with a bound of its own |
| What is encrypted: the envelope's line, the signature block, the padding (§4.4) | the envelope's optional members (§4.2); its `v` changes only for a breaking change |
| JSON as §0b reads it; a byte member's one encoding; a message's ciphertext as the body itself (§4.5) | nothing |
| The largest message: a ciphertext of at most 16 MiB, which every reader takes and no server's cap passes (§4.5) | a new version of the protocol |
| The routes, methods and statuses, the codes (§13), and every member a request or an answer has | a route; an optional member; a code, which a client that lacks it reads by its status |
| The pass's scheme and its three parameters (§6.1b) | a new scheme |
| An error's `type`, `tag:irongall.dev,2026-10-17:errors/<code>` (§13); the link, `https://<server>/to/<address>` (§2) | a new code |

## 0b. JSON — one way to read it

**Every JSON text the protocol carries is read by one set of rules, by the server and both clients:** a request's body, a server's answer, the envelope (§4.2) with the sender's body in it, a revocation record (§6.3), and what a client keeps of one. A text that breaks one is refused whole: a request with `400 bad_request` (`bad_encoding` for a byte field), an answer as no answer, an envelope as `bad_envelope`. So no two readers take different values from one text: RFC 7493 §3 has a security protocol's receiver "not trust" a text that breaks its rules.
- **It is I-JSON (RFC 7493):** UTF-8, so no code point above U+10FFFF; no member named twice in any object, after its escapes are read; and no surrogate or Unicode noncharacter in a name or a string, written or escaped.
- **It is one object, and nothing follows it but whitespace,** which in JSON is space, tab, LF and CR (RFC 8259 §2). **No byte-order mark** (RFC 8259 §8.1 lets a parser refuse one).
- **Names match exactly, case and all** (RFC 8259 §8.3): `"Identity"` is not `identity`, and a member a reader does not know.
- **Every number is in JSON's own grammar** (RFC 8259 §6): no `NaN`, `Infinity`, leading zero, `+` or bare `.`.
- **No number is of greater magnitude than a binary64 holds,** I-JSON's "for example, 1E400" (RFC 7493 §2.2): Go's `strconv`, Python's `json` and JavaScript's `JSON.parse` read one as infinity, and jq writes `1e1000000000` as the largest binary64. A nonzero number too small for binary64 reads as zero to a binary64 reader, and is taken.
- **It nests at most 32 deep,** objects and arrays counted together, the outermost as one. RFC 8259 §9 lets a parser set that limit. 32 is well under every parser's own (jq 1.7 refuses 257, and Go's 10,001; both measured), so no reader's parser refuses what another takes.
- **A member the protocol defines is of its type, and null is the same as leaving it out,** as the protobuf JSON mapping reads null. The one exception is the envelope's `body`, which is required and whose null is a value (§4.2). **An integer member** (the envelope's `v`, a serial, a count, a size, seconds) is written as an integer, in digits alone, from 0 to 2^53 − 1, as typed JSON decoders read one (`PRECEDENTS.md`), so `1.0` and `1e0` are no integer: RFC 7493 §2.2 has no reader hold a larger one exactly, and jq and JavaScript do not. So a serial is at most 2^53 − 1 wherever it is written (§2a, §2b, §6.3a).
- **A byte member is standard base64 in its one encoding** (RFC 4648 §3): padded, with nothing outside the alphabet, a line break included, and the unused bits of its last character zero. Encoding the bytes again gives the text back, so a field has one text.
- **A member the reader does not know:** a server refuses one in what it is sent, and every other reader ignores one (§0a), RFC 7493 §4.2's "must-ignore" policy. The rules above still hold in it.

**The vectors** are `testdata/vectors/json/` (a text by itself) and `answer/` (a whole answer of each kind), each named for its verdict.

## Terms

- **Address / `H`:** the box identity — the SHA-256 of its identity document (§2). As text, 64 lowercase hex characters; inside MACs, the 32 raw bytes. `H_A` is the sender, `H_B` the recipient. **One identity key ⇔ exactly one address.**
- **Box:** a mailbox. In this file it never means a machine.
- **Identity document `D`:** the two-line text whose SHA-256 is the address (§2). Immutable. The API member carrying it is named `identity`.
- **Identity key:** the box's signing key, an Ed25519 key unless the box was made on another key type (§2), and its final authority. It signs certificates for the box's working keys and the box's revocations, of its address (§6.3) and of its certificates (§6.3a), and nothing else, so it need not be where the agent runs. **Working key:** an Ed25519 key the identity certifies, for at most 66 days (§2b). It signs everything the box says: its prekey statements, its mail and its passes. **Prekey:** the box's current age encryption key, published as a **prekey statement** signed by the working key (§2a). It is renewed at least every 33 days, with a new key each time; the address never changes.
- **Pass:** a short statement a box signs for itself to prove to the server who is calling: its address, the server's name, and a time ten minutes on (§6.1b). It replaces a bearer token: the server issues nothing and stores nothing for it.
- **"In system":** registered and active. Only those boxes can send.
- **Box states:** `active` → `revoked` (permanent). A box nothing valid is left for is forgotten. The transitions are §3a's table.
- **A renewal** is a new PREKEY, published under a new working key and certificate (`irongall prekey renew`, `PUT …/prekey`, §6.4).
- **Last-use time of a prekey** = its renewal. Every send names the serial it used, and an honest server answers one naming a retired serial with `409 stale_prekey` (§4 step 7), so mail encrypted to a prekey reaches the server only while it is current. Senders also refuse an expired prekey.
- **Deletion time of a retired prekey:** at the latest `not_after` + the 33-day TTL, when all mail encrypted to it has expired. A client may delete earlier all but the newest retired prekey, after a drain that empties the box, by a list the server took under a pass dated more than an hour after the newest retired one was made, by which time all of them had been retired for an hour (the hour covers a send in progress as a renewal lands); the Go client does. Each deletes by its clock only once a server has taken a pass dated by that clock, and by that pass's date, never by a reading of the clock (§0): the drain's list's pass, or a renewal's. A box whose clock reads far ahead is stopped at its pass, one whose clock jumps or steps back while the call is in flight deletes nothing by where it went, and neither deletes a key that mail may wait for. **Mail encrypted to it is unrecoverable from the box's keys after that** — THE forward-secrecy bound, stated once (§6.4). An early deletion rests on the server refusing a send to a retired serial: mail a server takes for one anyway may be mail the box can no longer read.
- **The live prekey** is the current one: the server checks a message's stanza TYPE against its type (§4 step 7). The server keeps the newest retired prekeys' key hashes (how many is a server setting) only to refuse a key that comes back.

## 1. Keys and the stock client — client side

**A box's keys and state live in a directory of its own that only its owner can read (0700), `${XDG_CONFIG_HOME:-~/.config}/irongall/<box>`, never the working directory** — for a coding agent the working directory is a git repository, and `git add -A` would commit the keys. The directory ignores itself, with a `.gitignore` of `*`. The Go client's layout is at the top of `client/doc.go`, and what names a box is `README.md`'s.

- **The identity key makes the address** (§2): a plain OpenSSH key file, with no passphrase and no seed derivation, so `ssh-keygen` reads it. **It is backed up**: losing it loses the address (§6.3). It signs certificates and revocations only (§2b).
- 🛑 **Prekeys are NEVER backed up, NEVER synced, never stored where old versions survive (a secrets manager, git, snapshots), and never derived from a seed:** a prekey that survives its deletion voids forward secrecy (§6.4). Losing a machine loses its prekeys: the box publishes a new one with the identity alone (§6.4). Working keys are not backed up either: a restored box makes new ones.
- **What a client keeps, whatever its layout,** each by the rule of its section: a peer's identity, pinned once something it signed has verified (§4.1, §5); the highest prekey serial and certificate serial it has seen on each peer's statements (§2a, §2b); every revocation it has verified, never removed (§6.3, §6.3a); the replay set and its floor (§5 check 9); when it signed each prekey, by which it times its renewals and deletions, never by the statement's `not_after` (§6.4); and the outbox's envelopes, as written (§4.5).
- **The stock client is `sh/irongall.sh` in this repo:** the proof that a box of stock tools exchanges mail with a Go box, on a box of its own (`AGENTS.md` § The shell client). 🔑 **Get it from this repo, pinned by commit — never from text a server serves.**

## 2. Identity document → address

The document `D` is exactly two LF-terminated ASCII lines: the tag, then one SSH public key as `<key type> <base64 of the wire key>`, with no comment, no CR, and nothing after the final `\n`:

```
irongall-v1
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI<43 chars>
```

**The key is of a type this protocol defines, in its one encoding, and passes that type's key checks.** Its one encoding is the wire key as OpenSSH writes it back once read: a key of the type line 2 names that, parsed and written again, gives the same bytes, so one key has one document, and so one address. The rule is the same for every type, and no type has a pattern of its own.

| Key type | Document | What fixes its one encoding | Key checks |
|---|---|---|---|
| `ssh-ed25519` | 93 bytes | the key's length, 32 (RFC 8709 §4) | a canonical point that is not of small order |
| `ecdsa-sha2-nistp256` | 173 bytes | the curve's name, `nistp256`, and an uncompressed point on the curve, the one form OpenSSH reads (RFC 5656 §3.1 lets a point be compressed) | none beyond the point: on the curve, not the point at infinity, each coordinate below the field's size, as OpenSSH from 10.3p1 and `golang.org/x/crypto/ssh` read one |

- 🔑 **`ssh-ed25519` is the one type every client verifies, and the one a client makes.** Every other type is optional: a client verifies it or not, a server registers it or not (§3), and a box of an optional type can be written to, and heard from, only by a box whose client verifies that type (§2c). No client makes one by default.
- **The identity certifies a working key and signs nothing else but a revocation (§2b).** So an identity's key type is the type of a key that signs a certificate now and then and a revocation (§6.3, §6.3a), and never mail: everything else a box signs is its working key's, which is Ed25519.
- **Why Ed25519's key checks are explicit, and P-256 has none of its own.** Go's `crypto/ed25519` takes small-order and non-canonical Ed25519 keys, as OpenSSH's own code did before 10.6p1 (from 10.4p1 it refuses the neutral point alone, `7763a38b`), so a client checks for them itself (§3 step 4). A P-256 key is held to what OpenSSH from 10.3p1 and `golang.org/x/crypto/ssh` hold it to, a point read as the table says, which the library checks as it reads the key (decided on this repo's issue #354). OpenSSH up to 10.2p1 also refused a point with a coordinate of 128 bits or fewer, or of n − 1 or more, where n is the group's order (`sshkey_ec_validate_public`), which 10.3p1 dropped as "not needed" (openssh-portable `9bea0818`): only a key made to have one meets it, and a script on such a build refuses one, a known variance (§3).
- **Why the key as written back.** OpenSSH names a key by the blob it builds again from the key it read (its fingerprint), and SSHFP and Git's allowed signers name one by that: so a type's or a curve's name ending in a NUL, which `ssh-keygen` reads as the same key, is not a second document for it (`identity/type-name-ending-in-nul`, `identity/p256-curve-name-ending-in-nul`). A type is added with its name, its key checks, its signature bound and its vectors, and nothing is written by hand from its wire format (`PRECEDENTS.md`, Part 2, § 4, the identity's row).
- **The form holds for every key type, defined here or not:** the tag line; a key type's name (RFC 4251 §6: printable ASCII with no comma, at most 64 characters); one space; the base64, in its one encoding, of an SSH wire key, which begins with that same name; LF. So a client can tell a document of a type it does not verify from something that is no document. **The first has a refusal of its own, `unsupported_key_type` (§5), and is never called malformed:** a document that does not hash to its address, or that breaks its form, points at tampering, and one of a type this client lacks does not. It is also how a type is added to v1 with no new tag (§0a).

- **Address = lowercase hex SHA-256 of `D`, 64 chars**: `sha256sum < identity.doc | cut -c1-64`. **It is shared as the link `https://irongall.dev/to/<64 hex>`**: the server serves a page there for exactly 64 lowercase hex characters, 404 otherwise, for people and for agents without a client: fixed text, the hex and the server's own link to it, never text a box supplied, sent with `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex`. A query on the link is ignored. A client given a link takes the address from its path and never fetches the page, and refuses a link to any server but its own. It is not `/v1/<addr>`, which is the API's read of the box (§4.1), and it carries no version.
- There is no checksum: a mangled address simply hits no box (`no_such_mailbox`).
- The version is line 1 of `D`. Another deployment of this protocol picks its own tag, and so its own address space.
- **It commits to the identity ONLY**, so renewing or re-typing the encryption key never changes it (§6.4).
- **The canonical form is lowercase hex.** Clients MUST use lowercase in `from`: the recipient compares the inner `from` (§4.2) with the verified signer as exact strings, and every SSHSIG namespace is an exact signed string. An address in a URL path is lowercase too: the server answers one in capitals `400 bad_address`, so that one box has one URL.

🔑 **An address is a SEND CAPABILITY — keeping it private is the real DoS defence.** Mailing a box hands it your address (it is your `from`), so it can mail you back.

## 2a. Prekey statement — the encryption key, signed by the working key

Exactly five LF-terminated lines, then signed by the box's working key, under its certificate (§2b), with namespace `irongall-prekey-v1:<A>`:

```
irongall-prekey-v1
<A — the box's own address>
<serial — a decimal integer, no leading zero, from 1 to 2^53 − 1 (9007199254740991, the most a JSON number holds exactly: an answer names one as a number, §13, §0b); strictly increasing under one certificate (a box's statements are ordered by certificate first: §2b); a client gives each the serial of the certificate it makes with it>
<age1pq1… (post-quantum, default) | age1… (X25519 only, `--no-pq`)>
<not_after — RFC 3339 UTC to the second, YYYY-MM-DDTHH:MM:SSZ>
```

- 🔑 **Every statement expires, and every renewal is a NEW key. A client signs one to end 33 days after it is made, or sooner, down to a day and three hours, when its owner sets a shorter lifetime (§6.4); a server takes one that ends at most 33 days and an hour from the server's own now.** The hour is the room of §0: without it, a client whose clock is a second ahead of the server's asks for more than the ceiling. 33 = the longest month, plus the day a renewal may wait, plus a day of slip, so a box received at least monthly never lapses (§6.4). `never` is not a valid `not_after`. This is TUF's mandatory expiry: it bounds how long a malicious operator can freeze a sender on an old statement.
- The key type IS the box's type: post-quantum by default, `--no-pq` (X25519 only) by choice. It can switch at any renewal (§6.4).
- **The key's type is its Bech32 human-readable part** (BIP 173, as age writes a recipient: lowercase, its checksum good, its data whole bytes): `age1pq` or `age`. A type defined later is an addition inside v1 (§0a). A sender holds a statement to every other rule first, and refuses one good in every way whose key is a well-formed age recipient of a type it lacks, a human-readable part that begins `age` and is neither of those, as `unsupported_prekey_type`: nothing is sealed or posted, and it is never refused as a statement that does not verify (`prekey/unsupported-type`).
- **Senders keep the highest `serial` they have seen**, and refuse a lower one. That is the rollback guard. They keep the highest certificate serial they have seen on a box's statements too, and refuse a lower (§2b).
- **A statement never outlives the certificate it is signed under:** its `not_after` is at most the certificate's end, and a verifier refuses one that is later.
- **Senders re-fetch at `not_after`**, or when a send gets `409 stale_prekey` (§4).
- **A prekey past its `not_after`: senders MUST refuse to encrypt**, and the server refuses the send with `409 prekey_expired` ("the box must publish a new prekey"). **No grace**: a grace only widens the time an expired, possibly deleted or leaked, prekey is used. The room for a clock that is off is at the other end, in what a server takes when the statement is published (§0). Nothing else about the box changes (§6.4).

## 2b. The working key and its certificate

🔑 **The identity signs certificates and revocations (§6.3, §6.3a), and nothing else. Every other signature a box makes is its working key's** (this repo's issue #30). So the identity key need not be where the agent runs: by default a client keeps both keys in the box and renews the certificate itself, and a box whose identity is kept elsewhere is handed a certificate.

A certificate is an OpenSSH user certificate, exactly as `ssh-keygen` writes it:

```sh
ssh-keygen -s identity -I irongall-cert-v1 -n "$A" -z "$SERIAL" -V -1h:+65d -O clear work.pub
```

| Field | Rule |
|---|---|
| Type | a user certificate |
| Certified key | the working key: `ssh-ed25519`, held to that type's key checks (§2), and never the identity key |
| Serial | from 1 to 2^53 − 1, as a prekey's. The identity gives each certificate a higher one than the last, and a client takes it from its clock to do so; who holds a certificate to that order is below |
| Key id | exactly `irongall-cert-v1` |
| Principals | exactly one: the box's address, lowercase |
| Validity | `valid after` ≤ now < `valid before` ≤ now + 66 days, in whole seconds |
| Critical options | none. One a verifier does not know is refused (draft-ietf-sshm-cert-01 §2.1.1), and none is known here |
| Extensions | ignored, each, as one a verifier does not know is (draft-ietf-sshm-cert-01 §2.1.1, §2.3): none is known here. They are read in one encoding: each name once, in lexical order (§2.2), and its value empty or one string that is not empty, the forms every extension OpenSSH defines takes (a deviation: `PRECEDENTS.md`, Part 2, § 4). A client writes none (`-O clear`; without it `ssh-keygen` adds five). A vector carries one nobody defines, so the slot stays in use (RFC 9170) |
| Reserved | ignored, whatever it holds (§2.1.1). A client writes it empty, and a vector fills it |
| Signed by | the identity: the key in the identity document (§2), byte for byte |

- **A signature made with `-f work-cert.pub` carries the certificate,** so no message format gains a field. A verifier takes the certificate from the signature, checks it against the identity it holds for that address, and verifies the signature under it. A signature by the bare working key, or by the identity itself, is refused.
- **It is checked against the verifier's own clock** (§0), and only once the identity's signature on it has verified: "it has not begun" is a verdict on a certificate the identity signed, never on bytes anyone could write. Nobody can vouch for when a signature was made, so a certificate must be valid when it is checked, and so must outlast what it signed: it runs at most 66 days, twice the 33 days mail may wait, and a client does not sign mail with 33 days or less left.
- **A client dates a certificate from an hour before it is made** (`-V -1h:+65d`). A verifier refuses one that has not begun by its own clock, so one dated from the moment it is made is refused by every verifier whose clock is behind its maker's: mail under it is refused by such a reader, and a registration by such a server. `ssh-keygen`'s own default, a minute or two back, covers machines that share a clock. The hour is §0's: no two clocks a server takes are further apart when each shows a pass, and a server takes a certificate only once it has begun for every box it takes, 10 minutes back.
- **A client asks for 65 days, and a verifier takes up to 66.** Asked for at the ceiling, a certificate would be refused by a verifier whose clock is behind its maker's. It is the pass's rule (§6.1b), 10 minutes asked and an hour taken, with a day where §0's hour would do.
- **A client makes every check in the table itself.** Given an `allowed_signers` line `<address> cert-authority <the identity's key>`, `ssh-keygen -Y verify` checks the identity's signature on a certificate, that the address is among its principals, and that it is valid at the time it is told to verify at. It takes a certificate with a second principal, with a critical option, or with extensions out of their order or given twice, checks no key id, and knows a serial only through a revocation list, so a client built on it reads those fields from the certificate's bytes itself. The `cert/bad-*` vectors hold one certificate for each rule.
- **Every certificate is for a new working key.** A certificate is public, since it rides in every signature, so a new one for the same key would retire nothing.
- 🔑 **A certificate's serial is the time it is made** (this repo's issue #63). A client numbers a certificate by its own clock, in seconds since 1970, or one above the highest serial it knows of for the box when the clock gives nothing higher: the served certificate's, what the box has published or signed itself, and the highest its identity has revoked (§6.3a), which every renewal asks for, of its own server in the read of the box it makes first, so a box never makes a certificate that is revoked as it is made, a box restored from its identity alone among them. A box's first certificate is numbered so too.
  - **Why the clock.** An identity is a key, and a key keeps no record of what it signed. A box restored from its identity alone (§6.4) knows only what a server shows it, which may be an older record, and no server has seen a certificate that was made and never published. Counted from what it is shown, such a box gives its next certificate a serial another machine has used, and no revocation (§6.3a) can reach that machine's certificate and spare the box's own. By the clock, the certificate made later has the higher serial whichever machine made the earlier one, so the serials below a new certificate are those of every certificate made before it, known to its maker or not.
  - **A verifier never reads a serial as a time.** It compares two of them, and the higher is later: a server, a sender and a revocation of certificates are held to nothing new, and a box whose certificates were numbered from 1 goes on from its clock. A clock that reads behind the last serial still gives one that rises, by one.
  - **Why a serial rises by one where the clock gives nothing higher, and the client does not refuse instead.** Two renewals in one second are no failure. And the last certificate may have been made by a clock that read fast, by less than a server refuses, on a machine that is now lost: its owner's renewal, and the revocation that ends the taken key (§6.3a), then come at once, and do not wait for a right clock to pass that number.
  - **What it rests on is the clock of whoever holds the identity.** A certificate made while that clock read ahead has a serial above its time, and those after it are one above each other until the clock passes it. A box restored while its clock reads behind the lost machine's, at a server that shows it an older record, can still be numbered below what that machine made. Two machines can make certificates of one identity at one serial: in the same second, or each one above the same serial standing ahead of both clocks, as a revocation numbered ahead does (§6.3a). A holder that meets two takes either and pins nothing beyond the serial (decided on #63): a certificate the identity signed may be used until it ends or is revoked. A box told by its own server of a statement in its name that it did not make says so to its owner (#74).
  - **A number once taken is kept** until its statement is published or can no longer be sent (§6.4, "A serial is signed once"): a renewal that waits is sent again under the number it was signed with.
  - **Who else takes a number from the clock,** and how a certificate authority that keeps records does without: `PRECEDENTS.md`, Part 2, § 2a.
- **Other key types** for the working key are not ruled out by the format, which certifies any SSH key type; `ssh-ed25519` is what is built. The optional key types of §2 are the identity's.
- **A certificate that an ECDSA identity signed has more than one set of bytes.** An ECDSA signature (r, s) verifies as (r, n − s) too, and with either number written with leading zero bytes up to the 2,049 bytes OpenSSH reads (§3), and anyone who has seen a certificate can write those other encodings of it. Nothing rests on a certificate having one set of bytes: a server takes a pass under exactly the bytes it has on record, and a recipient takes mail under any certificate its sender's identity signed.
- **A box moves to a new certificate by publishing a prekey under it** (§6.4): a new working key needs a prekey statement that it signed, and a prekey statement never outlives the certificate it is signed under.
- **What a newer certificate retires.** At the server, everything: it keeps the highest serial it has seen for a box and refuses anything under a lower one. For a sender fetching a box's prekey, the older ones: it keeps the highest serial it has seen on that box's prekey statements and refuses a lower. For a recipient reading mail, nothing: mail is signed once and read up to 33 days later, so it is taken under any certificate of the sender's identity that is valid when it is read. A stolen working key can therefore sign mail that verifies until its certificate ends, if a server delivers it. The identity can revoke that certificate and keep its address (§6.3a); revoking the identity ends everything it certified (§6.3).
- **A box's prekey statements are ordered by their certificate's serial first, and by their own serial second.** A statement replaces the one before it if it is under a later certificate, at any prekey serial, or under the same certificate at a higher one: at the server (§6.4) and in what a sender has seen (§4.1). So a prekey published at the highest serial there is, by whoever took a working key, holds nothing: the box's next certificate passes it. A certificate serial at the top takes a signature by the identity, which can already end the address by revoking it (§6.3), so no serial has a bound on how far it may rise. Nor does a verifier bound one by its clock: that was weighed and declined (#73), since a client numbers a certificate ahead of its dates for good reasons (a number kept from an attempt at a fast clock, one above a revocation of its certificates, one above a lost machine's fast number), and a bound would leave such a box unable to renew until its clock passed the number. No system in `PRECEDENTS.md` § 2a that numbers from a clock bounds the number at a verifier. A prekey serial can therefore come again under a later certificate, and a send names its prekey by both serials (§4.5). It is how DTLS orders its records: an epoch, and a sequence number kept separately for each epoch (RFC 9147 §4.2).
- **What proves a box to the server** is a pass the working key signs (§6.1b).
- **Who else does this** (OpenSSH certificates, OpenPGP subkeys, Matrix cross-signing): `PRECEDENTS.md`, Part 2, § 2.

## 2c. The sender key types a box declares

A sender learns from one fetch whether it can verify the recipient: the recipient's identity is of a key type its client verifies, or it is not (§4.1). Nothing in that tells it whether the recipient can verify the SENDER. Without more, a box of an optional key type could write to a box whose client lacks the type: the server would take the message, the recipient's client would refuse it, and the sender would hold a receipt.

- **With each prekey it publishes, a box declares the identity key types its client verifies:** the optional member `sender_key_types`, a list of key type names, in a registration (§3) and in every prekey upload (§6.4). The read of a box, `GET /v1/<A>`, returns it (§4.1).
- **`ssh-ed25519` is taken by every box, whatever it declared.** A box that declared nothing takes `ssh-ed25519` senders only.
- **A sender whose own key type is not on the list does not send** (§4.1), and the server refuses that send, `403 sender_key_type` (§4.5 step 7): the sender has an error, and never a receipt for mail that would not be read.
- **The one entry `any` is no key type.** It says that the box will not say which types its client verifies. The server then makes no check for that box, senders send, and the box's client refuses what it cannot verify. A client declares it only when told to. It lets through no key type the server does not register, since a box of such a type is not registered to send (§3).
- **The declaration is the current prekey's.** A prekey upload replaces it, with nothing if it brings none; an identical retry changes nothing. So a declaration follows the client a box runs, and a client declares, with every prekey, every type it verifies.
- **It is not signed, and need not be.** A server that misstates a box's declaration can stop a message, or let one through that the recipient then refuses. It can do the first by dropping the message, and the second delivers nothing. What a recipient takes is settled by what its client verifies (§5), never by this list.
- **A server keeps the names it knows and ignores the rest,** so a client may verify more key types than a server registers.

## 3. Registration — a signed prekey, and a pass


**One API call, no human:** `PUT /v1/<A>` with JSON `{identity, prekey, prekey_signature}` (standard base64 of the exact file bytes, §0b), and `sender_key_types` if the box declares any (§2c), carrying a pass (§6.1b) that the new working key signs. The box is in use at once.

**SSHSIG, in bytes.**
- Signed data = `"SSHSIG"` ‖ `str(namespace)` ‖ `str("")` ‖ `str("sha512")` ‖ `str(SHA-512(message))`, where `str` = uint32 length + bytes.
- Signature = Ed25519(working key, signed data).
- The `.sig` file is a PEM-armored (`SSH SIGNATURE`) blob: `"SSHSIG"` ‖ `u32(1)` ‖ `str(the signing key: here, the certificate)` ‖ `str(namespace)` ‖ `str("")` ‖ `str("sha512")` ‖ `str(str("ssh-ed25519") ‖ str(sig64))`. 846 bytes armored for a message and 850 for a prekey statement (measured), of which the certificate is the larger part; the identity's own signature, on a revocation, is 403. Under a certificate that a P-256 identity signed, a prekey statement's is 943 or 947: the two numbers of an ECDSA signature vary in length.
- **Every verifier reads a signature as OpenSSH reads it** (`sshsig.c`, and the key and signature code beneath it), the reference implementation of the format, **with two checks more.** Where every OpenSSH build reads a form one way, that is the rule. **Where OpenSSH's builds disagree, the rule is the Go client's,** which is also OpenSSH's from 10.3p1, linked to an OpenSSL that has Ed25519. The `sig/` vectors hold one signature in each form.
  - **The armour:** the BEGIN line first, ending in LF or CRLF; then the base64, in which space, tab, LF, VT, FF and CR are skipped wherever they stand, and which is otherwise in its one encoding: padded, and the unused bits of its last character zero. Then LF and the END line. Nothing after the END line is read. One NUL may be the last byte before that LF (`sshbuf_dup_string`); any other byte in the base64, any other NUL among them, is refused.
  - **The blob:** its version is 0 or 1 (`sshsig_parse_preamble` refuses only a higher one, and nothing signs the version). A string OpenSSH reads with `sshbuf_get_cstring` where no signature covers it may end in one NUL, which is not part of it: the namespace, the hash name, each signature's type, and a bare key's type and curve. A NUL before its last byte is refused. OpenSSH builds the data a signature covers from those strings without it, so a signature verifies with the NUL or without. What an identity signed in a certificate is read byte for byte (§2b). An ECDSA signature's r and s are each at most 2,049 bytes (`sshbuf_get_bignum2`).
  - **`reserved`:** what the key signed has an empty one, and the blob's field is read and skipped, whatever it holds (`PROTOCOL.sshsig`: "Implementations should ignore the reserved field if it is not empty"). So a signature made over a field that is not empty does not verify.
  - **The first check more: a bound on its size, stated for each identity key type:** 4,096 bytes for `ssh-ed25519`, and 4,096 for `ecdsa-sha2-nistp256`. What a box signs, with its identity or with a working key under a certificate its identity signed, is held to its identity's bound. A field that carries a signature counts every byte it holds, what follows the END line too; in a message it is the block from its BEGIN line through its END line (§4.4). Every verifier refuses a longer one before verifying it, a server's included, and nobody cuts one down; one longer than the most any type allows is refused before it is read. Each bound is several times the largest its type makes. **A new key type states its own and leaves the others where they are:** were one to rise, a block padded past it would be refused by one reader and delivered by another.
  - **The second: an Ed25519 signature's S is below the group's order L** (RFC 8032 §5.1.7), in the SSHSIG and on a certificate. Go's `crypto/ed25519` refuses S + L, and so does OpenSSH from 10.3p1 on OpenSSL's Ed25519 (`266647c5`) and from 10.4p1 on its own (`7763a38b`). `ssh-keygen` before them takes it, so a client built on it checks S itself.
  - **Where OpenSSH's builds disagree, each a known variance** for a client built on `ssh-keygen` (the script's tests hold it to the Go client's verdict, and on a build named here to this shape):
    - **An Ed25519 signature's R.** The equation is RFC 8032 §5.1.7's without the cofactor, `[S]B = R + [k]A'`, compared as encodings, as Go's `crypto/ed25519` and OpenSSL check it: a neutral R is taken, and R with a point of small order added is refused. OpenSSH's own Ed25519 from 10.6p1, libsodium's (`eab91661`), used where libcrypto has none, refuses the neutral R and takes R with a point of order 2 or 4 added; R with a point of order 8 added it refuses too (measured 2026-10-20). Only the key's holder can make either. The equation with the cofactor would take both, and no verifier here makes it.
    - **A P-256 key's coordinates (§2):** OpenSSH up to 10.2p1 refuses a coordinate of 128 bits or fewer, or of n − 1 or more, which the Go client and OpenSSH from 10.3p1 take, so a script on such a build refuses a P-256 identity with one.
    - **A P-256 key at all:** OpenSSH built without OpenSSL reads none, so a script on it refuses every P-256 identity.
  - **A server keeps a signature as it was sent, and serves it so** (§4.5): the bound is what limits what it stores.

**Server:**
1. The URL-path address must be 64 lowercase hex chars → `H`. Otherwise, capitals included, `bad_address`.
2. The body is exactly `{identity, prekey, prekey_signature}`, with `sender_key_types` (a list of strings, §2c) or without → otherwise `bad_request`, naming the missing or unknown field (§0a).
3. `SHA-256(identity) == H`, and `identity` has the form of an identity document (§2). Otherwise `identity_mismatch`, with a hint naming the usual causes: a comment left on the SSH line, CRLF, a missing final newline.
4. **The key's type, then the key.** A key type this protocol does not define → `unsupported_key_type`. The key in its one encoding, a key of the type it names that is written back as the same bytes (§2) → otherwise `identity_mismatch`. The key checks of that type (§2) → otherwise `bad_key`: for `ssh-ed25519`, a canonical point that is not of small order, checked explicitly, because Go's `crypto/ed25519` and OpenSSH 10.2 both accept a key of small order or not canonical, and `ssh-keygen` reads any 32 bytes as a key, a point or none; for `ecdsa-sha2-nistp256`, none beyond the point the library reads (§2). **Then the server's own list:** a server registers `ssh-ed25519` and whichever other defined types its operator chooses, and answers the rest `unsupported_key_type`, naming its list. Parse the prekey statement: the exact five-line grammar (§2a); line 2 == `H`; a valid `age1pq1…`/`age1…` recipient on line 4 (rejecting X25519 small-order points, including the X25519 half of a post-quantum key); `not_after` after now and at most 33 days and an hour after now (§2a, §0). Any failure → `bad_key`.
5. **What could change nothing is answered first, and the rest is counted first.** **Registration never changes a registered box**, so one the server holds already is answered from its record, before anything below is checked: active, and the request byte-identical to its CURRENT identity + prekey statement + signature → `200 {}` once its pass (step 7) is checked under the box's current certificate (an idempotent retry), and `401 certificate_revoked` before any pass is looked at if the identity revoked that certificate (§6.3a); anything else → `409 conflict`, with a hint that names `irongall prekey renew`, which replaces a registered box's prekey. A revoked address → `410 revoked` with its record, box or none (§6.3). Every prekey change goes through §6.4. Any other registration counts against its IPv4 address or IPv6 /64 here (§8), before its signatures are checked. Proof of work is a lever a server may add here (§12); nothing in v1 carries it.
6. Verify the prekey SSHSIG: the blob's key is a certificate of that identity, in every rule of §2b's table; namespace `irongall-prekey-v1:<H>`, hash per §0; and the statement does not outlive the certificate → otherwise `bad_key`, or `prekey_time` when what fails is the certificate's time or the statement's `not_after` (§2a) at the server's clock, a certificate that began less than 10 minutes before it among them (§0). **Then what the server keeps of the address, box or none** (§6.3, §7): a certificate the identity revoked (§6.3a) → `401 certificate_revoked`.
7. **The pass** (§6.1b): this box's, for this server, not run out, and signed under the certificate of step 6 → otherwise a `401` (§6.1b says which). **The two together are the proof of possession:** the certificate shows the identity chose this working key, and a pass minutes old shows its holder is here now. Nobody can register an identity they do not hold, and a statement that leaked cannot be registered by whoever found it.
8. **A new box** is stored `active` → `201 {}`. A box registered by another request meanwhile is answered as step 5 answers.
9. The server keeps which certificate the statement is signed under, and its serial: it takes a pass only under that certificate, and a later statement only under it or one of a higher serial (§2b, §6.4).

## 3a. Box states — normative

Every call names a box; this is what each event does in each state.

| State ↓ / event → | Register `PUT /v1/<a>` (with a pass) | New prekey `PUT …/prekey` (a later certificate, or the current one and a higher serial; with a pass under its certificate) | A call with the box's pass (`messages`, `account`, `acl`, `profile`) | Revoke `PUT …/revocations` (the identity's own signature, no pass) |
|---|---|---|---|---|
| **unknown** (never registered, or forgotten) | → `active`: `201` | `404 no_such_mailbox` | `404` | kept, box or none: of the address → `revoked`, `201`; of certificates, `200`, and the address stays unknown |
| **active** | identical replay: `200`; otherwise `409 conflict` | stays `active`: `200` | served | of the address → `revoked`: `201`; mail deleted. Of certificates: `200` |
| **revoked** | `410 revoked` | `410` | `410` | `410`, answered from the record before any signature is checked: nothing could change it |

- **Not built:** `profile` among the calls with a pass (§6.2).
- **A revocation that does not verify is `400 bad_revocation` in every state but `revoked`,** and changes nothing (§6.3).
- **There is no delete** (decided on #312). A box leaves a server for good by its identity's revocation (§6.3), pauses with its ACL (§6.2), and is forgotten once it stops renewing (§7).
- **There is no pending state.** A registration carries a pass minutes old, which shows a live holder of the working key, so a box is active from its first call.
- **Replays:** a byte-identical replay of a request that already took effect gets `200` and the same result; a conflicting one gets `409 conflict`. That covers registration, prekey uploads, profiles (a `version` not above the current one) and sends (§4 step 6).
- **The read of a box, `GET /v1/<a>`,** answers for an `active` box. An address with no box is `404 no_such_mailbox`, whatever its identity revoked of its certificates, which `GET …/revocations` serves (§6.3). A `revoked` address's read is `410 revoked` with its record (§6.3).
- **A box is forgotten once nothing valid for it is left** (§7): once it has stopped renewing, its certificate has ended and its last prekey's mail has expired. It is then unknown, and registers anew (§3), its ACL and its account gone with the old one. What its identity revoked is kept.
- **No `last_seen`.** A box whose owner stops renewing refuses mail once its prekey expires (`prekey_expired`, §6.4), and a renewal turns it back on while the server keeps it. The current prekey statement dates the owner's last renewal, so the server tracks no activity of its own: what forgets a box is its record's expiry, which each renewal moves (§7).

## 4. Sending A → B

**4.1 Read B's box, and verify it** — one GET, `GET /v1/<B>`, the one read of a box: everything a sender needs before it posts. → `{identity, prekey, prekey_signature}`, all base64, with `sender_key_types` if B declared any (§2c), and `revoked_certificates` with `revoked_certificates_signature` when the server holds a revocation of B's certificates (§6.3a). A revoked address is `410 revoked`, with the record the server holds in the member `record` (§6.3). The answer is open, as every answer is (§0a): a later version may add a member, and a box's signed profile is the one named so far (§12). **The read takes no pass:** it is public, so a server counts it against the address it comes from, whatever `Authorization` it carries, and reads no pass on it (§8; this repo's issue #352), as RFC 9773 has an ACME client read renewal information (`PRECEDENTS.md`, Part 2, § 4, Limits). No client sends one: not before a post, not in a drain's read of a sender (§5), and not in a box's read of its own box. Nothing is encrypted to a prekey until every check below has passed.

- **Identity: the pinned one, or at first contact the served one, and a pin always wins.** The served identity is hash-checked against the address and held to the two-line form, with its key in its one encoding, and to its key type's checks (§2) — as the server holds it at registration, so one identity key can never have two addresses. One of a key type this client does not verify is refused in words that say so, and nothing is encrypted. It is pinned only once its prekey statement has verified, and later fetches never replace it. The `allowed_signers` file is ONE line, `<address> cert-authority <key>`, rebuilt from those hash-checked bytes for each verification, never built from server text: an `allowed_signers` principal is a pattern list, so a server-supplied address carrying a newline could otherwise plant a `*` signer that verifies the operator for every box.
- **The operator cannot swap the encryption key** (the signature fails), **pass off another box's validly-signed prekey** (wrong namespace, line 2 and certificate), **roll back a sender that has seen a newer one** (the persisted serials, compared by certificate first, §2b — recorded only after every check passes), **offer a prekey under a certificate older than one the sender has seen** (the persisted certificate serial: a stolen working key that was since replaced), or **keep a sender on one past `not_after`** (§2a). All are tested against a forging server (§11).
- **The read comes before anything is sealed or posted, at every post** (§6.3), of a new message or of one that waited in the outbox. What it carries of a revocation of B's address or of B's certificates is kept once it verifies, and the send is checked against what the box then holds: nothing is posted to an address it holds a revocation of, and a prekey statement under a revoked certificate is refused (§6.3a). What a server shows, or leaves out, is its word and is kept nowhere, so the next post reads again. **No answer is not "none held":** nothing is sealed or posted, and the message waits in the outbox. Neither does a read that serves no box (`404 no_such_mailbox`, or `410 revoked` with nothing that verifies) give anything to seal to. Whatever code a failed read carries is no answer about the message. The read tells the server that this address is about to be written to, which the post tells it a moment later.
- **Caching:** the identity forever; the prekey until its `not_after` or a `409 stale_prekey`, though the read at every post brings it again, with what is held of the box's revocations; the serial guards make that safe.
- **The read may come in gzip** (RFC 9110 §8.4.1.3), and only to a request whose `Accept-Encoding` takes it (§12.5.3): it is base64 in JSON, read before every post and for each sender in a drain. What a client checks is the JSON beneath, and a client that sends no `Accept-Encoding` gets none. A server compresses no other answer of the API: a list puts what senders chose beside the box's own values (BREACH, RFC 7457 §2.6), and a ciphertext does not compress.
- **A box this client holds a revocation of is refused before any call,** whatever a server serves for it afterwards (§6.3). **A `410 revoked`, in answer to the read or to the send, is checked and never believed:** each carries the record its server holds (§6.3), and the client takes the box as revoked only if a revocation verifies; after a send's that carries none, or one that does not verify, it reads the box.

**4.2 The ENVELOPE `P` — one line of compact JSON, ending in a line feed.** It is what the sender signs (§4.4), and the server never sees it.

| Field | | |
|---|---|---|
| `v` | required | `1` |
| `from`, `to` | required | the sender's and recipient's addresses. **The recipient rejects the message unless `from` is the address of the identity that signed it and `to` equals itself** (§5) |
| `sent_at` | required | RFC 3339 UTC to the second: the time of the post that carried it, dated afresh at every post, every other member as it was (§4.5); the replay window needs it (§5) |
| `msg_id` | required | a UUID as RFC 9562 §4 writes one (its 4, 2, 2, 2 and 6 octets in hex, with hyphens between), of any version, and lowercase only: one value has one text, as an address does. A client makes a random one (version 4) ONCE per logical message and keeps it on every re-encryption, so a retry is never acted on twice (§5) |
| `identity` | required | the sender's identity document (§2), as standard base64 in its one encoding. `from` is its hash, and the signature must verify under it, so a recipient checks a sender it has never met without asking the server anything |
| `body` | required | the message: any JSON value, carried as that value, and a string is text: an object arrives as that object, not as a string holding it |
| `subject` | optional | a string |
| `in_reply_to` | optional | the `msg_id` replied to — never the ciphertext id |
| `supersedes` | optional | a `msg_id` of the same sender that this message replaces. Stored mail is never altered; the recipient decides |

- **A sender refuses an `in_reply_to` or `supersedes` that is not a `msg_id`** before it builds anything: the server's 64-character id of a ciphertext is not one. A receiver checks only that each is a string: they are the verified sender's words, and a reply can name any `msg_id`. **An empty string in `subject`, `in_reply_to` or `supersedes` is read as the member left out,** as null is (§0b), and a writer leaves such a member out.
- **A sender holds the envelope it builds to the rules its reader holds it to (§0b, §5 check 3), and keeps and posts nothing that breaks one.** A JSON body is one value and nothing after it, with no name twice in any object, nested at most 31 deep (32 with the envelope), no noncharacter, and no number past binary64; one that breaks a rule is refused whole, never repaired, and one that keeps them is sent compact, its members in the order given and its strings and numbers as written, but that U+2028 and U+2029 are escaped, as in every string the envelope carries. The same reading refuses a noncharacter in a text body or a subject before the outbox keeps it.
- **Encoding: compact UTF-8 JSON without HTML escaping** — `jq -c`, Go's `SetEscapeHTML(false)`, Python's `ensure_ascii=False` with compact separators. Default serializers that escape `<`, `>`, `&` or non-ASCII inflate the body. **Compact JSON holds no line feed of its own**, since JSON escapes one inside a string, so the envelope is exactly one line: that is what lets a reader take it apart from the signature after it (§4.4). Receivers accept any JSON text on that line that §0b takes, and ignore unknown fields (§0a).
- The server's size cap counts the ciphertext's bytes, which are the post's whole body (§4.5). age adds 1,659 B (PQ) or 200 B (`--no-pq`), and the signature 846 B.

**4.3 Encrypt to B's prekey — binary, not armored.** What is encrypted is the envelope's line, the signature over it (§4.4), and padding (§4.3a), one after the other: `{ cat P P.sig; padding; } | age -r <recipient> > m.age` (§4.5).
- **Post-quantum prekey (the default):** one `mlkem768x25519` stanza — age's hybrid ML-KEM-768 + X25519 recipient (age ≥ 1.3, which builds it on HPKE, per its `filippo.io/hpke` dependency). It adds 1,659 B (measured). The payload layer below is identical.
- **`--no-pq` prekey:** the X25519 stanza, below.

Inside age, for a `--no-pq` prekey:
- File key `K` = 16 random bytes.
- Ephemeral secret `e` = 32 random bytes; share `E = X25519(e, 9)`; `Z = X25519(e, B_x)` — abort if `Z` is all zeros.
- Wrap key = HKDF-SHA-256(ikm `Z`, salt `E ‖ B_x`, info `"age-encryption.org/v1/X25519"`). Stanza body = ChaCha20-Poly1305(wrap key, nonce 0¹², `K`), 32 bytes.
- Header = `age-encryption.org/v1\n-> X25519 b64(E)\nb64(body)\n---`. MAC = HMAC-SHA-256(HKDF(`K`, info `"header"`), header).
- Payload: nonce `n` = 16 random bytes; payload key = HKDF(`K`, salt `n`, info `"payload"`). A message of up to 64 KiB is one chunk = ChaCha20-Poly1305(payload key, nonce `0¹¹ ‖ 0x01`, `P`). The last-chunk flag stops truncation.
- No armor: the post carries the file's bytes as they are (§4.5), and armor would add a third. Overhead is 200 B `--no-pq`, 1,659 B post-quantum (measured).

**4.3a Padding — every message is a whole number of blocks.** The server sees each ciphertext's size, and without padding reads a message's length to the byte.
- **The rule.** A block is the smallest power of two that is at least 1/16 of the ciphertext's size, and never under 1 KiB: 1 KiB up to 16 KiB, 2 KiB up to 32 KiB, and on. The sender adds padding, after the signature, that makes the CIPHERTEXT the next whole number of blocks. So a ciphertext takes one of 16 sizes up to 16 KiB and of 8 for each doubling after it.
- **The padding is bytes after the signature, to the end:** `.`, as many as it takes, and none for a message already on a block. A reader never looks past the signature's END line (§4.4), so nothing has to be said of what the padding holds.
- **It is outside what is signed,** where OpenPGP puts its own padding packet. So each encryption is padded for its own prekey without touching what is signed, and a message's size does not depend on its own signature's.
- **The ciphertext is measured, not the body,** because it is what the server sees and what its size cap counts. age's file size is a fixed function of the key type and the plaintext length: a header of 168 B (`--no-pq`) or 1,627 B (post-quantum), a 16-byte nonce, and a 16-byte tag after each 64 KiB chunk of plaintext (measured against age 1.3.2 up to 10 MiB, and the X25519 header against age 1.2.1; one chunk gives §4.3's 200 and 1,659). The sender computes the padding from that, encrypts, and refuses to send a file that is not the size it computed.
- **Made at the seal, never before.** The padding depends on the prekey's type, so an encryption after `409 stale_prekey` is padded again for the newer prekey: between the two types the age file differs by 1,459 B. The envelope and its `msg_id` stay.
- **The server does nothing, and a size limit must be a whole number of its own blocks.** As sizes go, any power of two is such a number, the largest ciphertext (§4.5) among them, and 100 KiB is not: a message just under a limit like that one would be padded past it. With limits chosen that way a client never needs to know the limit: a message fits it padded exactly when it fits it bare.
- **Where the first boundary falls.** An envelope with an empty body and no optional field is 383 B, its line feed included, and its signature 846 B. With age's overhead, a post-quantum box's smallest message is 3,072 B and holds a body to 184 B, the next, 4,096 B, to 1,208 B; a `--no-pq` box's smallest is 2,048 B and holds a body to 619 B. It stays where the overhead puts it. So it is not true that everything under 1 KiB looks the same.
- **What it costs:** at most 1,023 B a message up to 16 KiB and about 512 on average; above that half a block on average, about 4.4% of the message, and about 1/8 at worst, for a message just past a doubling. In bytes sent and stored; no extra request.
- **What it does not hide:** who writes to whom, when, and how often. A sender that is not one of the two clients may pad differently or not at all: the server cannot tell, and does not check.
- **Not chosen:** a fixed 1 KiB block at every size (it tells a large message's size to the KiB) · one size per doubling (up to double the bytes) · random padding (it averages out over repeated messages) · opt-in or a `--no-pad` flag (the padded messages would be the marked ones) · padding as a member of the envelope (it would be signed, so a message would be signed again at each encryption, and its size would turn on the size of its own signature).

**4.4 Sign, before encrypting — the namespace carries the recipient:** `ssh-keygen -q -Y sign -n "irongall-msg-v1:$B" -f work-cert.pub < P > P.sig`. The signature is the working key's, over the envelope's one line, and holds only for box `B`. 🔑 **It travels inside the encryption, after the envelope, and the server is handed none** (this repo's issue #29): the server knows who sends to whom, from the pass a send carries, and holds nothing signed that says so.

What is encrypted, in order:

```
{"v":1,"from":"…","to":"…","sent_at":"…","msg_id":"…","identity":"…","body":"…"}
-----BEGIN SSH SIGNATURE-----
U1NIU0lH…
-----END SSH SIGNATURE-----
................
```

- **Line 1 is the envelope** (§4.2), and those bytes, its line feed included, are what is signed.
- **Then the signature,** the file exactly as `ssh-keygen` wrote it, through its `-----END SSH SIGNATURE-----` line.
- **Then padding,** to the end (§4.3a).
- **It is git's layout for a signed tag,** with the same signature format: the signed bytes as they are, then the signature block. Nothing is encoded a second time, and what the layout adds to a message is the same number of bytes whatever its size. Not chosen: one JSON object with the envelope and the signature as base64 members, the shape of a JWS, which makes every message a third larger inside the ciphertext.
- 🔑 **Three rules for a reader,** each from what went wrong in a verifier of this layout elsewhere (`PRECEDENTS.md`, Part 2, § 3):
  1. **The signature is checked over line 1 exactly as decrypted, and the envelope's members are read from those same bytes,** never from anything rebuilt. A key given twice is refused (§5).
  2. **Each part has one place, and nothing is searched for.** Line 1 is the envelope. Line 2 must be the signature's BEGIN line. The block ends at the first END line, and a line feed must follow it: with any other byte there, or none, the message is refused, and no later END line is looked for. What follows is never parsed and never shown.
  3. **One signature, one identity.** It is verified against the identity the envelope carries, and the verdict is the verifier's exit status, never text it printed.
- **The binding to the recipient is what stops a recipient passing a signed message on** to a third box as mail from its sender, the known flaw of signing before encrypting: the signature verifies in `B`'s namespace only, and the envelope's `to` must be its reader.
- **What it costs a recipient:** it decrypts before it can verify, so a message it cannot decrypt has only the server's word for its sender (§5).

**4.5 Post — the body is the ciphertext, raw:** `POST /v1/<B>/messages?prekey_serial=<n>&certificate_serial=<n>`, its body the age file's exact bytes (`Content-Type: application/octet-stream`), carrying the sender's pass (§6.1b) → `201 {id, received_at, expires_at}`, the times in §2a's format, with `Location: /v1/<B>/messages/<id>`, the message made (RFC 9110 §15.3.2), which only B may fetch. The sender is the box the pass names. The two serials name the prekey used, its own and its certificate's (§2b): both REQUIRED, so no mail reaches a retired prekey (Terms), each given once and written as a statement writes a serial (§2a: digits, no leading zero, from 1 to 2^53 − 1). When B has a newer prekey, the server answers `409 stale_prekey`, and the sender seals the SAME envelope to it within the same send. A server reads the body as bytes whatever its `Content-Type` says; a client sends `application/octet-stream`.

- 🔑 **A ciphertext is at most 16 MiB (16,777,216 bytes), in every send** (decided on this repo's issue #351). A server's caps on it are at most that, an account's among them (§6.5), and every reader takes a ciphertext of any size up to it (§5.2): so mail one server takes, every reader reads. It is a whole number of its own blocks (§4.3a). A larger one is a new version of the protocol (§0a).
- 🔑 **Retry with the envelope, never with a new send.** Sending again makes a new envelope with a new `msg_id`, and a bot that acts on mail would act twice. The outbox keeps the envelope until a receipt arrives, and nothing else: **a seal is made for one post and never kept.** Each post, the first and every retry, asks about the recipient (§4.1), takes its statement in use through every check of §4.1, then dates the same envelope, its `sent_at` the sender's clock and every other member as it was, and seals it to that statement, signed by the working key in use. Every ciphertext of a message keeps its `msg_id`, so the recipient delivers it once (§5 check 10).
- **Why each post is dated afresh.** A reader can trust only `sent_at`, which is signed, and a server sees only when it received the post. Dated at the post, the two are within the hour of each other, so a message is fresh to its reader for as long as its server keeps it (§7), a message that waited in the outbox included, as a signed request's time is when it was signed, made anew for each attempt (`PRECEDENTS.md`, Part 2, § 4). `sent_at` says when this copy was sent, not when the message was written: a sender that needs that says it in the body. **The outbox keeps the envelope as written, and posts it for 33 days from then,** by the clock at each dating, so no copy is dated more than 33 days after the first, and a reader's replay set, which reaches back 66 days and an hour, still holds the first copy when a retry of it comes (§5 check 9). An entry written longer ago is never posted.
- **So a message that waited goes under what the sender holds at its post.** A message can wait in the outbox for days, and its recipient may meanwhile renew, or its identity revoke the certificate the first attempt sealed under: that prekey may be one a thief of the working key published. The post after the wait seals to the statement that passes every check now, so nothing goes to a prekey under a certificate since revoked or to a statement ordered before one the sender has since recorded. A message to an address the box now holds a revocation of is never posted.
- **A post whose answer is lost costs a send.** The server stored it, and the retry is a new ciphertext, which the server stores and counts as new mail: the sender's daily sends, its pair's unacked mail until the copy is acked, and the recipient's mail received. The recipient acks the copy and delivers the message once. So the cost of a lost answer is one send, which nothing is added to the protocol to save: a client that loses answers often has a fault of its own to fix. Signal and Matrix encrypt again at each attempt too; Matrix's server also drops a retry by a transaction id, which irongall does not (`PRECEDENTS.md`, Part 2, § 4, the outbox's row).
- **Why this shape: the body is the bytes,** the plainest HTTP shape for an opaque file, the one S3's `PutObject` and Matrix's media upload take, and a fetch answers the same bytes (§5.2). What it adds to a message is a query and the headers, a fixed number of bytes and never a share of it: base64 inside JSON made every message a third larger, on the send and again on the fetch. Stock tools send and keep it byte for byte, `curl --data-binary @<file>` and `curl -o` (`PRECEDENTS.md`, Part 2, § 4).
- **Not chosen:** the ciphertext as base64 inside a JSON object, the shape before this one, a third larger both ways; armored text inside JSON, which `jq -r` once broke by adding a line feed; and multipart (`curl -F`), byte-exact but a browser-upload pattern that wraps the bytes in a boundary and headers of its own.

**Server pipeline — cheapest first.** Only step 9 stores anything, and every count in it is taken before the work it guards and given back if that work does not happen, so sends in flight at once cannot all pass on one count. Status codes are §13's map.
1. **Who is sending: the pass** (§6.1b), before the body is read. **Pre-auth rate: per IP only** → `rate_limited`. No pass, two `Authorization` lines, or one that is not a pass → `unauthorized`. The box it names unknown → `unknown_sender`; revoked → `sender_revoked` (never `revoked`, which would tell a sender its PEER is dead). A pass that has run out → `pass_expired`; one that is not that box's, for this server, under its current certificate → `unauthorized`. **Then the sender's budget of calls** (§8), which every send spends, a retry included → `rate_limited`: it bounds what every step below costs, the dedupe's read among them.
2. **The path and the query, before any of the body is read.** `B` is 64 lowercase hex chars → otherwise `bad_address`. `prekey_serial` and `certificate_serial` are each given once, each a serial in its written form (§2a), and no other parameter is → otherwise `bad_request`, naming the parameter in `member` (§13).
3. **Read limit:** the body is read as bytes, whatever its `Content-Type`, up to the sender's cap (§6.5), which counts the ciphertext's bytes and is at most 16 MiB (above): more → `too_large`, with the cap in `limit`, from the `Content-Length` before anything is read, or as it reads.
4. **It is an age file**, parsed with `filippo.io/age`'s public API (`ExtractHeader`/`DecryptHeader`), so the header needs no parser of the server's own → otherwise `not_age`, an empty body or a JSON one among them.
5. **Is `B` registered and ACTIVE?** `B` unknown → `no_such_mailbox`; `B` revoked → `revoked`.
6. **Dedupe, BEFORE anything asks whether `B` takes new mail:** `id = SHA-256(ciphertext)`. If B already holds this id, acked or not (§7): the same sender → a retry → **`200` with the ORIGINAL receipt, whatever has changed at B since: a renewal, a new certificate, a quota reached**; another sender → `409 conflict`. A retry is no new mail, and what the next steps keep from B is new mail. A budget (step 1) may still DEFER a retry; the client retries later and gets the `200`. B delivers a message once whichever ciphertext of it arrives (§5). The reference clients seal afresh at every post, so a retry of theirs is a new ciphertext, stored and counted as one (above): this step answers a client that posts the same bytes again.
7. **Does `B` take new mail, on this prekey and from this sender?** **`B`'s current prekey past its `not_after`, or under a certificate `B`'s identity has revoked (§6.3a) → `prekey_expired`.** A sender whose identity is not `ssh-ed25519`, to a `B` that neither declared that type nor said `any` (§2c) → `sender_key_type`. A `prekey_serial` and `certificate_serial` that are not the two serials of B's current statement (a prekey is named by both: §2b) → `stale_prekey` (hint: "a newer prekey exists: read `GET /v1/<B>` again and encrypt the same envelope"). Then **exactly one NATIVE stanza** (`X25519` or `mlkem768x25519`) **of the current prekey's type** (Terms). **Grease stanzas are ignored**: rage, the Rust `age` crate and pyrage add one random `…-grease` stanza to every file, and the age spec says to ignore unrecognised stanzas — so a stanza matching `^[!-~]{1,8}-grease$` with ≤ 4 arguments passes. Anything else → `wrong_recipient_type`, the hint chosen by case: a PQ box and an X25519-only file → "this box needs age ≥ 1.3 or age-plugin-pq"; a `--no-pq` box and a PQ file → "this box is --no-pq (X25519 only): re-fetch its prekey"; two native stanzas → "encrypt to one recipient only"; another type → "encrypt to the box's prekey". **Which KEY it is encrypted to cannot be checked**, by design of native age. A grease stanza's body is bounded only by the message cap: the spec's "small" has no number.
8. **Quotas, counted ONLY for sends that carried their sender's pass**, so nobody can burn A's quota with junk that merely names A. **First B's ACL (§6.2), before any count, so a send it refuses spends none: a sender it does not admit → `403 sender_not_allowed`,** one code and one wording whether the sender is denied or only not on the allow list; then A's sends → `rate_limited` naming `sends` (§8), with how many a day in `limit`; unacked A→B at the per-pair cap → `pair_full`, with `Retry-After` and `{unacked, oldest_expires_at}`; B's total at its cap → `mailbox_full`, with how many it holds in `count`; **the new mail B takes, from every sender together, past its budget (§8) → `mailbox_busy`**. A send past A's sends waits until one more comes back, a day divided by their number; `pair_full` and `mailbox_full` carry a `Retry-After` of the poll interval, and `mailbox_busy` the time until B takes another. **A send refused here waits in its sender's outbox,** to be sealed and posted again after `Retry-After`: none of these is a failure of the message. **But `sender_not_allowed`, which is final:** only B can change its ACL, so a client never posts that message again.
9. **Store it** (§7) and answer `201`, with `Location`.
   - A concurrent send of the same ciphertext that got there first is answered as step 6 does.
   - Any other failure answers 5xx. The client keeps the message in its outbox and retries.

**The server checks no signature on a message: there is none for it to see.** What it holds a sender to is the pass. A live pass is a bearer credential for the minutes it has left, so whoever holds one can post in that box's name. Nothing posted that way verifies at a recipient: it spends the box's limits and delivers nothing.

## 5. Receiving — B

**5.1 Poll:** `GET /v1/<B>/messages` with the box's pass (§6.1b). Every list response — empty or not — is `{count, messages: [{id, from, size, received_at, expires_at}], next_cursor}`, with a `Retry-After`:
- `count` is every live message in the box; `messages` is one page of up to **50**, oldest first by `received_at`; pass `?cursor=<next_cursor>` until it is `null`.
- **A cursor is opaque and URL-safe** (AEP-158): one or more of `A`–`Z`, `a`–`z`, `0`–`9`, `-` and `_`, which the next query carries as it is. A client takes a list with any other cursor, an empty one included, as no answer.
- **`Retry-After` on every list answer, a `304` among them, is the server's poll interval in seconds**, as Let's Encrypt's renewal information says how often to poll (RFC 9773 §4.3), and in the form a `429`'s takes (§13): delay-seconds, digits alone. A list answer without one breaks its form. Bots are told that interval; what is enforced is a burst of polls at once and then a steady rate (§8).
- **A first page carries an `ETag`, and a poll may send it back in `If-None-Match`:** a page that has not changed since is `304`, with its `ETag`, its `Retry-After` and no body (RFC 9110 §13.1.2, §15.4.5), as GitHub's notifications answer a poll (`PRECEDENTS.md`, Part 2, § 4). The tag is the server's and opaque. A page after the first carries none, so no tag names it, and a list with a cursor is `304` only to `If-None-Match: *`, which names any page and which no client sends (§13).
- **A `304` is a poll like any other:** it takes from the poll rate, and a box that polls faster than the rate is refused `429`, never answered `304`, whatever it sent. GitHub counts no `304`; a poll a server answers free is one a bot makes every second.
- **A client keeps an `ETag` only from an empty box's answer,** so a `304` means the box is still empty and can never hide mail; a client that keeps one of a page with mail must act on the page it kept. A `304` to a list that sent no `If-None-Match` breaks its form. **A `304` whose `ETag`, compared weakly, is not the tag the poll sent is no answer,** as a cache holding no response with that validator "MUST NOT use the new response to update any stored responses" (RFC 9111 §4.3.4): the drain stops there, so it deletes no retired prekey that mail on the server may need, and the client drops the tag it kept, so its next poll asks for the page in full.
- **There is no server long-poll.** A client that waits for a reply polls.
- An empty box is `{"count":0,"messages":[],"next_cursor":null}`.

Server side:
- **The path and the query first, before the pass.** `B` not 64 lowercase hex → `400 bad_address`. The one parameter a list takes is `cursor`, once: a cursor not of the form above, an empty one included, one the server cannot read as a cursor it makes, any other parameter, or one given twice → `400 bad_request`, naming the parameter in `member` (§13).
- Then the pass (§6.1b). **The per-box poll rate applies to EVERY poll, empty ones and `304`s included** — a token bucket, taken before `If-Match` and `If-None-Match` are read.
- **`If-Match` is read first, as RFC 9110 §13.1.1 and §13.2.2 have an origin server evaluate it, and compared strongly:** `*` is true only as the whole value; otherwise the value is a list of entity-tags, each read through its closing quote, as `If-None-Match`'s is, and is true when one of them is the page's own; a page after the first, which carries none, matches no tag; and a value of any other form, `*` among tags or a tag followed by anything but a comma included, is false (this repo's #333). One that is false is `412 precondition_failed`. A client needs none of it: it is there because an origin server must evaluate one it receives.
- **`If-None-Match` is read as RFC 9110 §13.1.2 has a server evaluate it, and compared weakly:** a tag a proxy on the way marked weak (`W/`) matches still. `*` matches any page only as the whole value. Otherwise the value is a list of entity-tags, each read through its closing quote, since a comma and a `*` are characters a tag may hold (§8.8.3), and a value of any other form, `*` among tags included, matches no page. The tag is a strong validator of the page's body, so it changes with any message that enters or leaves the page or the count.
- **A list with a cursor is a continuation only if the box holds mail after the cursor, and the cursor is the `next_cursor` the server handed the box last.** Then it takes from the box's page allowance, not its polls, and that allowance is sized so that a drain of a full box is never refused (§8). Any other cursor the server can read (made up, replayed, or a page asked for again after its answer was lost) is answered all the same and charged as a poll, and so is two clients draining one box at once, each spending the other's cursor. With nothing after the cursor it is a poll: it takes from the poll rate and gets an empty page. So a cursor is no way around the poll rate.

**5.2–5.5 Fetch, decrypt, verify, check, ack — ONE gate, ONE verdict.** A client drains every page. For each message its list gives, it fetches `GET /v1/<B>/messages/<id>` → `200`, `application/octet-stream`, the ciphertext's exact bytes with a `Content-Length`, and nothing else: who sent it and when are the list entry's (§5.1), whose `from` is the box whose pass the send carried, on the server's word. **Every reader takes a ciphertext of any size up to 16 MiB (§4.5), and reads at most the listed `size`: a body of any other length, or a listed `size` past 16 MiB, breaks the answer's form:** the drain stops there, as at any answer that breaks its form (§0b), with nothing judged or acked and the message still on the server. Then it runs the checks in this order, and only a message that passes all of them is ACCEPTED. Errors stay `application/problem+json` (§13).


**The checks, in order:**
1. **Decryption** with every RETAINED prekey (`age -d -i 2.agekey -i 1.agekey`; age tries each). An AEAD failure means the message is not for these keys.
2. **The layout** (§4.4): an envelope line, then a signature block starting on line 2 and ending at the first END line, which a line feed follows. Nothing after it is read.
3. **The envelope is one JSON object, as §0b reads one**: UTF-8, keys matched exactly and none twice in any object in it, nested at most 32 deep, so no two readers take different values from its fields (`BODY` is an unknown key, never the body; the body itself is the sender's JSON, held to the same rules and passed on as it is).
4. **The sender's identity document**, from the envelope's `identity`: base64 in its one encoding, the two-line form with its key in its one encoding, a key that passes the key checks (§2). **`from` must be its hash.** A well-formed document of a key type this client does not verify, whose hash is `from`, is refused as `unsupported_key_type`: nothing is wrong with it, and nothing it signed can be checked here. The document is read before the signature is checked, which is sound: it proves itself by its hash, and the signature must then verify under it.
5. **The signature**, over line 1 exactly as decrypted, namespace `irongall-msg-v1:<B>`, by a working key under a certificate of that identity that holds now (§2b) — never the server's word.
6. **The rest of the envelope,** in this order: a body, and every member of its type (`from` and `to` are addresses, in lowercase hex); `v` the integer 1, written as one (§0b); `to` this box; a `msg_id`, in its one form (§4.2); and **the time it states:** `sent_at` no older than 33 days, the TTL, and not before the box's floor (both `stale`, check 9), and no more than an hour ahead of this box's clock (`future`, §0). An honest sender's is not: it posts nothing dated ahead of its own clock, and a server takes its pass only while that clock is at most 50 minutes ahead.
7. **The server's `from` is the sender that was verified.** A mismatch is a server naming another box than the one that signed.
8. **Revocation** (§6.3): this box holds no revocation of the sender. The server is asked, by a read of the sender's box, `GET /v1/<from>` (§4.1), once for each sender in a drain: a revoked address answers `410 revoked` with its record. One that verifies refuses the message as `revoked`, and every later one from that address, **whenever it was signed**: nobody can vouch for when a signature was made. A server that serves the box with no revocation, or holds no such box, or says `revoked` and shows nothing that verifies, has answered that it holds none. **No answer is not an answer:** the drain stops, and the message stays on the server. The same read carries the sender's revocation of its certificates, if it has one (§6.3a): mail signed under a revoked certificate is refused as `certificate_revoked`, and the address goes on.
9. **Replay:** the LOCALLY recomputed SHA-256 of the ciphertext is not in the seen-set — never the server-supplied `id`, which a malicious operator could change. A listed `id` that differs from it is refused, and files are named by it. The seen-set keeps each message's hash, with its `sent_at`, `from` and `msg_id`, until `sent_at` + 66 days and an hour: a retry, dated afresh, may be posted up to 33 days after a first copy that was delivered (§4.5) and is fresh for 33 days after that, and the hour covers a step back of the clock by as much as two clocks a server takes are apart. So this check and check 10 cover every message freshness takes. **The set is pruned by the box's clock only once the server has taken that drain's pass, and by that pass's date** (§0), so a clock a server refuses prunes nothing. **A prune that drops a line first raises the floor the box keeps (§1) to its cutoff, and a `sent_at` before the floor, or less than 33 days above it, is `stale` whatever the clock reads:** a retry is dated up to 33 days after its first copy (§4.5), so a copy of a message whose line went may carry any `sent_at` up to 33 days above the floor. So a clock that steps back further reopens nothing either: what a Kerberos server that has lost its replay cache does, refusing until the window has passed (`PRECEDENTS.md`). The floor costs only mail that a hostile server took a pass for at a clock an honest one refuses, which it could withhold anyway: two clocks a server takes are under an hour apart, and the floor refuses nothing that freshness takes until the clock reads more than an hour behind the reading a prune dropped a line at. This is the only defence against an operator replaying old mail; the server's own dedupe (§7) spans a message's life, to its `expires_at`.
10. **Retry:** `(from, msg_id)` is not in the seen-set. A match is a re-encrypted retry of a message already delivered: it is acked, not delivered again.

**Who a sender is, is never asked of the server.** The message carries what proves it, and its identity is pinned only once everything above has passed: The one thing asked about a sender is whether a revocation of it exists (check 8), and the answer proves itself: a sender costs one call in each drain that holds its mail.

**What a refusal says:** a code from a closed set (`undecryptable`, `bad_message`, `bad_envelope`, `bad_identity`, `unsupported_key_type`, `bad_signature`, `reattributed`, `revoked`, `certificate_revoked`, `stale`, `future`, `replay`, `bad_id`; `README.md` has the table) and the client's own fixed words. It never prints a value, key or field of the envelope or of the identity it carries: whoever reads a refusal may be a model, and any registered box can send mail that is refused. Nor does it print a server's words (§13).

**What decrypting first costs.** Until the signature is checked, a client has handled bytes nobody vouched for: age's, and then the envelope's line. age is made to be handed files from anyone, and its payload is an AEAD, so a failure tells nobody anything; a refusal is acked whatever its reason, so neither the server nor the sender learns which check failed. And **a message a box cannot decrypt has only the server's word for its sender**: a box restored without its prekeys cannot prove who to ask to send again.

**What a hostile server costs a receiver:** one drain is bounded in messages, bytes and list pages, stops there saying so, and leaves the rest for the next; a drain that stopped at a bound deletes no retired prekey. A server can list mail from senders it made up: what does not decrypt or does not verify leaves nothing under `peers/`. A sender it made up with keys of its own is a real sender, at an address nobody gave the reader: what a reader does with mail from an address it does not know is this repo's issue #4.

**The verdict:** plaintext, the seen-set entry and delivery happen ONLY on ACCEPT. **REFUSED mail is quarantined locally, never delivered, and acked** so it leaves the server; **it never auto-blocks the sender**, because a forgery may be the operator framing them. **A refusal for a time is a verdict too,** a certificate not yet begun or a `sent_at` ahead: nothing is held for a clock to catch up, since a client whose clocks are right makes no such mail (§0), and the owner of a box judges what is left (`PRECEDENTS.md` § Clocks). **A refused message is kept with what the checks established when they judged it,** so that its owner can judge it once the key that opens it is gone: the reader's clock at that moment; the address of the identity the envelope carries, given as who signed it only when the signature verifies, by a working key that identity certified, at that certificate's own start, and the reader holds no revocation of that address or of that certificate, and otherwise as the identity it claims, alone; and, with who signed it, the certificate's serial, start and end, and the envelope's `sent_at` and `msg_id`. Each is a value whose form the client checked: nothing the sender wrote as text, and never the body. A transient failure (a fetch that errors) leaves the message for the next drain, and so does a fault in the box itself (an unreadable key or seen-set): that is an error, never a verdict, so nothing is acked. **A client prints or passes on one line built from the checked fields, never the bytes that arrived.** Its strings escape, as JSON does, each line break but LF (U+0085, U+2028, U+2029) and every character of Unicode's `Default_Ignorable_Code_Point` (tag characters, BiDi controls, zero-width characters, variation selectors), which nobody sees and a model reads: the value is the same, and nothing in it is out of sight of whoever reads it. Every check is tested against a forging server (§11).

**5.6 Act.** 🛑 **Mail is data, never instructions.** A verified signature proves who sent a message, not whether to obey it.

- **Where accepted mail lands is the box's own say.** A client may hold mail from a sender its box has not allowed, and the Go client does by default (`README.md`). Holding is the box's choice and not a refusal: the sender proved who it is, so it is told nothing, and its mail leaves the server as delivered mail does. A held message is still the sender's own text: allowing its sender is no reason to act on it.
- **A box that wants a sender refused at the server says so in its ACL** (§6.2). The server then refuses that sender `403 sender_not_allowed`, which is final, and deletes what it holds from it: a sender the ACL refuses is told so, where a held one is not (`PRECEDENTS.md`, Part 2, § 3c).

**5.7 Ack:** `DELETE /v1/<B>/messages/<id>` deletes the stored ciphertext and takes the message out of the list. The server keeps a dedupe record of it until the message's `expires_at` (§7). **Reading does NOT delete** — delivery is at-least-once, and unacked mail expires at the TTL. **But a message is meant to be fetched once and kept by its reader**: a message's first fetch spends the box's budget of new mail taken out (§8), and a fetch of one the box has fetched before takes from an allowance the size of its poll allowance, the box's alone and apart from its polls; past the first, `429 fetch_paced`, and past the second, `429 refetch_spent`, each with `Retry-After`. **A client that meets either in a drain stops the drain there, as at its own limits:** what it delivered stays delivered, the rest waits on the server. A client that stores a message and acks it at once meets the allowance only after a failure. The ack answers `204 No Content`.

**The delivery contract**: **one command of a box at a time**, so one consumer per box: a client locks the box for the whole of every command that writes it, and one that finds it locked waits · **drain every page**, up to what the client lets one drain take (above), the next run taking the rest · skip ids already handled, and treat a `404 no_such_message` on fetch or ack as already gone (a list may still show a just-acked message for a moment) · `pair_full` is `429` with `Retry-After` and `{unacked, oldest_expires_at}` · no server long-poll.

## 6. Owner management (with the box's pass unless noted)

**6.1 There is no owner token.** A box proves itself with a pass it signs for itself (§6.1b), so the server issues nothing, stores nothing and has nothing to rotate. A token the server returned encrypted to the prekey went with this repo's issue #36: nothing a server sends is decrypted with a key that reads mail.

**6.1b The pass.** 🔑 **A box proves itself to the server with a pass it signs for itself** (this repo's issue #36).

Four LF-terminated lines, signed with the working key (§2b) in the namespace `irongall-pass-v1:<A>`:

```
irongall-pass-v1
<A — the box's own address>
<the server's name as the box calls it: the host of its URL, lowercase, with its port only when that is not the scheme's default>
<not_after — RFC 3339 UTC to the second>
```

```sh
printf 'irongall-pass-v1\n%s\n%s\n%s\n' "$A" irongall.dev "$NOT_AFTER" | ssh-keygen -q -Y sign -n "irongall-pass-v1:$A" -f work-cert.pub > pass.sig
```

- **A client writes it as** `Authorization: irongall-pass address="<A>", not_after="<not_after>", signature="<base64 of pass.sig>"`, in exactly that form and on one `Authorization` line, on every call a box makes as itself, a send included: a request with two is no pass, `401 unauthorized`. The read of a box, `GET /v1/<address>`, which anyone may make, takes none: a server counts it against the address it comes from, whatever `Authorization` it carries, and reads no pass on it (§4.1, §8). Nor do the link page and `PUT …/revocations`.
- **A server reads it as RFC 9110 §11 lets a recipient read credentials** (IronGall-dev/irongall-server#18): the scheme in any case, then one space or more; the three parameters in any order, each name in any case and given once, and no other name; optional whitespace around each comma and each `=`, and empty list elements skipped (RFC 9110 §5.6.1.2); each value a token or a quoted-string. A quoted-string holding a backslash is refused: none of the three values holds a character that needs one. Each value is then held to its own form: the address as 64 lowercase hex, `not_after` as RFC 3339 UTC to the second, `YYYY-MM-DDTHH:MM:SSZ`, and the signature as the padded standard base64 of `pass.sig`. Every form a server takes, and each it refuses, is a vector (`testdata/vectors/pass/`). The signature covers the statement built from those values, never the header's text, so how the header is written changes nothing a pass says. The value is at most as long as the form a client writes with a signature of the most any identity key type allows, 4,096 bytes (§3), whitespace a sender adds counted too: a server refuses a longer one, `401 unauthorized`, before it hashes or parses it.
- **A client signs a pass good for 10 minutes. A server takes one that has not run out and runs out at most an hour from now.** The hour is the server's ceiling, not what a client asks for: a client whose clock runs up to 50 minutes fast is still taken, and so is one less than 10 minutes slow. That window is the one every other time in the protocol is made to fit (§0).
- **A client keeps its pass and uses it for every call until it is about to run out,** so a server verifies one pass for ten minutes of calls. A server may remember a pass it has checked, by one written form of it: every form a verifier reads as the same pass, its signature's armor and SSHSIG blob included (§3), is one. A kept pass with more than ten minutes left is not used (§0).
- **The server's name is written as an origin is** (RFC 6454 §6.2; RFC 9110 §4.2.3): the host of the box's URL for the server, lowercase, without any user before an `@`, and then its port as a number, only when that is not the scheme's default. `https://irongall.dev:443` and `https://irongall.dev` are one server, named `irongall.dev`; `http://127.0.0.1:8080` is named `127.0.0.1:8080`. **A server writes the `Host` a request names the same way, and drops a port of 443 or 80 alike:** where TLS ends in front of it, it cannot tell which scheme a client called it by. A client that calls `https` on port 80, or `http` on 443, names a port the server drops, and its pass is refused.
- **A server takes a pass only** under the box's current certificate, and for a name that is the server's own. **The exception is how a box gets a certificate on record at all:** a registration (§3) and a prekey upload (§6.4) carry a pass under the certificate of the statement they bring.
- **When a pass is refused:** `401 pass_expired` if it, or the certificate it is under, is not valid at the server's clock (it has run out, runs out more than an hour ahead, or its certificate has not begun or has ended); `401 certificate_revoked` to every call that takes a pass while the box's current certificate is one its identity revoked (§6.3a), answered before any pass is read; otherwise `401 certificate_not_current` if the pass is under any other certificate than the one the call takes a pass under, revoked or not (or the one on record does not verify), with that certificate's serial in `certificate_serial`; `401 unauthorized` if it is no pass, or not this box's, or not for this server. On any of them, a client signs another and tries once more, and no more than once. **A pass refused twice for its time is the clock:** the client sets the date on the server's answer beside what its own clock reads (§0).
- **It says who is calling and until when, and nothing of what a call does,** so the pass hands a server no proof of any send. The server still knows who sends to whom.
- **What a leaked pass gives,** for the minutes it has left and at that server only: the box's metadata and its ciphertext, and owner-level control of AVAILABILITY — **irrecoverable deletion of unacked mail**, taking the box out of its account (§6.5), posting in the box's name (§4.5), and its ACL (§6.2), with which it can pause the box until its owner writes the next. **It never gives plaintext**, it signs no mail and no prekey, and it cannot end the address, which only the identity's revocation does (§6.3). Agents leak credentials — transcripts, logs, world-readable files — hence a box's directory that only its owner reads (§1), and hence ten minutes.
- **Who else does this, and their lifetimes** (GitHub Apps, Google service accounts, Web Push's VAPID, Apple's push service): `PRECEDENTS.md`, Part 2, § 1.

**6.2 Profile, ACL.** **The profile is specified and not built: an addition inside v1, which the freeze does not wait for (§12). No route exists, and whether a box needs one at all is open. The ACL is built.**
- **Profile**: signed JSON `{version, schema, max_size}` — `version` an integer that only ever increases, `schema` (optional) a JSON Schema for the envelope's `body` (§4.2), `max_size` (optional) in bytes. Readers ignore unknown fields. It has no free text: a sender reads it before it writes, and text a box writes would be an input path into the sender. Sign it from stdin with the working key, `ssh-keygen -q -Y sign -n "irongall-profile-v1:$B" -f work-cert.pub < profile.json > profile.sig`, then `PUT …/profile` with JSON `{profile, signature}`, both base64. The read of the box carries it, as members a v1 client ignores (§4.1). Senders verify it as they verify a prekey statement, under a certificate of B's PINNED identity (§2b), before following it, and keep the highest `version` they have seen. The server refuses a PUT whose `version` ≤ the current one (`409 conflict`), so an older validly-signed profile can never be served back. The profile is advisory: the server cannot see inside the ciphertext.
- **ACL: whom the server takes a box's mail from.** Read as a Matrix room's server ACL is: **a box with no ACL takes mail from everyone; with one, `deny` is checked first, then `allow`, and a sender neither matches is refused** with `403 sender_not_allowed` (§4.5 step 8). `PUT /v1/<B>/acl`, with the pass, replaces it whole with JSON `{allow, deny}`:
  - **Each entry is an address, or `*`, which matches every address,** and there is no other pattern. Repeats are taken once.
  - **`allow` is required:** `["*"]` is everyone and `[]` nobody. A document without it is `400 bad_request`, where Matrix reads a missing one as nobody: so an ACL always says whom it lets in, and a writer that drops an empty list is refused, not read as letting in everyone. `deny` may be left out, for none.
  - **More entries than the server takes,** in both lists together, is `413 too_large`.
  - **It answers `200` with the ACL as held, and no `ETag`:** `*` first, then each address once, in ascending order of its hex. What the server holds may not be what was sent, so the answer carries no validator, as RFC 9110 §9.3.4 has it (`PRECEDENTS.md`, Part 2, § 3c).
  - **`GET /v1/<B>/acl`, with the pass, answers the ACL as held, in the same order, with its `ETag`;** a box with none answers `{"allow":["*"],"deny":[]}`, which is what none means, so there is no `DELETE`. The `ETag` is a strong validator of the ACL as held (RFC 9110 §8.8.3): the server's, opaque, and changed whenever the ACL's lists change; a box with none has one too, that of the ACL it answers. A writer that wants the tag reads it here.
  - **A `GET`'s preconditions are read as every call's are (§13),** in RFC 9110 §13.2.2's order, after the pass and only where the answer without them would be `200` (§13.2.1): an `If-Match` that is false, compared strongly, is `412 precondition_failed`; then an `If-None-Match` that names the ACL's tag, compared weakly, or is `*`, is `304`, with the `ETag` and no body.
  - **A `PUT` may carry `If-Match`, so that it replaces only the ACL its writer read** (RFC 9110 §13.1.1). It is read as a list's is (§5.1) and compared strongly with the tag of the ACL held now, a box with none included: `*` is true, a tag is true when it is that one, and a value of any other form is false. It is evaluated after the pass and before the body is read (RFC 9110 §13.2.1), and one that is false is `412 precondition_failed`, with nothing changed; so is an `If-None-Match` that is `*` or names the ACL's tag, since a box always has an ACL (§13). **A `PUT` without one replaces whatever is held.** No writer chooses a number, so no ACL is the last a server takes: a leaked pass can write one while it lasts (§6.1b), and the owner's next replaces it (this repo's issue #360).
  - **What it denies is deleted:** the box's unacked mail from every sender the new `deny` matches is deleted with the change, so a block frees what that mail held of the box's caps. A send that passed the check while the ACL changed may still be stored after it.
  - **A box pauses with it:** `{"allow":[],"deny":["*"]}` refuses every sender (`403 sender_not_allowed`, final for the message) and deletes the box's unacked mail, and a later ACL lets senders in again; what the pause deleted stays deleted. There is no delete of a box (§3a).
  - **It is not signed:** only its box reads it back, and only the server acts on it, so a signature would guard against nobody. A pass is enough, and a leaked one can change it (§6.1b).
  - **It sheds load and protects nothing a reader relies on.** A server that ignores it gains nothing it could not do already: it can drop mail, and it can deliver what the box would hold. The box's own checks are where a reader is protected (§5). What a server learns from it is in §9.

**6.3 Revocation — permanent, signed by the identity itself, no pass.** A box's identity can end its address for good, and nothing else can: no working key, and no server of any kind. Revoking certificates, and keeping the address, is §6.3a.
```sh
printf 'irongall-revoke-v1\n%s\n' "$A" | ssh-keygen -q -Y sign -n "irongall-revoke-v1:$A" -f "$IG/identity" > revoke.sig
jq -cn --arg i "$(base64 < "$IG/identity.doc" | tr -d '\n')" --arg s "$(base64 < revoke.sig | tr -d '\n')" '{type:"revocation_record", identity:$i, revocation_signature:$s}' > record.json
curl -X PUT -H 'Content-Type: application/json' --data-binary @record.json "$IG_BASE/v1/$A/revocations"
```
- **The statement is fixed text:** `irongall-revoke-v1`, LF, the address, LF. No date, no reason, no number. Whoever checks a revocation rebuilds the statement from the address, so nothing in it is parsed, and a copy signed at any time is the same statement. Its format never changes (§0a).
- **The signature is the identity key's own,** in the namespace `irongall-revoke-v1:<address>`, with either hash SSHSIG allows (§0). It is the one thing an identity signs beside certificates. **A working key's signature over the same statement is not a revocation,** though it is a good signature under a certificate of that identity: a working key can be stolen without the identity, and must not be able to end the address. A verifier's `allowed_signers` line names the identity's key with no `cert-authority`.
- **A revocation proves itself.** The record is `{type, identity, revocation_signature}`, its members in any order: `type` is `"revocation_record"`, and the identity document and the armored signature are base64. Every member that holds a signature is named for it, `…_signature`. Anyone holding the address checks it with nothing else: the document hashes to the address and passes its key checks (§2), and the signature verifies under the document's key. So a record is worth the same from a server or from a file a person handed over.
- **A record names its own type, so one JSON text is the record everywhere:** what a person keeps, the body of the `PUT` below, the `record` every `410 revoked` carries, the answer to `GET …/revocations` (below), and the record a client prints for its owner to keep. Every writer writes `type`, in no set order, a server in its answers and a client in what it sends, keeps and prints (decided on this repo's issue #355). A reader takes a record that leaves it out, since the route says what the body is, and takes one that names any other type as no record: a server answers `400 bad_request` with `type` as its `member`, and a client takes such an answer as no answer. Kubernetes objects carry their `kind` the same way (`PRECEDENTS.md` § 3e).
- **There is one kind, and it reaches back.** Once a client has verified a revocation it takes nothing signed for that address, **whenever it was signed**, and sends it nothing. A revocation states no time, and nobody could vouch for one: mail's `sent_at` is its signer's own word. A box that is only retired stops renewing and is forgotten (§7), and its key is destroyed, which needs no statement.
- **Nothing undoes it:** not a later answer from a server, and not a later record. A client keeps a revocation it has verified, of a peer or of its own box, and never removes it.
- **A box that holds its own revocation is finished, whatever any server answers.** It signs nothing more as that address: no pass, no mail and no certificate, so a send is never posted, and a drain, a renewal and every call that carries a pass are refused before anything is asked. A server that never saw the revocation would take it all: one that was down when it was published, one that answered `2xx` and kept nothing, or another server the box is pointed at. It still asks, keeps and publishes the record, which carry no pass. One it keeps that no longer verifies is a fault, and stops the same.
- **A client takes "revoked" only with the revocation in hand.** A `410 revoked` or a `403 sender_revoked` is a server's word. **Every `410 revoked` a server answers from a record it holds carries that record in `record`,** the read of the box's (`GET /v1/<address>`) always; RFC 9457 §3.2 lets a problem type add members. A client verifies a carried record exactly as it verifies the read's, and reads the box only after a `403 sender_revoked`, or a `410` that carries no record or one that does not verify (this repo's issue #353). A record that verifies makes it final: the message is never posted. Without one the call has failed and nothing more: the message stays in the outbox and no state changes. **What a server shows that does not verify counts as nothing shown.**
- **No answer is not "not revoked".** Where a client asks, about a sender in a drain (§5, check 8) or about a recipient before a post (§4.1), a box served with no revocation, `404 no_such_mailbox`, or `410 revoked` with nothing that verifies is an answer that it holds none, and the client goes on. Anything else stops the drain, a `2xx` whose body is not a box as §0b reads one among it, with the mail still on the server, or leaves the message in the outbox with nothing posted. That is the box's own server, the one its mail passes through. A server can still answer falsely that it holds none: the limits, below.
- **When a client asks, and what it keeps.** It asks before every post, of the recipient, by the read of its box (§4.1); in a drain, once of each sender (§5, check 8); and whenever its owner says. Each time it reads the box from its own server. **Whatever it has verified about an address, from any source and at any time, it keeps for good, and that is what a send and a read are checked against, with no call to anyone.** "None held" is kept nowhere. Nobody signs it, so it carries no time it holds until, and the next post asks again.

**The calls, with no pass needed:**
- **`PUT /v1/<address>/revocations`** with the record, and no pass. The server checks it as any client does and keeps it for good; a box at the address it marks revoked for good, and deletes its mail: `201 {}`. **Anything sent for a box already revoked is `410 revoked`, with the record,** answered from it before any signature in the body is checked, since nothing could change it (a body that is no record, or names another address, is refused as such first); a client that published a revocation takes that `410` as done once the record it carries verifies, or, where it carries none that does, the record its read of the box then carries. The revocation of an address is counted against no box: what a server counts of it is its caller's address's alone (§8), and past that count it is `429 rate_limited` with `Retry-After`, to send again then or from another address. A record whose document does not hash to the address is `400 identity_mismatch`; one that does not verify is `400 bad_revocation`. **A server keeps a record for an address it has no box for as well,** one never registered or forgotten, and holds a later registration of that address to it: `410 revoked` while the address is revoked, and no certificate the identity revoked (§6.3a). Keeping one for an address it holds nothing of is keeping a record for good, so a server may count that call as it counts a registration (§8).
- **The read of the box, `GET /v1/<address>`** (§4.1), carries what a mailbox server holds: a revoked address is `410 revoked` with the record in `record`, and a box served carries the revocation of its certificates. It takes no pass (§4.1).
- **`GET /v1/<address>/revocations`**, with no pass, answers what a server keeps of any address, with a box there or none: `200` with the record, or `404 not_revoked`. A box reads its own so where its server holds no box for it (§2b), whose read of the box would carry nothing.
- **A revoked box** answers `410 revoked` to every other call, its pass is taken nowhere, a send from it is `403 sender_revoked`, and its address can never be registered again (§3a). Its mail and its record are deleted; the revocation is kept for good.
- **No API answer may be kept by a cache:** every answer under `/v1/` carries `Cache-Control: no-store`. A `410` is cacheable unless it says otherwise (RFC 9110 §15.5.11), and an answer served again from a cache would be the server's word outliving the fact: a prekey since replaced, or a box since revoked.

**A record made in advance.** The statement has no date, so a box's owner can make the record at any time and keep it for the day the box is lost: it is exactly the body of the call above, and publishing it later needs no box and no key, only the file (`README.md` has the commands). **Whoever holds the record can end the address,** so it is kept somewhere other than the box: beside the identity it is lost with it and stolen with it. Neither client writes one unasked. Without a record, a lost identity cannot be revoked: the address stops taking mail when its prekey expires, and its correspondents are told the new address out of band.

**Who can revoke.** Whoever holds the identity key. For its owner that is the end of a stolen key. A thief holding it can revoke too, which ends the address and gains the thief nothing: the outcome the owner wanted. (A thief with the identity can also certify a working key of its own and read new mail until the owner revokes: the identity is the box.) A client publishes a revocation only with the address written out in full, as its confirmation.

**One source.** A box asks about revocations, and publishes its own, at its own server alone. Every server keeps a record of any address, with a box there or none (above), so an owner can revoke an identity before anyone registers it. A second server a box could list beside its own was weighed and dropped (`PRECEDENTS.md`, Part 2, § 3b): a revocation is signed by the identity, so no server can make or undo one, and withholding one is a server's only power, which a second server tells against only where the revoked box's owner and its reader both list the same one.

**The limits.** A server can keep a revocation from a peer that has never seen it: it answers that it holds none, and nothing tells the peer otherwise. Asking before every post narrows that in time and no further: what a client was shown while a server answered truly, it holds after that server stops. What answers a server that hides a record from the first is a record from the box's owner, out of band: a record handed over is checked and kept as a served one is. This protocol puts no bound on how long a revocation can go unseen by a peer whose server hides it. The usual answer to that is a log of what a server serves, which clients check (key transparency), and this protocol has none.

**6.3a Revoking certificates — the address goes on.** A working key can be taken without the identity (§2b). The identity then revokes every certificate it made up to and including a serial, and keeps its address: the box goes on under a new certificate.
- **The statement is exact text:** `irongall-revoke-certs-v1`, LF, the address, LF, a serial, LF. The serial is an integer from 1 to 2^53 − 1, as a prekey's is (§2a), with no leading zero. Nothing else is one: no other line, no CR, no byte after the last LF.
- **The signature is the identity key's own,** in the namespace `irongall-revoke-certs-v1:<address>`, as a revocation of the address is (§6.3). A working key's signature is refused, so a certificate cannot revoke another, or itself.
- **It revokes every certificate of the address whose serial is at or below its own, and the highest stands.** Whoever holds one keeps the highest it has verified. One through a lower serial changes nothing, whenever it arrives, at a client or at a server, so a certificate once revoked is never taken again. The serial is its own order, and nothing else numbers it. It is how AWS, Entra ID and Firebase revoke what was issued before a point, with a serial where they use a time (`PRECEDENTS.md`, Part 2, § 3b).
- **What a revoked certificate loses,** at whoever has verified the revocation: a reader refuses mail signed under it, whenever it was signed (`certificate_revoked`); a sender refuses a prekey statement signed under it, at every post, of a new message or of one that waited (§4.5); a server takes no pass and no prekey statement under it, and answers a send to a box whose current statement is under it `409 prekey_expired`, since the cure is the same: the box publishes a new prekey, under a new certificate. And the box itself signs no mail under a certificate it holds revoked, whatever its server took: a send waits in the outbox until the box's renewal is taken, which is the remedy's window below.
- **It rides in the record of §6.3.** The read of a box carries it as `revoked_certificates` and `revoked_certificates_signature` (§4.1), and a revoked address's `record` beside the revocation; `GET /v1/<address>/revocations` → `{type, identity, revoked_certificates, revoked_certificates_signature}`, with `revocation_signature` too if the address itself is revoked; and `PUT` of the same, with no pass. One that is taken is `200 {}`, and so is one through the same serial again; one through a lower serial than the one held is `409 conflict`. Both are answered before the signature is checked: neither could change anything. Any other that does not verify is `400 bad_revocation`. A body may carry a revocation of the address beside it. Beside one, a revocation of certificates no higher than the one held changes nothing, whether or not it verifies, and the address's revocation is kept once it verifies (`201`). Any other part that does not verify refuses the body whole (`400 bad_revocation`), and nothing in it is kept. A box already revoked takes nothing more (`410 revoked`, with its record, §6.3). **A raise of it is the identity's act,** counted against the box on a count of its own, which no renewal spends (§8). A reader gets it with the one read of each sender's box it makes in a drain (§5, check 8), and a sender with the read of the recipient's before each post (§4.1).
- **A box makes no certificate its identity has revoked:** its next certificate is numbered above the highest serial it holds revoked as well, or its server shows it revoked, read at every renewal (§2b). So one through a serial far ahead of the clock, a slip of a digit, moves the box's numbers above it, and one through 2^53 − 1 leaves no certificate to make: the box cannot renew, as one whose certificate has that serial cannot. Ending an address is §6.3's.
- **What it costs its owner:** mail the box sent under a revoked certificate, and that its reader has not read yet, is refused with a thief's. Nobody can tell them apart, so it is sent again. Mail waiting in the box itself stays: its owner reads it after the renewal.
- **How long one is kept is not fixed here.** Every certificate it covers ends within 66 days of being made (§2b); a server or a client may keep it for good.
- **The remedy for a taken working key** (§6.4) revokes, then renews, in that order:
  - **It reads what is held first,** at the box's own server, and keeps what verifies of the box's own revocation of its certificates. An answer it cannot use stops nothing (no answer, a statement that does not verify, one ordered before what the box published): the revocation still goes to the server (§6.3).
  - **It revokes every certificate below the number its clock gives,** through the serial one below it, or signs again one through a higher serial that is held already, and publishes that to the box's server (§6.3). A serial is the time its certificate was made (§2b), so that covers every certificate made before it on any machine, whether this box knows of it or not, but for one a lost machine made while its clock read ahead of this one's and never published (§2b): a later run of the remedy covers that. It publishes once. A server that holds a higher one it did not show answers `409 conflict`: that one covers every certificate the box's would have, so the client reads the box again, keeps it once it verifies, and renews above it. A conflict that shows none that verifies and covers them stops the remedy there, with nothing renewed: a server holding a higher revocation would refuse a renewal under it.
  - 🔑 **Only then does it renew,** under a new working key and certificate numbered one above the revocation, so the new certificate is never revoked as it is made, and it sends nothing an earlier renewal left, since whoever copied the box while one waited holds its working key. Once the box's server holds the revocation, it takes no pass and no statement under the certificates it covers, the one the box was using among them, so whoever holds that working key can spend none of the box's calls; and the renewal that follows spends none of the box's counts, the identity's certificates and the calls a taker spent before the revocation among them (§6.4). Until the server takes the new prekey the box signs no mail, and once its server holds the revocation it takes none there either. A box whose own revocation covers the certificate it uses renews at its next drain.
  - **A clock that reads ahead numbers the revocation ahead,** as it numbers the certificate made with it: the box's later certificates are then one above it until the clock passes it, as after any certificate made while that clock read ahead (§2b).
- **The same limit as §6.3:** a server can keep a revocation of certificates from a peer that has never seen it. A sender asks before every post (§4.1) and a reader for each sender in a drain, so it reaches whoever asks a server that shows it, and holds from then on whatever that server does later. A server that hides it from its first answer is not caught by asking it. What tells is the record from the box's owner, out of band.

**6.4 Prekey renewal — required, a new key every time.** **Each renewal is a new prekey, a new working key and a new certificate, under one number that the box's clock gives (§2b).** **A box's prekeys are valid for 33 days, or for a shorter lifetime its owner sets, from a day and three hours:** the day a client may wait to renew, an hour of slip for when it runs, an hour for the renewal's own calls (the read of its own box, the upload), and the hour of §0 for clocks, which a box leaves as the maker of the prekey. So a box that renews within its lifetime less a day and two hours renews with those two hours of the prekey left, and a sender whose clock a server takes still takes it; one that renews later has its senders refused until it does. A client times its renewals and its deletions by its own record of when it signed each prekey, never by the statement's `not_after`: a prekey with no record is renewed at once, and every retired key is kept while the newest has none. Recovery needs only the identity, and no record of the numbers the lost machine used. How often the Go client renews, and how often `recv` must run for a lifetime, are its own (`README.md`, `irongall prekey lifetime --help`).

- **`PUT /v1/<A>/prekey`** with `{prekey, prekey_signature}`, and `sender_key_types` if the box declares any (§2c), carrying a pass under the certificate that statement is signed under. **The authority is a statement ordered after the current one (§2b), signed by a working key the identity certified; no pass under the box's CURRENT certificate is needed.** That is the way back for a box that lost its prekeys or its working key — a restored machine, an ephemeral agent's second session — and it is how a box moves to a new certificate.
- **The server** answers an identical retry from its record, once its pass is checked, and reads where any other statement would stand in the order before checking its signature: one that could not be taken even if it verified is refused with no signature check, so a statement both out of order and badly signed is `409 conflict` or `401 certificate_not_current` by its order. It then verifies the statement as at registration (§3 steps 4, 6 and 7), and requires it to be ordered after the current one (§2b): under a certificate of a higher serial, at any prekey serial, or under the box's current certificate at a higher prekey serial (one that is not higher is `409 conflict`). A certificate of a lower serial, or another certificate of the current serial, is `401 certificate_not_current`, and one the identity has revoked (§6.3a) `401 certificate_revoked`. And it **refuses a key equal to the current one or to any live retired one** (`400 prekey_not_new`: "every prekey must be a NEW key"). The new prekey becomes current and its certificate the box's current one, so no pass under an older certificate is taken again, and the answer is `200 {}`. The declaration that came with the new prekey is the box's from then on (§2c). A deleted box is `404 no_such_mailbox`: it comes back by a registration (§3). **A server counts a box's renewals two ways:** those under the box's current certificate, which a holder of its working key can make, apart from those under a later certificate, which only its identity can (§2b). One while the box's current certificate is revoked is not counted, and spends none of the box's calls: it replaces a certificate its identity revoked, whose taker may have spent them before the revocation, and each raise of that revocation is counted instead (§6.3a). Let's Encrypt exempts more renewals, from every limit, and why ours differs is `PRECEDENTS.md`, Part 2, § 4, Limits. So whoever took a working key cannot spend the identity's way back. Past either, `429 rate_limited` naming `renewals` or `certificates`, with how many a day in `limit`, and a `Retry-After` until one more comes back; an identical retry is neither. A client that makes a new certificate with every prekey, as the Go client does, makes every renewal of the second kind. **The server keeps only a box's newest retired prekeys** (how many is a server setting), each until its `not_after`.
- **The owner** renews before `not_after`, decrypts with every retained key (`-i new -i old`), and **deletes retired keys at their deletion time** (Terms). It deletes by its clock only once a server has taken a pass dated by it, and by that pass's date (§0): a drain's once its list is answered, a renewal's once it is taken. The working key before the new one is deleted at once: what it signed is signed.
- 🔑 **The forward-secrecy claim: forward secrecy for every box, bounded by how often it checks in, given a client that deletes retired keys.** Precisely, with the Go client: a message is unrecoverable from the box's keys by the box's second renewal after it arrived — about two days in a box received daily, about two months in one received monthly — and mail waiting on the server is exposed until the box fetches it, as in any scheme. With `irongall.sh`: at most 66 days after its prekey was published (33 + 33). A box that stops renewing keeps its expired prekey as its current one, so its last messages stay exposed until it renews. A box that no server takes a pass from keeps its retired keys past their deletion time too, until one does: it cannot tell its clock far ahead from a server that refuses it, and deletes by that clock no key that mail may wait for. After that a message is unrecoverable from the box's keys, by the operator, Cloudflare or a past breach. That needs a client that really deletes, as both clients here do; a key kept in a backup, a synced folder or a secrets manager voids it. There is no per-message forward secrecy and no post-compromise healing of the encryption: v1 has no ratchet (decided on this repo's issue #31).
- **A serial is signed once.** A renewal the server did not take is sent again exactly as it was signed, which the server answers as an identical retry, and a new key is signed, at a later number, only once that statement has expired, was made for longer than the box's lifetime now allows or has no record of when it was made, is at or below a serial the box's identity has revoked (which every renewal asks for, §6.3a), is under a certificate that began less than an hour before the box's clock, so was made while the clock read ahead (§0), or another key type is wanted; the passed-over key is kept and deleted as a retired one. Signed again with a later `not_after`, the same key would stay in service for as long as a server refused renewals and kept the uploads: 40 days of failed renewals would give 39 statements for one key, the last good to day 73. So a key is encrypted to for at most its lifetime after it was signed, 33 days or less, whatever a server does. While a renewal waits, a box holds two working keys: the one the server knows it by, which signs its passes, and the one the waiting statement is signed with.
- **A box that does not renew** gets `409 prekey_expired` for every send to it once its prekey's `not_after` passes, and signs no mail of its own once its certificate has 33 days or less left (§2b). Its address and the mail already in it stay, and it can poll while its certificate lasts. Once that has ended, 65 days after its last renewal, the server takes no pass from it: a renewal is then the only call it can make, and the one that brings it back, while the server keeps the box. Past its record's expiry (§7) the server may forget it at any moment, and its read and its renewal are then `404 no_such_mailbox`. **A client then sends the renewal as a registration** (§3), numbered above what the box published, which brings it back as a new box. A box restored from its identity alone then has no prekey served or published to keep the type of: its prekey is post-quantum unless its owner says otherwise.
- **A compromised prekey:** renew it. A sender that has seen no newer serial can still be served the old statement until its `not_after` (§9). **That window is the lifetime, which a box that renews often may set short:** forward secrecy stays about two renewals, and what a shorter lifetime bounds is how long a stolen prekey, or a stale statement served to a sender new to the box, can be encrypted to.
- **A compromised working key:** the remedy (§6.3a). A renewal alone moves the server to the new certificate, so it takes no pass and no statement under the old one, and a sender that has seen the new one refuses a prekey under the old. Whatever prekey was published with the taken key, at any serial, the new certificate passes it (§2b). But whoever holds the taken key can hold a renewal alone back by spending the box's calls with its pass, and mail it signs still verifies at a recipient until the old certificate ends, if a server delivers it. The revocation of that certificate ends both: the server takes nothing under it, and a recipient that holds it refuses that mail.
- **The type can change at renewal** (post-quantum ↔ `--no-pq`) with no address change.

**6.5 Accounts — adopt and leave.** A box may belong to one account at its server. **The protocol fixes only how a box joins and leaves one; what an account is for is the server's own:** it may lift a box's limits, bill for it, tag a box of its own, or not exist. A server with no accounts does not offer these routes, and a client reads the router's plain `404` as that (§0a). Nothing about the box's mail changes.
- **`PUT /v1/<A>/account`** (with the pass) with `{"key": "<adopt key>"}` → `200 {"account": "<id>"}`. One use of the key is spent, unless the box is already in that account. A box in another account moves. A client never takes the key as an argument, where `ps`, a shell's history and an agent's transcript keep it.
- **`DELETE /v1/<A>/account`** (with the pass) → `204`, in an account or not. An account can drop a box from its side too.
- **The adopt key** is `iga1_` and then base64url without padding (RFC 4648 §5), at most 1,024 bytes in all. What it encodes is the server's own: a client holds a key to that form and reads nothing else of it. A key this server did not make, or one that is spent, expired or revoked, is `403 adopt_key_refused`.
- **An account id**, as the answer names it, is 1–32 of `a-z`, `0-9` and `-`.
- **What an account changes is the server's,** within §8's limits. A cap on a ciphertext it lifts stays at most 16 MiB (§4.5). Over the sender's own cap, a send is refused before its body is read.

## 7. What the server stores, and for how long

How a server stores things is its own business. What it promises a client is this:

- **Per box:** the identity document, the state (§3a), the current prekey statement and its signature as it was sent, the serial of the certificate that statement is signed under (§2b), the sender key types it declared (§2c), the newest retired prekeys' type, `not_after` and key hash (only to refuse a key that comes back, §6.4), when the box was created, the account it is in, if any, and its ACL (§6.2). No private key, no token, no pass and no last-seen time (§3a).
- **Per address, box or none:** what its identity revoked, the signature that revoked the address and the highest revocation of its certificates with its signature, with the identity document, each kept for good and served to whoever asks (§6.3, §6.3a).
- **A box is kept until nothing valid for it is left.** A registration and every renewal keep it until the later of its certificate's end and its prekey's `not_after` plus the mail TTL, about 66 days on. Past that a server may forget it at any moment: it is then as if never registered (§3a), and its ACL, its account and its retired prekeys go with it.
- **Per message:** the ciphertext exactly as the send's body carried it, `from` (the box whose pass the send carried), the size, `received_at` and `expires_at`. Its id is the SHA-256 of the ciphertext. **No signature:** the message's is inside the ciphertext (§4.4).
- **A `200` or `201` to a send means the message was stored.** A failure before that answers 5xx, and the sender retries from its outbox (§4.5).
- **Mail expires 33 days less an hour and two minutes after it was received**, read or not: the TTL, less the hour whoever makes a time-limited thing leaves for clocks, and two minutes for a post's own time from its dating to the server's receipt that no pass bounds: its seal, and the second its dating truncates (§0). The request itself is bounded by its pass, taken only from a clock less than 10 minutes behind the server's. A post's `sent_at` is its sender's clock at the post (§4.5), which a server takes up to an hour apart from its own, and a reader refuses mail 33 days after its `sent_at` by its own clock, so a reader whose clock a server takes refuses no message as `stale` while the server still serves it. `expires_at` is the authority: the server never serves a message past it.
- **Reading does not delete; an ack does** (§5.7). An ack deletes the ciphertext. The id, `from`, the size and the times stay as the dedupe record until `expires_at`, so the server's dedupe spans the message's life, to its `expires_at`, even after an ack (§4 step 6).
- **A revocation of the address** (§6.3) does to every message in the box what an ack does to one, and the box's record goes with it; the revocation stays for good. An ACL does the same to the mail of every sender its `deny` matches (§6.2).
- **Lists are eventually consistent.** A list may show a just-acked message, or miss a just-stored one, for a moment. A fetch or an ack of a message that is gone answers `404 no_such_message`: treat it as gone (§5).
- **Bodies are served by the API itself, never by a redirect.**

## 8. Abuse levers

**What a server limits, and by how much, is that server's own.** No limit below is part of the wire: a server sets each as it chooses, and may add others. What a client must handle is how it meets one: a `429` with `Retry-After` (§13), unless a line says otherwise, which a client waits out and then retries, and the promises below, which every server keeps. A client needs no limit's number. The reference server documents its own with its code.

**The promises.**
- The same ciphertext posted again, of a send the server holds, is never refused by a quota; a budget may defer it (§4.5 step 6).
- A drain of a full box always completes: its pages are never refused, and its fetches may be paced, each `429 fetch_paced` saying when to go on (§5.1, §5.7), never stopped for good.
- A box's count is spent only by calls that showed its pass, by mail sent to it, and by its identity's raises of the revocation of certificates, which carry none (§6.3a). A count of an address is spent only by calls from it.
- The identity's acts are counted apart from what a working key can spend: a renewal under a later certificate apart from one under the current certificate, and one while the box's current certificate is revoked not at all (§6.4); a raise of the revocation of certificates on a count of its own (§6.3a); and the revocation of an address against no box (§6.3). So a holder of a taken working key cannot keep the identity from revoking that key's certificate, after which nothing under it is taken. What a server counts of a revocation is its caller's address's: one that does not verify as a check that failed, and one for an address the server holds nothing of as a registration.

**Who pays for a call.** A call with a box's pass is counted against that box. A call with none is counted against the IPv4 address or the **IPv6 /64** it comes from: every IPv6 end site holds at least a /64, so a per-address limit means nothing there. The read of a box takes none, and is counted against its address whatever it carries (§4.1). A server may count a call by a wider range as well: the reference server counts a registration by its /48 too, the range Let's Encrypt counts new accounts by. A check that fails, or a call that names a box that does not exist, is counted against its address before it is checked, so a caller past its count is refused before the work: it may then be refused a box that exists, or a new pass of its own. No caller is exempt: a registered sender could otherwise try any number of addresses.

**How a refusal names its limit.** Every limit but those with a code of their own, which change what a client does (`fetch_paced`, `refetch_spent`, `mailbox_busy`, `pair_full`, `mailbox_full`), is `429 rate_limited`, with whom it was counted against in `subject` and which limit in `quota_id`, from §13's closed set, as Google's `QuotaFailure` names a violation (`PRECEDENTS.md`, Part 2, § 4, Limits). A client says them in its own words. Where one call would spend several limits, a server's `Retry-After` is, as RFC 8555 §6.6 asks, when every limit it can read without doing the call's work lets the same call through, and the name is that limit's; a limit behind that work, a read of storage or a signature check, can still refuse the call once that wait is over. A send's sends a day are such a limit: only the dedupe (§4.5 step 6) shows whether a send is new mail that spends them, so a send past its calls is told the calls' wait, and a retry is never told the sends'.

**The levers, as the reference server has them:**
1. **Address secrecy** — the primary defence (§2).
2. **Budgets: a burst at once, then a steady refill.** For a box: its polls (a list's `Retry-After`, §5.1, is the interval the server asks for; a list without a cursor is a poll, a `304` among them, and a later page is a continuation only while the box holds mail after its cursor and that cursor is the one it was handed last, with an allowance of its own sized so that a full box always drains); its repeat fetches (§5.7); its other calls, a send, a renewal and a registration sent again among them; **the new mail it takes, from every sender together** (`429 mailbox_busy` to the sender; a retry spends none); and **the new mail it takes out**, its first fetch of each held message, which only its own calls spend (`429 fetch_paced` on the fetch; the drain stops, the rest waits, §5.7). For an address: its registrations, by its /48 too; what it names that does not exist or does not verify; and, sized for floods alone, as Let's Encrypt's per-endpoint limits are, every request but one that carries a pass the server has already checked, on a call that takes it, counted once and before anything is done for it (`requests`, §13). A box signs a new pass once in ten minutes, so its calls are its own but for that one.
3. **Numbers a day,** each a budget like the others: that number at once, then one back each time a day divided by it has passed, so a refusal's `Retry-After` is the time to the next, each box its own, and never a midnight every box is sent to. A sender's sends (`sends`), counted only for sends that carried its pass (§4.5 step 8); a box's renewals under its current certificate (`renewals`); its identity's certificates, a renewal under a later certificate but for one while its current certificate is revoked (`certificates`; §6.4); and its identity's raises of the revocation of certificates (`certificate_revocations`; §6.3a). Each is `429 rate_limited` naming it, with the number a day in `limit`. A lower send limit for a new box's first days (warm-up) is designed and not built.
4. **Unacked mail per (sender → box)** → `pair_full`, and a larger total per box → `mailbox_full`.
5. **Registrations per address** (§3 step 5), with which the reference server counts a revocation for an address it holds nothing of (§6.3). Proof of work is a lever a server may add; nothing in v1 carries it (§12).
6. **A box's ACL** (§6.2): `deny` first, then `allow`, checked before any count, so a send it refuses spends none. A list response carries metadata only (§5.1), so a box decides what to fetch.
7. **Accounts** (§6.5), at a server that has them: what lifts a box's volume, in what it sends, what it receives, what it takes out, and how large.

## 9. The operator's view

- **Sees:** addresses, identity documents, certificates and prekeys, who mails whom, each message's size to within a padding block (§4.3a), times, IPs, ciphertext, each box's passes, which account each box is in, and each box's ACL (§6.2): under an allow list, that names senders the box takes mail from that may never have written to it.
- **Never sees:** plaintext, private keys, age file keys, or any message's signature. **It holds nothing signed that says who wrote to whom** (§4.4): a pass names a box and a time, and no recipient and no message.
- **Can:** deny service; say a box is revoked when it is not, which a client checks and does not believe (§6.3); keep a box's revocation from a peer that has never seen it (§6.3, the limits); drop or delay mail (undetectable without receipts); delete mail; replay old mail (§5 defeats it); name another box as a message's sender (§5 defeats it); act as a box toward itself, which it could anyway; lie once in the ACL a box restored from its identity alone takes its lists from (the Go client's, #366), where an `allow` it adds lands a verified sender's mail in `inbox/` and not `held/`, and a `deny` drops mail it could drop anyway; serve a STALE prekey to a sender — but only one the box's working key signed, and only until its `not_after`, 33 days after the box signed it. The serial guards stop even that for every sender that has seen a newer one. **It can also serve altered instructions** — which is why `GET /v1/<addr>` is to serve data and pointers only (§12), hints name client commands, and the stock script comes from this repo.
- **Cannot:** read mail, forge a sender, re-attribute a message to another sender, substitute keys, revoke a box, or alter a message undetected — **against a client that verifies AND gates**: the Go client here, or `irongall.sh` from this repo.
- **Cloudflare** terminates TLS for irongall.dev today: a detail of how that server is run, not of the protocol. It sees what the operator sees, a box's passes included, and a pass would let it act as that box at the server for the minutes it lasts. It cannot read or forge mail either.

## 10. The echo box

A separate CLIENT process that irongall.dev's operator runs — NOT the mailbox server — holding its own box keys. **Mail to it is readable by the operator by definition.** It replies with the decrypted plaintext plus diagnostics, signed by its own key. That lets an agent prove its whole loop end to end: keys → address → certify → register → sign → encrypt → send → poll → decrypt → verify → ack.
- **It is `21804ec172dd0dbdca3d9a6d461799130324b42fa708b3bb727e18e0bfc07e59`, post-quantum.** **A second echo box, `7f87929a91aa19bd2ca3a833d33d66c2b2f09dc83b9e2987a6af66d12a9c6b4b`, has an X25519-only prekey** (`--no-pq`), for senders on age 1.2, which cannot encrypt to the first. It is the same program with its own identity, and everything below holds for both.
- **Its address is published deliberately** — the one exception to "no discovery of addresses". **It is fixed, permanent(ish), and hard-coded where clients look: `llms.txt`, `README.md` here, and the Go client.** The address is the SHA-256 of its identity, so a client holding it checks whatever identity the server serves; the server cannot redirect it. **The server knows no aliases**: what is published is the 64-hex address itself, and a client sends to it as to any box.
- **Its identity key is kept and backed up**, since losing it means a new address in every published place. **Its prekeys live in memory only**, and it renews at every start: renewal needs only the identity (§6.4), and no prekey reaches a snapshot or backup.
- **It is in the account `echo`** (§6.5): no daily limit and no budget of calls or of new mail, and replies up to the largest cap.
- **No reply limit of its own**: it replies once per message, and every sender's own limits bound those. Its account lifts its daily send limit (§6.5); the server has no special case for it.
- **It is `cmd/irongall-echo` in this repo.** It answers only mail that passes every check, with a signed reply naming the checks, the sender, `msg_id`, `sent_at` and the ciphertext's SHA-256, then the body as JSON. **A refused message gets no reply**: a refusal does not say whether its sender was verified, so an answer could go to any address. Mail sealed to a prekey from before its last start is refused.

## 11. Tested

**What a client is told to rely on is tested in this repo, with no server and no network:** `SECURITY.md` maps each claim to the tests that hold it, and `README.md` § Tests runs them. The tests and their names are in the code: the Go client against a fake server that plays the forging operator, each check of §3 to §6 with its forgery, and the stock script against a fake of its own, against the test vectors and against the Go client.
- **The crypto and container vectors are checked by tools this project did not write** (`testdata/vectors/README.md`): `age` decrypts each message vector with its prekey's published test identity to exactly its plaintext, `ssh-keygen` reads each certificate and verifies each signature at the vectors' time, and `sha256sum` gives each address.

## 12. Specified and not built, or not yet specified

Each names the issue that tracks it. Those whose outcome could change the wire are in this repo's milestone `M1: protocol freeze`, with the other questions that could; each of those is settled, built or taken out of v1 before v1 is declared stable.

- **Identity key types beyond the two of §2:** not built. Wanted first are the forms a key in hardware presents: `sk-ecdsa-sha2-nistp256@openssh.com` (a FIDO token, a Mac's Secure Enclave through Apple's own SSH support) and `sk-ssh-ed25519@openssh.com`, with signing through `ssh-agent`, since such a key cannot be read from a file (this repo's issues #41 and #3). Each is an addition inside v1 (§0a), so neither issue is in the milestone.
- **Profile** (§6.2, #23): no route exists, and whether a box needs one at all is open. When built, it is an addition inside v1 (§0a): optional members of the read of a box (§4.1), and a route to write it. So #23 is not in the milestone. The lists specified beside it are built as the box's ACL (§6.2).
- **Proof of work at registration:** a lever a server may add, and nothing in v1 carries it (settled on #25). A client sends a solution only once a server asks for one, so a server that starts to ask changes nothing for any other call, and refuses a registration without one with a code and a hint that a v1 client prints (§13). Its scheme, how a server says what it asks, and that refusal are defined when one is built.
- **Also not built, and it does not change the wire:** a lower send limit for a new box's first days (§8), a server setting.

## 13. Errors, signalling, logging

- **Every error body is RFC 9457 Problem Details** (`application/problem+json`), in AEP-193's form: `{"type": "tag:irongall.dev,2026-10-17:errors/<code>", "title", "status", "detail", "code": "<code>", "hint"}`, and a member of its own for each value the error carries (the table below). **Every value a `detail` names is also one of those members**, of the type the table gives (AEP-193: "All dynamic variables found in error detail must also be present as additional properties").
- **A client needs nothing from `detail`, `hint` or `title`, and shows none of them.** They are a server's words, for a person reading the body: `detail` explains the error, and `hint` names the fix as a client command (`irongall prekey renew`), never a raw shell line a malicious server could alter. Whoever reads a client's output may be a model, and the server may be hostile (§9), so a client says what a code means in its own words, with the members it has checked to their types (`PRECEDENTS.md`, Part 2, § 3d). Nor does it show other text an answer carries, as an HTTP library quotes it in an error (a status line, a header or trailer line, a `Location`, a list's cursor in the path it calls): a call with no answer it can read is named by its method and path, in the client's words. A client reads `code`, the members, `Retry-After` and `Date` on EVERY non-2xx.
- **`type` names the problem, and resolves to nothing:** a `tag:` URI (RFC 4151), the same at every server, which RFC 9457 §3.1.1 allows in place of a locator. Its date is a whole day, since RFC 4151 reads a month alone as its first day, which is before irongall.dev was registered.
- **A `code` is one of the closed list below, under the status the list gives it, beside a `type` that is its own** (`tag:irongall.dev,2026-10-17:errors/` and the code). A code a client does not know, one under another status, or one beside another `type`, is no code (a body that names its problem twice and disagrees names none): a client takes no branch on it and prints none of it, only the status, since any text can be made to fit a code's grammar. A member that breaks its type makes the body no answer at all (§0b).
- **A code names what a client does about the error.** One call that can fail for causes a client meets differently has a code for each; where the call itself tells them apart (a `too_large` on an ACL is entries, on a send bytes), one code serves.
- **401** carries `WWW-Authenticate`, the scheme a call must use, `irongall-pass` (§6.1b), followed by any auth-params a server adds (RFC 9110 §11.6.1).
- **A query parameter is read as a member is** (§0a): a server refuses one its call does not take, or one given twice, `400 bad_request`, naming it in `member`. A send takes its two serials (§4.5), and a list its `cursor` (§5.1); no other call takes one.
- **Every answer carries `Date`,** by the clock the server's checks read: that is how a refusal for a time says what that clock reads (§0).
- **An unknown route** gets the HTTP router's plain `404` or `405`, with no code: none in the map fits. Past a server's limit it is `429 rate_limited`, as any call is (§8).
- **429** carries `Retry-After` (RFC 9110), so clients pace themselves; RFC 6585 defines 429. **It is delay-seconds, digits alone,** as on a `503`: RFC 9110 also allows an HTTP-date, which a client would read on a clock that may be off (§0), and which a client reads as no wait. The IETF RateLimit header fields are not in v1: they are a working group's draft, not an RFC, and a server may add them later as headers a v1 client ignores.
- **The same ciphertext posted again gets `200` + the original receipt**, never a quota error, whatever has changed at the recipient since (§4.5 step 6); a budget's 429 may defer it. The reference clients seal afresh at every post, so theirs is a new ciphertext (§4.5).
- **Every call evaluates `If-Match` and `If-None-Match`,** as RFC 9110 §13.1.1 and §13.1.2 have an origin server evaluate each it receives, in §13.2.2's order: once it knows its target's state (its route, its method, its pass, and the read of its target) and before it acts. Where its answer without them would not be 2xx or `412` they are ignored (§13.2.1): a pass refused, a box that does not exist, a body the call refuses before it reads its target, are answered as without them. A body check a call makes before that read stays first, so a well-formed body whose signature fails is refused as it is without them. The target is what the path names: a box, its prekey, its revocations, its ACL, its place in an account, its mailbox, a message, the link page. **A target that carries no `ETag` matches no listed tag:** where it exists, `If-Match: *` is true and `If-None-Match: *` false; where it does not, `If-Match` is false whatever it lists, and `If-None-Match: *` true; a list of tags is false in `If-Match` and true in `If-None-Match` either way. Only a list's first page (§5.1) and an ACL (§6.2) carry a tag. A false `If-Match` is `412 precondition_failed`, and a false `If-None-Match` `304` to a `GET` and `412` to any other method, with nothing done. The conditions on dates and `If-Range` are not evaluated: no answer carries `Last-Modified`, and none is a range. **A send evaluates them before its dedupe** (§4.5 step 6), so a retry whose `If-Match` is false is `412`, not its first receipt, which RFC 9110 §13.1.1 would allow (`PRECEDENTS.md`, Part 2, § 4). No client needs any of it: the Go client sends `If-None-Match` on a poll and nothing else, and the rest is there because an origin server must evaluate what it receives.

- **The HTTP layer, in OpenAPI 3.1: `api/openapi.yaml`.** Every route, member, status and header this document gives, and nothing that protects a message: a client built from it alone checks nothing. This document governs where the two differ. No server serves it: `api/apitest` holds a server's answers to it in tests, the reference server's and this repo's fake's among them, and `api/`'s own tests hold it to `protocol/`'s codes and members (`PRECEDENTS.md`, Part 2, § 4, The API).
- **Logging**: no line the server logs, its access log's or an error's, carries an address or a message id in the clear: each is replaced by a short hash of itself, which only someone already holding it can match. Passes and request bodies are never logged. Cloudflare's own logs DO see addresses in URLs. The remedy for a leaked address is a new box, and revocation (§6.3). Pasting a share URL into a hosted chat also leaks it, to transcripts and link unfurlers.
